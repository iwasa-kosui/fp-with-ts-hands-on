<h2>Event Store</h2>

<p>Event Store は、起きた出来事をイベントとして記録する保存先です。完成形の Event Store は、イベントを受け取ると、予約の現在の状態の更新と、履歴の行の追記を、同じ1回の保存で行います。予約の現在の状態は、更新した行から読みます。履歴を最初から再生して現在の状態を作り直す方式（イベントソーシング）ではありません。</p>

<aside class="decision-card">
  <h3>このハンズオンで Event Store を選ぶ理由</h3>
  <p>Event Store を使うことは、DMMF（Scott Wlaschin の書籍『Domain Modeling Made Functional』）一般の必須条件ではなく、このハンズオンの設計です。成功イベントから、現在の状態の更新と履歴の追記を1回でそろえられ、誰がいつどの予約をキャンセルしたかを後から確認できるため、ユースケースの出力先に Event Store を選びます。</p>
</aside>

<h2>ビジネスイベントとワークフローから考える方法</h2>

<p>この回はデータから説明を始めました。これは説明の順序です。データベースの設計から業務を決めるという意味ではありません。</p>

<p>業務を発見する段階では、「データ構造よりも、ビジネスイベントとワークフローに注目する」という考え方もあります。ビジネスイベントは、「予約がキャンセルされた」のような業務で起きた出来事で、コードではイベントとして表します。ワークフローは、依頼を受けてからイベントが起きるまでの一連の処理です。イベントストーミングはその代表的な手法で、関係者が集まり、業務の出来事を付箋に書いて時系列に並べます。</p>
