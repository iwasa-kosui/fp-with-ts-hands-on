  <p>{"\n"}ビジネスユースケースとは、アクターが達成したい業務上の目的です。アクターは、システムを使って業務を行う人や外部のシステムです。例えば「受付担当者が予約をキャンセルする」がこれにあたります。{"\n"}</p>
  <p>ソフトウェアのユースケースは、S03で説明したとおり、ビジネスユースケースを実行する処理です。キャンセルのユースケースは、実行者と対象の予約を取得し、権限の有無、予約の存在、予約の現在の状態を確認してから、キャンセルの結果を作ります。</p>

<section id="rop">
  <h2>ROPでユースケースの失敗を扱う</h2>
  <p>前の表の「失敗の理由」が、ユースケースの失敗です。ROP（Railway Oriented Programming）は、工程の流れを成功と失敗の2本のレールで捉える考え方です。</p>

  <h3>成功と失敗の2本のレール</h3>
  <p>各工程は、成功なら次の工程へ値を渡し、失敗なら下のレールへ移って後続の工程を飛ばします。失敗の値は下のレールを終点まで進みます。図の4工程は、前の表の4工程と同じです。</p>
  <RailwayOrientedProgramming />

  <h3>S04のandThenは切り替え線に当たる</h3>
  <p>S04で使った <code>andThen</code> は、Ok のときだけ次の関数へ進み、Err になった後はコールバックを呼びません。これは、失敗のレールへ移った値が後続の工程を飛ばすことに当たります。業務エラーを返さない <code>map</code> は、切り替え線のない工程です。S04で書いた診察開始の処理は、図の工程に次のように当たります。</p>
  <table>
    <thead>
      <tr><th scope="col">図の工程</th><th scope="col">診察開始の処理</th><th scope="col">失敗のレールへ移る値</th></tr>
    </thead>
    <tbody>
      <tr><th scope="row">入力を検査する</th><td><code>StartExaminationInput.parse</code>。S03の境界で検査します</td><td>S03の境界で返す検査の失敗</td></tr>
      <tr><th scope="row">対象を取得する</th><td><code>resolver.resolveById</code> と <code>ensureAppointmentFound</code></td><td><code>AppointmentNotFound</code></td></tr>
      <tr><th scope="row">権限と状態を確認する</th><td><code>andThen(ensureCheckedIn)</code>。S04の演習コードは権限を確認しません</td><td><code>InvalidAppointmentState</code></td></tr>
      <tr><th scope="row">結果を作る</th><td><code>map(transitionToInExamination)</code> と <code>store.save</code></td><td>なし</td></tr>
    </tbody>
  </table>
  <p>キャンセルでは、3か所で失敗のレールへ切り替わります。次の図を左からたどり、どの条件で失敗のレールへ切り替わるかを確認してください。</p>
  <CancelRailwayAnimation />

  <h3>なぜROPを利用するのか</h3>
  <p>ROPでは、工程ごとに起きる失敗を同じ流れで扱います。キャンセルでは、「キャンセル先の予約が存在しない」「キャンセルする権限がない」などの理由で失敗したとき、後続の処理を実行しません。そのため、全体の処理のうち一部だけが実行されて不整合が起きることを防げます。たとえば、権限のない依頼でキャンセルの記録だけが残ることはありません。</p>
</section>

<section id="io-boundaries">
  <h2>I/Oをパイプラインの両端へ置く</h2>
  <p>この節では、S04で <code>deps</code> から受け取ったResolverとStoreを、キャンセルのパイプラインの両端に置く構成を読みます。中心のドメインロジックは、副作用のないpureな関数（純粋関数）として扱えます。副作用と純粋関数の意味は、<a href="/sessions/01-state-transitions/#pure-functions">S01の説明</a>を見てください。</p>
  <p>前の表の工程のうち、「対象を取得する」はデータベースを読むI/Oです。この工程はResolverが担います。記録はパイプラインの成功の後でStoreが担います。「入力を検査する」「権限と状態を確認する」「結果を作る」は、値だけで結果が決まります。</p>

  <h3>中心に置くpureな関数</h3>
  <p><code>Appointment</code>は、予約のデータと業務ルールの置き場です。一つのデータと一つのユースケースが常に対応するわけではありません。同じ予約のデータを、キャンセルや診察開始など複数のユースケースが扱います。</p>
  <p>手元の <code>examples/session-05</code> にも、キャンセルの結果を作る関数 <code>cancel</code> があります。診察開始前の予約、キャンセル理由、キャンセルした時刻を受け取り、<code>Canceled</code> の予約を返します。データベースへ接続せず、受け取った値だけで結果が決まります。</p>
  <Code code={props.cancelSource} lang="ts" />
  <p>完成形の参照実装（<code>examples/final</code>）の <code>Appointment.cancel</code> は、同じ確認を通った予約から、<code>Canceled</code> の予約の代わりにイベント <code>AppointmentCanceled</code> を返します。イベントは、出力側の節で読みます。</p>

  <h3>なぜResolverとStoreをドメインロジックの外へ置くのか</h3>
  <p>ResolverとStoreを外へ置くと、<code>cancel</code>はデータベースへ接続せず、入力された値だけで結果が決まります。業務ルールを値だけでテストできます。取得方法や記録先が変わっても、<code>cancel</code>を変更せずにResolverとStoreの実装を差し替えられます。S04の <code>startExamination</code> が resolver と store を <code>deps</code> から受け取ったのも、同じ理由です。</p>

  <h3>入力側：Resolverの役割</h3>
  <p>{"\n"}User ResolverとAppointment Resolverは、実行者と予約の現在状態を取得し、ユースケースへ値として渡します。S04の<code>resolver</code>と同じ役割です。下の図で、Resolverから受け取った値が確認の条件を通り、ドメインロジックへ渡るところをたどってください。{"\n"}</p>

  <h3>出力側：Storeの役割</h3>
  <p>{"\n"}<code>Appointment.cancel</code>は、確認を通った予約から<code>AppointmentCanceled</code>を作ります。Storeは、S04の<code>store</code>と同じく成功の後にだけ呼ばれ、その成功イベントを受け取ってEvent Storeへ渡します。失敗した場合はStoreが呼ばれません。そのため、不正なキャンセルや途中状態は記録されません。完成形の参照実装（<code>examples/final</code>）の<code>AppointmentCanceled</code>には、実行者のID、発生した時刻、予約のIDが入ります。誰がいつどの予約をキャンセルしたかは、Event Storeに追記されたこのイベントから確認できます。完成形の参照実装の Event Store は、イベントを受け取ると、予約の現在の状態の更新と、履歴の行の追記を、同じ1回の保存で行います。予約の現在の状態は、更新した行から読みます。履歴を最初から再生して現在の状態を作り直す方式（イベントソーシング）ではありません。{"\n"}</p>
  <CancelPipelineBoundaries />
  <h3 id="consistency-and-aggregate">整合性と集約</h3>
  <p>キャンセルでは、予約の状態を Canceled に変えるだけでなく、誰がいつキャンセルしたかの履歴も残します。この2つは、片方だけが書かれると困ります。予約は Canceled なのに履歴にキャンセルが無い状態や、履歴にキャンセルがあるのに予約が Scheduled のままの状態です。業務のルールが求めるデータの組み合わせが崩れていないことを、整合性が保たれていると言います。</p>
  <AggregateConsistencyFlow />
  <p>一緒に変えないと整合性が崩れるデータのまとまりを、集約と呼びます。集約は DDD（ドメイン駆動設計）の用語です。このハンズオンでは、予約1件の現在の状態と、その予約の履歴が、予約の集約に入ります。</p>
  <p>DDDでは、1回の保存で変える集約は1つにする、という指針がよく示されます。診察の完了で診察結果と予約を1回で保存するのは、この指針から外れる、完成形の参照実装の判断です。集約をまたいで1回で保存すると、同時に保存できる操作が減ります。その代わりに、診察結果だけが残る状態を作りません。</p>
  <p>2つの書き込みを1回の保存にまとめる実装は、S06で書きます。</p>
  <p>{"\n"}配布コード<code>examples/session-01</code>の<code>startExamination</code>は、S01〜S04で学んだ形より前の段階のコードです。<code>Repository</code>（データベースの読み書きをまとめたオブジェクト）からの取得、状態の記録、監査記録（誰がいつ何をしたかを後から確かめるための履歴）、時刻とIDの生成を、一つのユースケースで行います。このコードは、このハンズオンで目指す形ではありません。時刻とIDの生成を外から渡す話と、状態と監査記録を1回の保存にまとめる話は、次のS06で扱います。{"\n"}</p>
  <aside class="decision-card">
    <h3>このハンズオンでEvent Storeを選ぶ理由</h3>
    <p>{"\n"}Event Storeを使うことは、DMMF（Scott Wlaschin の書籍『Domain Modeling Made Functional』）一般の必須条件ではなく、このハンズオンの設計です。成功イベントから、現在の状態の更新と履歴の追記を1回でそろえられ、誰がいつどの予約をキャンセルしたかを後から確認できるため、ユースケースの出力先にEvent Storeを選びます。{"\n"}</p>
  </aside>
</section>
