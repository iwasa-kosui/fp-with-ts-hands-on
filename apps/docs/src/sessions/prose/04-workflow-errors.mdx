  <article class="teaching-topic" id="rop-recap">
    <h3>ROPで失敗の流れを捉える</h3>
    <p>診察開始は、入力を検査する、対象を取得する、権限と状態を確認する、結果を作る、という工程を順に実行します。ROPは、この工程の流れを成功と失敗の2本のレールで捉える考え方です。</p>
    <p>各工程は、成功なら次の工程へ値を渡し、失敗なら下のレールへ移って後続の工程を飛ばします。失敗の値は下のレールを終点まで進みます。</p>
    <RailwayOrientedProgramming />
    <p>ROPを使うと、予約が見つからない、来院済みでないといった工程ごとの失敗を、同じ流れで扱えます。失敗した後に状態遷移や保存だけが実行され、途中の状態が残ることを防げます。図の工程と診察開始の処理は、次のように対応します。</p>
    <table>
      <thead>
        <tr><th>図の工程</th><th>診察開始の処理</th><th>失敗レールへ移る値</th></tr>
      </thead>
      <tbody>
        <tr><th>入力を検査する</th><td><code>StartExaminationInput.parse</code>。Session 03の境界で検査します</td><td>このセッションでは扱いません</td></tr>
        <tr><th>対象を取得する</th><td><code>resolver.resolveById</code> と <code>ensureAppointmentFound</code></td><td><code>AppointmentNotFound</code></td></tr>
        <tr><th>権限と状態を確認する</th><td><code>ensureCheckedIn</code>（権限はこのセッションでは扱いません）</td><td><code>InvalidAppointmentState</code></td></tr>
        <tr><th>結果を作る</th><td><code>transitionToInExamination</code> と <code>store.save</code></td><td>なし</td></tr>

    </table>
    <p>失敗レールを進むのは、呼び出し側が理由別の対応を選べる失敗です。このセッションでは、この失敗を業務エラーと呼びます。一方、保存障害のように呼び出し側に理由別の対応がない異常はシステムエラーと呼びます。システムエラーは失敗レールへ載せず、例外として外側へ伝えます。</p>

  <article class="teaching-topic">
    <h3>neverthrow の Result で失敗を値として表す</h3>
    <p>前の例の Result、ok、err、isErr は neverthrow というライブラリが提供しています。Result&lt;T, E&gt; の T は成功値、E は呼び出し側が扱う業務エラーです。ok(value) は成功側の Ok、err(error) は失敗側の Err を作り、どちらも Result&lt;T, E&gt; として扱えます。</p>
    <p>Result に含める失敗は、先に呼び出し側の対応から選びます。失敗理由に応じて呼び出し側が次の操作を選べる業務エラーを E として返します。</p>
    <p>たとえば、予約が見つからなければ予約を探し直し、まだ受付されていなければ受付を先に行います。呼び出し側が理由ごとに異なる対応を選ぶ必要があるため、これらは Err で返します。</p>
    <p>一方、呼び出し側に理由別の対応がなく、要求された処理を完了できない異常はシステムエラーとして扱います。このような異常はResultに変換せず、例外として外側へ伝えます。</p>
    <p>たとえば、データベースへの保存中に接続が切れ、保存が完了したか確認できない場合です。データベースへの保存が完了したか確認できないままキューへのイベント追加や外部サービスへの通知を行うと、データベースには保存されていないのに、イベントや通知だけが送られる可能性があります。そのため、イベント追加や通知は実行せず、保存時の例外をそのまま外側へ伝えます。</p>
    <p>外側の例外境界では、例外をログへ記録し、必要なロールバックや接続の解放を行ったうえで、500などのエラー応答へ変換します。</p>
