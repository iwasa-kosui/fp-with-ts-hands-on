  <article class="teaching-topic" id="exception-or-result">
    <h3>例外と Result を使い分ける</h3>
    <p>失敗には、Result の Err として返すものと、例外のまま外側へ伝えるものがあります。どちらにするかは、呼び出し側がその失敗の理由ごとに次の操作を選べるかで決めます。このハンズオンでは、前者を業務エラー、後者をシステムエラーと呼びます。</p>
    <table>
      <thead>
        <tr><th scope="col"></th><th scope="col">業務エラー</th><th scope="col">システムエラー</th></tr>
      </thead>

        <tr><th scope="row">呼び出し側の対応</th><td>予約を探し直す、先に受付を行う</td><td>理由ごとに選べる操作はない</td></tr>
        <tr><th scope="row">伝え方</th><td><code>err</code> で Result の Err として返す</td><td>Result に変換せず、例外のまま伝える</td></tr>
        <tr><th scope="row">受け取る場所</th><td>Web ルートの <code>match</code> と <code>switch</code></td><td>外側の例外境界</td></tr>
      </tbody>
    </table>
    <p>次の図で、2つの失敗がどこで止まり、どこで受け取られるかを見比べます。図のコードの andThen、map、match は後の節で説明します。</p>
    <ExceptionOrResultAnimation />
    <p>システムエラーを Result に変換しないのは、保存が完了したか分からないまま後続の処理を続けないためです。保存の結果を確認できないまま別の記録先への書き込みや外部サービスへの通知を行うと、データベースには保存されていないのに、書き込みや通知だけが行われる可能性があります。演習コードの外側の例外境界は <code>app.onError</code> で、例外を受け取ると500を返します。実際の業務では、この境界で例外をログへ記録し、必要なロールバック（途中まで進めたデータベースへの書き込みを取り消すこと）や接続の解放も行います。</p>
    <p class="teaching-topic__why">業務エラーを例外で投げると、関数の型から失敗理由を読み取れず、呼び出し側は処理漏れに気付けません。システムエラーを Result に入れると、呼び出し側に選べる操作がない失敗まで型に並び、すべての呼び出し側が同じ処理を書くことになります。迷ったときは、呼び出し側がこの失敗の理由ごとに違う操作を選ぶかを確かめます。</p>
