S05は18分の回です。コードは編集しません。予約のデータから始め、キャンセルをデータを順に処理するパイプラインとして読みます。

3. 10:00〜16:00: 工程の条件を守る仕組みを選ぶ演習で、必須の誤った変更3件を検出します。

## 参加者が行うこと

## パイプラインとROP

- 入力は、予約ID、実行者ID、キャンセル理由です。
- 入力の検査は、ユースケースの手前の境界で行います。ユースケースの工程は、「実行者の確認」「予約の確認」「結果を作る」「記録して返す」の4つです。
- `Appointment.cancel`は、確認を通った診察開始前の予約とキャンセル理由を受け取り、成功イベントを返します。
- 成功出力は`AppointmentCanceled`です。
- 失敗出力は`Unauthorized`、`AppointmentNotFound`、`InvalidAppointmentState`、`AppointmentConflict`など、理由を区別できるエラーです。

User ResolverとAppointment Resolverによる現在状態の取得は入力側へ置きます。`AppointmentCanceled`を受け取るEvent Storeは出力側へ置きます。権限の確認、状態の確認、結果の作成はデータベースへ接続せず、入力からイベントか型付きエラーを返します。

ROPでは、それぞれの処理で起きる失敗を同じ流れで扱います。失敗を網羅的に検証するので、変更箇所とテストの観点を追いやすくなります。予約がない、権限がないなどの理由で処理が止まっても、適切に対応できます。また、処理の一部だけが実行されて不整合が起きることを防げます。

Event StoreはDMMFの必須要件ではありません。このハンズオンでは、パイプラインの成功出力と保存の入力を同じイベントでつなぐために選びます。

## 持ち帰る内容

1. キャンセル前とキャンセル後の予約のデータ
2. 権限、予約の存在、現在状態、理由の条件
3. 3か所で失敗へ切り替わるROP基本図と、ResolverとEvent Storeを外側へ置いたユースケース図

## S01〜S04の診察開始とのつながり

S01〜S04の診察開始も、キャンセルと同じ形で読めます。入力は「どの予約を、どの獣医師が開始するか」です。確認する条件は「来院済みだけが診察を開始できる」です。
