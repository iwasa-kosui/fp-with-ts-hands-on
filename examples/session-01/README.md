# Session 01: EventStormingとROPで予約キャンセルを設計する

S1は15分の班ワークです。コードは編集しません。「予約がキャンセルされた」という一つの出来事から、依頼、業務ルール、集約、成功出力を逆算します。

## 15分の進行

1. 0:00〜2:00: 一つのドメインイベントを確認します。
2. 2:00〜6:00: アクター、コマンド、業務ルールを班で決めます。
3. 6:00〜8:00: 業務ルール、`Appointment`集約、業務ワークフローの違いを確認します。
4. 8:00〜10:00: ROPの成功レールと失敗レール、3つの切替点を読みます。
5. 10:00〜14:00: EventStormingの要素を業務ワークフローへ写します。
6. 14:00〜15:00: ResolverとEvent Storeをワークフローの外側へ置きます。

## 参加者が行うこと

- 誰が何を依頼したために、予約がキャンセルされたかを逆算します。
- 実行者の権限、予約の存在と現在状態、キャンセル理由の条件を業務ルールとしてまとめます。
- 答えが揃わない点はHotspotとして残します。

条件は次の文へ揃えます。

> 予約を管理できる担当者が、診察開始前の予約だけを、理由を残してキャンセルできます。

## EventStormingからROPへ写す

- コマンドは業務ワークフローの入力です。
- 権限や状態の条件は、ワークフロー内部の業務ルールです。
- `Appointment`集約の`Appointment.cancel`を内部のドメイン判断として呼びます。
- 成功出力は`AppointmentCanceled`です。
- 失敗出力は`Unauthorized`、`AppointmentNotFound`、`InvalidAppointmentState`、`AppointmentConflict`など、理由を区別できるエラーです。

User ResolverとAppointment Resolverによる現在状態の取得は入力側へ置きます。`AppointmentCanceled`を受け取るEvent Storeは出力側へ置きます。中心の業務ワークフローはデータベースへ接続せず、入力からイベントか型付きエラーを返します。

ROPを使うと、顧客にとっては途中で条件に違反した依頼がキャンセルや保存へ進まず、「一部だけ処理された」を防げます。技術者にとっては失敗を共通の出口へ流せるため、条件追加とテストケースの対応が明確になります。

永続化を両端へ置くと、顧客にとっては条件を通過したキャンセルだけが保存され、誰がいつ取り消したかを追えます。技術者にとっては業務ルールをデータベースAPIから切り離し、値だけでテストしながら読み方や保存先を交換できます。

Event StoreはDMMFの必須要件ではありません。このハンズオンでは、業務ワークフローの成功出力と保存の入力を同じイベントでつなぐために選びます。

## 残す成果物

1. アクター、コマンド、`Appointment`集約、`AppointmentCanceled`を順に並べた図
2. 権限、予約の存在、現在状態、理由の条件とHotspot
3. 3か所で失敗へ切り替わるROP基本図と、ResolverとEvent Storeを外側へ置いた業務ワークフロー図

班ワークには`docs/event/session-01-event-storming.excalidraw`を使います。TAがS1の開始前にボードを開きます。共同編集が30秒で復旧しない場合は、印刷したカードへ切り替えます。
