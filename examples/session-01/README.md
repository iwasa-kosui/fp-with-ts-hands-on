# Session 01: EventStormingから診察開始を定義する

S1は15分の班ワークです。コードは編集しません。講師が事前配置した4つのドメインイベントを見て、「診察が開始された」からアクター、コマンド、事前条件を逆算します。

題材のアプリは起動できます。

```bash
pnpm demo:01
```

`http://localhost:3000` で、会計済みの予約でも診察を開始できる事故を確認できます。

## 15分の進行

1. 0:00〜1:30: 事故と4つのドメインイベントを確認します。
2. 1:30〜3:00: ドメインイベント、アクター、コマンド、Hotspotを確認します。
3. 3:00〜7:00: 診察開始のアクター、コマンド、事前条件を班で決めます。
4. 7:00〜9:00: 班の答えを比べ、講師が予約集約を加えます。
5. 9:00〜15:00: EventStormingの並びをROPへ対応させ、読み込みと保存をワークフローの外へ置きます。

## 参加者が行うこと

- 「診察が開始された」からアクターとコマンドを逆算します。
- アクターの認識が違う場合はHotspotとして残します。
- 診察開始の事前条件を業務の言葉で1文にします。

事前条件は次の文へ揃えます。

> 受付を済ませた予約だけ、診察を始められます。

集約名を当てる作業や、一日の全イベントを集約ごとに分類する作業は行いません。事前条件を決めた後、講師が予約集約を加え、状態と業務判断の単位として説明します。

## EventStormingからROPへ写す

EventStormingで見つけた要素を次のように対応させます。

- コマンドはワークフローの入力にします。
- 予約集約は、現在状態から診察を開始できるか判断します。
- 成功時は `ExaminationStarted`、失敗時は `StartExaminationError` を返します。

Appointment Resolverによる現在状態の取得は入力側の境界へ置きます。成功イベントを受け取るEvent Storeは出力側の境界へ置きます。`startExamination` はデータベースへ接続せず、受け取った入力から結果を返します。

Event StoreはDMMFに必須の永続化方式ではありません。このハンズオンでは、EventStormingで合意したイベントをワークフローと永続化の共通の契約にするために採用します。

## 残す成果物

1. アクター、コマンド、予約、ドメインイベントを並べたEventStormingの図
2. 「受付を済ませた予約だけ、診察を始められる」という事前条件
3. Resolverを入口、Event Storeを出口に置き、成功イベントと型付きエラーへ分岐する `startExamination` の構成図

班ワークには `docs/event/session-01-event-storming.excalidraw` を使います。TAがS1の開始前にボードを開きます。共同編集が30秒で復旧しない場合は、印刷したカードへ切り替えます。
