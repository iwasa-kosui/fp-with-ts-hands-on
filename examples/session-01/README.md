# Session 01: データとパイプラインで予約キャンセルを設計する

S5は15分の回です。コードは編集しません。予約のデータから始め、キャンセルをデータを順に処理するパイプラインとして読みます。

## 15分の進行

1. 0:00〜2:00: ひと幕と、予約のキャンセル前とキャンセル後のデータを確認します。
2. 2:00〜9:00: パイプラインの4工程、ROPの成功レールと失敗レール、I/Oの分離を読みます。
3. 9:00〜13:00: データとパイプラインについての3問に答えます。
4. 13:00〜15:00: 答えと持ち帰る内容を確認します。

## 参加者が行うこと

- キャンセル前とキャンセル後の予約のデータを見比べ、変わる項目と変わらない項目を分けます。
- 会計済みの予約と、キャンセル理由が空の依頼が、パイプラインのどの工程で止まるかを答えます。
- 答えが揃わない点は未決の問いとしてメモに残します。

キャンセルを許す条件は次の文へ揃えます。

> 予約を管理する担当者が、診察開始前の予約だけを、理由を記入してキャンセルできます。

## パイプラインとROP

- 入力は、予約ID、実行者ID、キャンセル理由です。
- 工程は、「入力を検査する」「対象を取得する」「権限と状態を確認する」「結果を作る」の4つです。
- `Appointment.cancel`は、確認を通った診察開始前の予約とキャンセル理由を受け取り、成功イベントを返します。
- 成功出力は`AppointmentCanceled`です。
- 失敗出力は`Unauthorized`、`AppointmentNotFound`、`InvalidAppointmentState`、`AppointmentConflict`など、理由を区別できるエラーです。

User ResolverとAppointment Resolverによる現在状態の取得は入力側へ置きます。`AppointmentCanceled`を受け取るEvent Storeは出力側へ置きます。権限と状態の確認と結果の作成はデータベースへ接続せず、入力からイベントか型付きエラーを返します。

ROPでは、それぞれの処理で発生する失敗を同じフローで扱い、その失敗を網羅的に検証することで、変更箇所とテスト観点を追いやすくします。これにより、予約なしや権限なしなどの理由で止まっても適切にハンドリングでき、一部だけ処理されて不整合が発生することを防げます。

Event StoreはDMMFの必須要件ではありません。このハンズオンでは、パイプラインの成功出力と保存の入力を同じイベントでつなぐために選びます。

## 持ち帰る内容

1. キャンセル前とキャンセル後の予約のデータ
2. 権限、予約の存在、現在状態、理由の条件
3. 3か所で失敗へ切り替わるROP基本図と、ResolverとEvent Storeを外側へ置いたユースケース図

## 後続のセッションとのつながり

後続のセッションでは、診察開始を題材にします。入力は「どの予約を、どの獣医師が開始するか」です。確認する条件は「受付済みだけが診察を開始できる」です。
