## 1. エグゼクティブサマリー

このハンズオンは、関数型ドメインモデリングの技法を網羅的に教える講座ではない。参加者が業務上の既存実装を見つめ直し、事故や変更要求を手がかりに問題を発見し、必要な設計手段を選んで段階的に改善できるようになるための実践機会である。

参加者は、動物病院の予約・カルテ管理システムに生じる要求と事故を追体験する。S0 で事故報告と既存コードを観察し、S1〜S4 の4演習では、守るべき不変条件を言語化し、依頼文へ変換して委譲し、自分の差分を型とテストで検証した後に班内相互レビューを行う。各演習は1モジュールに範囲を絞り、次のスナップショットへ解答と回帰テストを持ち越す。`examples/session-05` を当日の到達点とし、Final では `examples/final` を講師が参照実装として案内する。この反復を通じて、関数型ドメインモデリングを「完成形として導入するもの」ではなく、「目の前の問題を一つずつ減らすために使える手立て」として捉え直す。

このハンズオンが目指す最終成果は、参加者がイベント後の業務で既存実装を観察し、小さな改善を一つ実践し、その判断理由と次の改善候補を説明できることである。

## 2. 背景と解決する課題

「関数型ドメインモデリング」という言葉や代表的な技法を知る機会は増えている。一方で、完成されたサンプルと日々保守している業務アプリケーションの間には距離がある。既存実装には期限、互換性、チームの習熟度などの制約があり、理想的なモデルへ一度に置き換えることは難しい。

そのため、関心を持った開発者が次の段階へ進めないことがある。

- 既存実装のどこを問題として捉えるべきか分からない
- Discriminated Union や Result 型などを、どの業務課題へ使うべきか判断できない
- 全面的な再設計が必要に見え、小さな着手点を決められない
- 技法の導入と、事故や変更コストを減らす効果を結びつけられない
- 型で守れることと、人が仕様として判断すべきことを区別できない

このプロダクトは、理想的な完成形を示すだけでなく、問題の発見から次の改善候補を決めるまでの反復可能な進め方を提供することで、この隔たりを埋める。

## 3. プロダクトビジョン

### ビジョン

TypeScript 開発者が、関数型ドメインモデリングを特別な全面刷新としてではなく、既存の業務アプリケーションから問題を段階的に減らすための日常的な選択肢として使えるようにする。

### 提供価値

参加者の認識と行動を、次のように転換する。

> 関数型の技法を知っている

から、

> 目の前の業務上の問題を捉え、必要な手段を選び、小さく適用し、効果を確かめて次へ進める

### ジョブ

業務アプリケーションの既存実装に事故や変更要求が生じたとき、開発者が守るべき業務ルールを見つけ、無理のない変更単位と設計手段を選び、改善を継続できるようにする。

## 4. 対象参加者

### 主対象者

TypeScript の基本文法を使って業務アプリケーションを開発している初級から中級の開発者を主対象とする。次のような状態を想定する。

- 関数型ドメインモデリングに関心がある
- Discriminated Union、Branded Type、Result 型などの名前を聞いたことがある、または初見でも TypeScript の型を読める
- 完成されたサンプルを見ても、自分たちの既存コードへどこから適用するか判断できない
- 段階的に導入できるものか、導入した結果として何が改善されるのか、具体的なイメージを持てない

### 前提知識と参加条件

- TypeScript の基本文法を読み書きできる
- 関数、オブジェクト、union、テストコードの基本的な読み方を理解している
- Node.js 20以上、pnpm、Git、TypeScript を編集できるエディタを用意できる
- 関数型プログラミングやドメイン駆動設計の実務経験は求めない

### 主対象としない参加者像

- 関数型プログラミング理論を体系的に学ぶことだけを目的とする人
- 特定の関数型ライブラリのAPI習得を目的とする人
- 新規システムの理想的な全体アーキテクチャを設計したい人
- TypeScript の基本文法やテストコードをまだ読めない人

参加を拒む区分ではなく、本ハンズオンが提供する中心価値との適合を示すための定義である。

## 5. 期待する行動変容

### 参加前

参加者は技法に関心を持っているが、既存実装から問題を見つけ、適用範囲を決め、業務上の効果を確かめるまでの進め方を持っていない。

### ハンズオン終了時

参加者は、未知の既存コードを題材に次の行動を実行できる。

1. 壊れ得る業務ルールを一つ発見する
2. 発見した問題を、守るべき不変条件として説明する
3. 問題に合う設計手段を選び、その選択理由を説明する
4. 全面刷新ではなく、1モジュールに閉じた変更単位を決める
5. 不変条件を依頼文へ変換し、差分を型とテストで個人検証する
6. 型で守れる範囲、実行時の分岐で守る範囲、人がレビューすべき範囲を区別する
7. 班内相互レビューを通じて、未解決の問題から次の改善候補を一つ決める

### ハンズオン後1か月以内

参加者が業務で次の行動を一つ以上実践している状態を目指す。

1. **既存実装を観察する**

   `string` による状態表現、optional項目の増加、未検証の外部入力、`throw`、過剰なログ出力などから、業務上の問題につながる箇所を発見する。
2. **問題を設計課題へ翻訳する**

   不具合や変更要求を、守るべき不変条件、入力境界、失敗の種類、追跡すべき出来事として言語化する。
3. **適用する手段を選ぶ**

   一括導入ではなく、Discriminated Union、Branded Type、スキーマ検証、Result 型などから必要な手段だけを選ぶ。
4. **小さな改善を実装する**

   一つのモジュールを対象に、不変条件、依頼文、型で守れなかった残りを残しながら、局所的な型と関数の変更によって改善する。
5. **改善結果を検証する**

   型の高度さではなく、不正状態を作れない、入力事故を境界で止められる、失敗理由を呼び出し元が扱えるなどの効果を確認する。
6. **次の改善につなげる**

   今回守れたことと未解決の問題を整理し、次に改善する小さな対象を決める。
7. **チームへ説明する**

   技法名だけでなく、どの事故や変更コストを減らすために、なぜその範囲へ適用したかを同僚へ説明する。

### 行動変容モデル

```text
技法への関心はある
  ↓
既存実装から業務上の問題を発見する
  ↓
問題を不変条件・境界・失敗・出来事として整理する
  ↓
必要な設計手段を一つ選ぶ
  ↓
言語化し、委譲し、個人検証と班内相互レビューを行う
  ↓
効果を確認し、次の改善対象を決める
```

## 6. ゴールと非ゴール

### ゴール

- 既存実装の観察から始める改善手順を体験する
- 業務上の問題と設計手段の対応関係を理解する
- 問題に対して必要最小限の適用範囲を判断する
- テストを使って問題と改善効果を確認する
- 改善を一度で完成させず、次の小さな改善へつなげる
- 設計判断を依頼文と人間のレビューへ転用する

### 非ゴール

- 関数型プログラミング理論の網羅
- 代表的な関数型ドメインモデリング技法の網羅
- 特定ライブラリの習熟
- 理想的な新規アーキテクチャの完成
- 既存システムの全面刷新
- event sourcing、レイヤードアーキテクチャ、ロギング基盤などの詳細設計
- AIエージェントだけで業務要件を正しく実装できるようにすること

## 7. 体験設計

### 共通の学習ループ

S1〜S4 の各演習を、次の順序で進める。

```text
要求・事故を知る
  → 失敗するテストで問題を再現する
  → 守るべき不変条件を言語化する
  → 不変条件を依頼文に落とし、委譲する
  → 各参加者が自分の差分を型とテストに照らして個人検証する
  → 班内で差分を比較し、不変条件が守られる境界を相互レビューする
  → テストが成功することを確認し、次の改善候補を整理する
```

技法の説明を入口にしない。最初に業務上の要求または事故を示し、何を守るためにその技法を使うのかを参加者が考えてから、実装へ進む。

### モジュールと行動変容の対応

| セッション | 時間 | 提示する要求・事故 | 主な行動変容 | 用いる手段 |
| --- | --- | --- | --- | --- |
| S0: 引き継ぎ | 15分 | 会計済みの予約が診察中へ戻り二重請求された。予約全体のログから PII が流出した | 既存実装を観察し、業務上の問題を発見する | 事故報告と既存コードの読解 |
| S1: 状態を型にする | 30分 | 終端状態から戻れる。状態に必要な情報が欠ける | `Scheduled | CheckedIn | InExamination | Paid | Canceled` の5状態を不変条件として翻訳し、適用手段を選ぶ | Discriminated Union、純粋な状態遷移関数 |
| S2: 値を型にする | 30分 | 外部入力で ID を取り違える。PII がログへ出る | 種類の異なる問題を分け、それぞれに必要な防御を選ぶ | Zod、Branded Type、`Sensitive` |
| S3: 失敗を値にする | 35分 | 失敗理由が呼び出し元へ伝わらない | 予期可能な失敗を、利用側が扱える形にする | Result 型、純粋なユースケース、fake port テスト |
| S4: 副作用を外に出す | 35分 | 現在状態と監査記録が別々に保存され、非決定的な値がテストを不安定にする | 副作用の境界と成功時の記録を明示する | `ResultAsync`、port、`andThrough`、型付きドメインイベント |
| Final: 参照実装ツアー | 5分 | `examples/session-05` の到達点を、より大きな実装へ接続する | 当日の到達点と参照実装の関係を説明する | `examples/session-05` と `examples/final` の講師ツアー |

### 体験設計上の要件

- S0 は事故報告と既存コードの観察から始め、S1〜S4 は技法名ではなく業務上の要求または事故から始める
- S1〜S4 では、技法を導入する前に守るべき不変条件を参加者が言語化する時間を設ける
- 各技法について、解決する問題と解決しない問題を明示する
- S1〜S4 のコード編集では、参加者の編集範囲を1モジュール（最大5ファイル・実効80行）に限定し、進行を最大4ステップ、下す設計判断を最大3件に制限する
- 改善前後を同じテストまたは同じ検証観点で比較する
- S1〜S4 の最後に、業務へ転用するための問いを置く。Final は参加者が編集する演習ではなく、`examples/final` を講師が5分で案内する参照実装ツアーとする
- AIエージェントは主目的にせず、利用する場合は設計判断を依頼文とレビューへ転用する題材として扱う。利用は推奨するが必須にしない
- 参加者はローカル clone を主線として進め、Playground は説明用・退避先として用いる
- `examples/session-05` は S1〜S4 の解答と回帰テストを統合した到達点スナップショットであり、参加者向けセッション一覧には含めない。`examples/final` は当日編集せず、参加者は環境構築しない
- 時間が不足した場合は実装量を減らし、問題の観察と判断理由の説明を優先する

## 8. プロダクト要件

### 必須要件

| ID | 要件 |
| --- | --- |
| PRD-01 | 冒頭で、完成形の習得ではなく段階的な問題解決がゴールであると参加者へ伝える |
| PRD-02 | S0 では事故報告と既存コード、S1〜S4 では要求または事故と守るべき不変条件を明示する。 |
| PRD-03 | S1〜S4 に、問題を再現する演習用テストまたは観察可能な失敗を用意する。S0 では事故報告とコードの対応を観察できるようにする。 |
| PRD-04 | S1〜S4 で、採用する技法と解決対象の対応関係を説明する。 |
| PRD-05 | S1〜S4 で、採用する技法だけでは解決できない範囲を説明する。 |
| PRD-06 | コード編集を行うモジュールでは、参加者の編集範囲を1モジュール（最大5ファイル・実効80行）に限定し、進行を最大4ステップ、下す設計判断を最大3件に制限する |
| PRD-07 | 改善後に、守れるようになったことをテストまたは型検査で確認できるようにする |
| PRD-08 | S1〜S4 の最後に、同種の問題を業務で探すための振り返り設問を置く |
| PRD-09 | S1〜S4 で問題の発見、手段の選択、局所的な変更、個人検証、班内相互レビューを一巡させ、`examples/session-05` に全解答と回帰テストを統合する |
| PRD-10 | 終了時に、参加者が業務で見直す具体的な実装箇所と最初の行動を記述できるようにする |
| PRD-11 | 30日後に行動を確認するフォローアップを実施する |
| PRD-12 | ファシリテーターが実装量を減らしても、またはコーディングエージェントを利用しない参加者でも、判断の学習を継続できる代替進行を用意する |
| PRD-13 | コード編集を行うモジュールでは、参加者が (a) 守る不変条件の1文、(b) 依頼文、(c) 型で守れなかった残り、の3つを成果物として残す。 |
| PRD-14 | コード編集を行うモジュールでは、各参加者の個人検証後に班内の相互レビューを1回行う。S1・S2 では7分、S3・S4 では8分を確保する。原則として TA が班から2名の差分をピックアップして比較し、2名を選べない場合のみ1名を選ぶ。班の全員が同じ画面を見て、不変条件が型で守られているか実行時の分岐で守られているかを判定する。参加者へ投げる問いをあらかじめ定義しておく。 |
| PRD-15 | 予約の状態は `Scheduled | CheckedIn | InExamination | Paid | Canceled` の5状態とし、`AwaitingPayment` を導入しない。S1 の状態モデリングでこの状態モデルと遷移を扱う。 |

### 品質要件

- 通常の `pnpm test` は、参加者が編集する前の環境確認として成功する
- S1〜S4 で扱う失敗は、専用の `pnpm exercise:01` から `pnpm exercise:04` で通常テストと区別できる。演習の RED はモジュール解決エラーではなく、業務の言葉で命名された assertion failure とする
- テストの失敗理由から、対象となる業務上の問題を読み取れる
- `examples/session-05` は S1〜S4 の全回帰テストを成功させる到達点とする。`examples/final` は講師ツアーだけに用い、参加者の環境構築を求めない
- ドキュメントは「次に何を観察し、何を実行し、何を確認するか」を各段階で一つに絞り、エージェントを利用しない参加者はステップ単位の解答提示へ復帰できる
- S1〜S4 の差分レビューは `git diff --stat -- examples/session-0N` の形で現在の開始snapshotへ限定し、`git status --short` でリポジトリ全体の想定外pathを別に確認する。前のセッションの未commit差分を消すための reset、stash、commit を参加者へ強制しない
- 演習にデータベース、Docker、外部APIキーを必要としない

## 9. 成功指標

初回開催では、次の数値を検証対象となる仮説として置く。イベント規模と実測値を記録し、次回開催時に基準値を見直す。

### 当日指標

| 指標 | 目標 | 判定方法 |
| --- | --- | --- |
| S1〜S4 の設計判断を説明できる参加者 | 参加者の80%以上 | 不変条件、依頼文、型で守れなかった残り、レビュー観点シートの4項目中3項目以上を、提出シートまたはファシリテーターの確認で説明できる |
| 業務での最初の行動を決めた参加者 | 参加者の70%以上 | 終了時に「見直す実装箇所」と「最初の小さな行動」の両方を具体的に記述できる |

### 30日後指標

| 指標 | 目標 | 判定方法 |
| --- | --- | --- |
| 業務で改善行動を実践した参加者 | 全参加者の30%以上 | 既存実装の調査、改善提案、テスト追加、局所的な実装変更、レビューでの指摘のいずれかについて、対象と判断理由を報告する |
| 改善結果と次の候補を共有した参加者 | 全参加者の15%以上 | チーム内で共有した改善効果と、次に見直す対象を報告する |

分母はアンケート回答者ではなく、当日の全参加者とする。回答率も併記し、回答者だけを分母にした過大評価を避ける。業務上の機密情報やソースコードの提出は求めず、対象となった問題、選んだ手段、確認した効果を抽象化して回答できる形式にする。

## 10. 計測計画

### 当日

- 冒頭で、既存実装の問題に対する現在の着手方法を簡潔に尋ねる
- S1〜S4 の各チェックポイントで、実装完了数ではなく不変条件と依頼文を説明できる人数を確認する
- S1〜S4 の成果物とレビュー観点シートから、不変条件、依頼文、型で守れなかった残り、レビュー観点の4項目を収集する
- 終了時に、業務で見直す実装箇所と最初の行動を収集する
- 環境問題、時間不足、内容理解のどこで進行が止まったかをファシリテーターが記録する

### 30日後

- 実践した行動の種類を選択式で確認する
- 対象となった問題、選んだ手段、判断理由、確認した効果を自由記述で確認する
- 実践できなかった場合は、知識、適用対象、時間、チーム合意、技術的制約のどこが障壁だったかを確認する
- 次に試す行動が決まっているかを確認する

## 11. 制約と前提

- 開催は180分、オフライン、5人1班と各班TA1名で行う
- セッションの内容時間は150分とし、S0=15分、S1=30分、S2=30分、S3=35分、S4=35分、Final=5分に配分する。固定枠30分を合わせて、合計180分とする
- S1〜S4 の ADV（言語化 → 委譲 → 個人検証）は、順に S1=2+9+2分、S2=2+8+2分、S3=2+10+3分、S4=2+10+3分とする
- 対象は TypeScript 初級から中級とする
- 題材は動物病院の予約・カルテ管理システムとする
- 演習は S1〜S4 の4本とし、各演習の編集範囲を1モジュール（最大5ファイル・実効80行）、進行を最大4ステップ、設計判断を最大3件に制限する
- 新しい技法を学ぶ時間より、問題と適用理由を考える時間を優先する
- 通常テストと演習用テストを分離する
- 演習コマンドは `pnpm exercise:01` から `pnpm exercise:04` とし、S0 と到達点スナップショットには演習コマンドを設けない
- コーディングエージェントは推奨するが必須にしない。ローカル clone を主線、Playground を説明用・退避先とする
- `examples/session-05` は単一集約の `ResultAsync` pipeline を含む到達点スナップショットであり、`examples/final` は5分の講師ツアー専用の凍結された参照実装とする
- 進行が遅れた場合、ステップ単位の解答を提示し、個人検証と相互レビューを保ちながら実装量を減らす
- 参加者の業務コードや機密情報を収集しない

## 12. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 技法の学習自体が目的化する | 業務課題との対応を説明できない | 必ず要求・事故から始め、技法の適用理由と限界を言語化する |
| 扱う概念が多く認知負荷が高い | 手を動かすだけで判断過程が残らない | S1〜S4 の編集を1モジュール（最大5ファイル・実効80行）、最大4ステップ、最大3件の設計判断に限定し、Final では新しい概念を増やさない |
| 環境構築で時間を失う | 中心体験へ到達できない | ローカル clone を主線に事前セットアップと通常テストを用意し、Playground、トラブルシューティング、ステップ単位の解答を退避先にする |
| 全面刷新が正解だと受け取られる | 業務へ適用できない | 局所的な変更と、未解決事項を残して次へ進むことを成功条件にする |
| AIエージェントの使い方が主題になる、または利用できない参加者が取り残される | 人間の設計判断が薄れる、または演習を完走できない | AIは依頼とレビューへの転用例に限定し、不変条件の決定は人が担うと明示する。エージェントを利用しない参加者にはステップ単位の解答を用意する |
| 30日後アンケートの回答率が低い | 行動変容を過大評価または過小評価する | 全参加者を分母にし、回答率と自由記述の具体性を併記する |

## 13. リリース判定基準

イベントで使用する初版は、次の条件をすべて満たしたときに準備完了とする。

- S0 が事故報告と既存コードの観察から始まり、S1〜S4 が業務上の要求または事故から始まる
- S1〜S4 で守るべき不変条件、技法の適用理由、適用限界が明示されている
- S1〜S4 で、参加者が編集する範囲が1モジュール（最大5ファイル・実効80行）、最大4ステップ、最大3件の設計判断に収まっている
- S1〜S4 で、不変条件の1文、依頼文、型で守れなかった残りの3つが成果物として残る
- S1〜S4 で、個人検証後に、S1・S2 は7分、S3・S4 は8分の班内相互レビューを実施できる。TA は原則として2名の差分を比較し、時間超過または2名を選べない場合のみ1名を選び、同じ画面で不変条件を判定する
- 予約の状態が `Scheduled | CheckedIn | InExamination | Paid | Canceled` の5状態として S1 に明示されている
- S0=15分、S1=30分、S2=30分、S3=35分、S4=35分、Final=5分のセッション内容150分と、30分の固定枠を合わせた180分の時間配分が、ページとファシリテーター資料に反映されている
- 通常テストが成功し、`pnpm exercise:01` から `pnpm exercise:04` で各演習の業務名を持つ失敗を確認できる
- `examples/session-05` が S1〜S4 の全回帰テストを成功させる到達点として用意され、Final で `examples/final` の参照実装を講師が5分で案内できる。参加者は `examples/final` の環境構築を求められない
- 終了時の行動計画を収集する設問が用意されている
- 30日後のフォローアップ設問と送付方法が用意されている
- 実装を完了できない参加者向けの代替進行がファシリテーターガイドに記載されている

## 14. プロダクト原則

教材、演習、進行方法に迷った場合は、次の順序で判断する。

1. 技法より、減らしたい業務上の問題を先に示す
2. 完成形より、既存実装からの小さな一歩を優先する
3. 実装量より、判断理由を説明できることを優先する
4. 型の巧妙さより、改善効果を確認できることを優先する
5. 一度の完成より、次の改善へ進めることを優先する
