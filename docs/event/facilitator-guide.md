# ファシリテーター向けガイド

2026年8月30日の第1回と2026年11月7日の第2回は、開催済みです。このガイドは、第2回のハンズオンに合わせた進行例です。別のハンズオンや社内勉強会でも使えます。以下の時間、班の人数、TAの配置は第2回の想定です。再利用する場合は、参加人数と開催時間に合わせて調整します。

## 別のハンズオンで使うとき

1. 参加者へサイトの [事前準備のページ](https://fp-with-ts-hands-on.kosui.workers.dev/setup/) を共有します。[事前準備](./participant-setup.md) は、同じ内容の資料です。演習はブラウザ内で実行されるため、デスクトップ版の Chrome または Edge が必要であることを案内します。連絡先や質問先は開催ごとに決めて案内します。
2. 扱うセッションと休憩を決めます。全編は学習180分と休憩30分が目安です。短い勉強会では、S0 で事故の題材を共有してから、選んだセッションの exercise ページを開きます。
3. S5の演習には相互レビューがありません。参加者は各自で仕組みを追加し、takeaways のページで担当業務に適用する内容を確認します。
4. S1〜S4とS6の相互レビューでは、参加者がそれぞれ作った仕組みを比較できる時間を確保します。TAがいない場合は進行役を決め、全員が順番に自分の仕組みを見せます。
5. Finalは、講師が参照実装を案内し、参加者が all-rules、own-rule-review、next-mechanism のページで判断します。複数回に分ける場合は、次に開くセッションの exercise ページを最後に共有します。

個人学習の演習・振り返りの手順は、各セッション内で案内しています。

## 開催時の進行例

- 開催時間: 全体210分（学習180分と休憩30分）を仮定します。時刻は開始からの経過時刻で記載します。
- 体制: 5人1班、各班にTA 1名
- 対象: TypeScript の基本文法を読み書きできる初級から中級の参加者
- 題材: 動物病院の予約・カルテ管理システム
- 主線: 各セッションの exercise ページのブラウザ内の演習。参加者はデスクトップ版の Chrome または Edge で開きます。
- 退避先: exercise ページの「解答の例を見る」

参加者が担当するのは、誤った変更の一覧を確認し、Linter のルール、型のテスト、テストのどれかで検出する仕組みを追加することです。追加した後に「検出を検証する」を押し、隣の人の仕組みで検出されない変更を作り、担当業務での防止策を議論します。

## 演習の合格条件

S1〜S6の演習は、各セッションの exercise ページのブラウザ内で行います。作業場所はブラウザ内の隔離環境で、ローカルPCのファイルにはアクセスしません。

必須の誤った変更がすべて「検出」で、正しいコードがすべて「誤検知なし」で、表の下に「問題」が表示されていない場合に合格です。S4 は、型検査にも成功しないと合格しません。

画面の表には、次の言葉が表示されます。

- 検出: その誤った変更で「対象外」と表示されていない列の仕組みが、誤った変更を検出した。
- すり抜け: 誤った変更を検出できなかった。「対象外」の列の仕組みだけが検出した場合も、行は「すり抜け」のままです。
- 誤検知あり: 正しいコードを誤った変更として検出した。
- 誤検知なし: 正しいコードを検出しなかった。
- 未変更: 相互レビューで作る誤った変更を、まだ書き換えていない。
- 未確認: 行の判定がまだ表示されていない。
- 未検出: 誤った変更の行で、その列の仕組みがまだ検出していない。
- 対象外: その誤った変更では数えない仕組み。
- エラー: その列の検証でエラーが発生した。

S3、S4、S5、S6 の演習ページは、合格後に「この仕組みで検出できないこと」の記入を求めます。この欄はプログラムでは判定しません。S3 で UUID を通す変更は、テストでだけ検出できます。

検査中に参加者が別のタブへ切り替え、タブが隠れている間に時間切れが発生した場合、画面に「このタブに戻ると、検出を再検証します。」と表示されます。タブに戻ると、画面は「タブが隠れていた間に時間切れになったため、再検証しています。」と表示します。この表示は演習の失敗ではありません。

デスクトップ版の Chrome または Edge 以外で開くと、作業場所が起動しないことがあります。その場合、画面に「ChromeまたはEdgeで開き、サイトの分離ヘッダーを確認してください。」と表示されます。

## 講師の共通台本

S1〜S4 と S6 は、次の順序を崩しません。S2 の相互レビューは問いが1つです。ほかの回は問いが3つです。

1. 事故と要求を読み、「何が壊れたか」を業務の言葉で確認する。
2. 事前知識のページで、技法を説明する。
3. 演習のページで、参加者が誤った変更の一覧を確認し、1件選んでコードを読む。
4. 参加者が、Linter のルール、型のテスト、テストのどれで検出するかを選んで追加する。
5. 参加者が「検出を検証する」を押し、表の「検出」「すり抜け」「誤検知あり」を確認する。「対象外」の列の仕組みだけが検出した誤った変更は、「検出」にならず「すり抜け」のままになる。必須の誤った変更が「検出」、正しいコードが「誤検知なし」になれば合格する。
6. 「相互レビューで作る誤った変更」の行は、演習の必須を満たした後にだけ、表に表示される。表示されていない場合は、先に必須の検出を終える。相互レビューのページで、参加者が隣の人のブラウザのその行を書き換え、相手の仕組みに検出されないかを確認する。その行が「すり抜け」なら成功する。TA が選んだ1名の仕組みを班で確認し、ページの問いを議論し、全員がシートへ1行記載する。S1 と S2 では、peer-review ページの2分で誤った変更を作って検証し、シートへの記入は guard ページへ進んでから行う。
7. guard のページで、演習で追加した仕組みが検出するものと、人が確認するものを区別する。参加者が、担当業務での防止策を議論する。S1 と S2 では、議論するのはカードの「セッション別の問い」から1つ（S2 は default の問い）で、guard ページの問いは進行役が読み上げ、参加者が担当業務で検討する。
8. S3、S4、S6 は review のページで、担当業務に適用する問いに自分の言葉でメモする。

S6 の guard のページでは、「1回の保存」と「原子性」を、それぞれどの仕組みで守るかを議論します。演習で追加した仕組みは、本番の原子性を保証できません。

S0 では、講師が incidents のページで2件の事故を読みます。why-not-stopped のページでは、操作1回を画面、コード、DB の7コマで追跡します。参加者がモックの「診察を開始する」を押せるのは、最初のコマだけです。押すと、2コマ目へ進みます。以降は、「次のコマ →」で進みます。common-cause で2件に共通する原因を確認し、code-layout で事故の操作を5つのステップと担当ディレクトリに対応付けて、業務ロジックの配置先を示します。hexagonal で教材のコードの構成の理由を示し、when-noticed で誤りを検出できる4つの時点を確認します。goal、roadmap、your-rule で、担当システムの暗黙の業務ルールを1つ選びます。S0 の参加者は、演習を行いません。S0 に合否の判定はありません。

S5 では、講師が予約キャンセルを工程に分けて読みます。ROP基本図で3か所の失敗への切替を示し、別のユースケース図では、User ResolverとAppointment Resolverを入力側、Event Storeを出力側へ配置した成功経路を確認します。この説明では業務のコードを修正しません。S5 の演習は、参加者が業務のコードを編集せず、誤った変更を検出する仕組みを追加する6分です。

Final は、講師が参照実装 `examples/final` を、`examples/final/src/useCase/startExaminationUseCase.ts` を入口にして6分で案内します。参加者へ `examples/final` のセットアップと編集を求めません。残りの4分は、参加者が判断します。all-rules では、ルールの適用範囲を広げたときの3件の指摘を判断します。カードごとに選ぶと、教材の判断が表示されます。all-rules に合否はありません。own-rule-review では、S0 で記入した業務ルールを見直します。next-mechanism では、「依頼文に記載したくなる内容」と「実行する場所」を1つずつ選びます。「依頼文」は、Agent に渡す指示のことです。Agent を使わない参加者は、「チームで合意した規約」に読み替えます。シートの末尾にある「業務への振り返り」と「業務へ戻って最初に見る箇所」は、参加者が持ち帰って記入します。Final に演習と相互レビューはありません。self-study、persistence-notes、software-factory、agent-skill は「あとで読む」のページで、時間内に扱いません。

## S5 の進行

S5はページ上で進めます。TAが事前に用意するボードやテンプレートはありません。

講師と参加者の作業は次のとおりです。

1. 0:00〜1:00: index のページ「キャンセルで変わる予約データ」で、講師が事例を示し、予約のキャンセル前とキャンセル後のデータを見せます。
2. 1:00〜2:00: tangled のページ「1つの関数に実装したキャンセル処理」で、講師が1つの関数に実装した仮の例を見せます。
3. 2:00〜10:00: 講師がユースケースの4工程、ROP基本図の2本のレールと失敗へ切り替わる3か所、S04のandThenとの対応、ResolverとEvent Storeを両端へ配置する理由を説明します。
4. 10:00〜16:00: 参加者が、業務のコードを編集せず、誤った変更を検出する仕組みを追加します。
5. 16:00〜18:00: 答えと担当業務に適用する内容を確認します。

## Session の移動と作業内容の保存

参加者は、次の Session の exercise ページを開くだけで移動できます。ローカルのファイルを確認する必要はありません。

作業内容は、そのブラウザの IndexedDB に Session ごとに保存されます。保存されるのは、編集したファイル、作業場所の出力、選んだファイル、「検出を検証する」の結果、「この仕組みで検出できないこと」に記載した文です。別のタブが IndexedDB の接続をふさぐと、画面に「IndexedDB の接続がほかのタブにふさがれています。」と表示されます。

## Checkpoint

### 0:10 — S0 を終えて S1 へ進む

- 2件の事故（二重請求、監査記録に残った個人情報）の経緯と、2件に共通する原因を説明できるか確認する。
- S1 では、予約の状態と遷移に関する誤った変更を、仕組みで検出することを共有する。
- S1 の peer-review ページの3つの進め方を読み上げる。5回で全員を最低1回選ぶ計画をTAが記録欄へ立てる。

### 0:30 — S1 を終えて S2 へ進む

- 必須の誤った変更3件が「検出」、正しいコード3件が「誤検知なし」になっているか確認する。
- 合格できなかった参加者は、S1 の exercise ページの「解答の例を見る」を開く。S2 は、S2 の exercise ページを開けば始められる。
- 相互レビュー3分は落とさない。S1 と S2 は短い版がなく、3分のまま行う。

### 0:50 — S2 を終えて S3 へ進む

- 必須の誤った変更4件が「検出」、正しいコード3件が「誤検知なし」になっているか確認する。
- 相互レビューの問いは1つである。default を残したいのはどんなときか、残すなら何で漏れを検出するかを議論する。
- 相互レビュー3分は落とさない。

### 1:25 — S3 を終えて休憩へ入る

- HTTPから受け取った予約IDと担当獣医師IDが、両方とも検証に成功した場合だけ `StartExaminationInput` になることを確認する。
- 必須の誤った変更4件が「検出」、正しいコード4件が「誤検知なし」になっているか確認する。UUID を通す変更は、テストでだけ検出できる。
- 値を伏せる方法は時間外の補足で、「あとで読む」のページ「Sensitive による値のマスク」にある。時間内の演習では、必須の誤った変更「監査記録に飼い主の連絡先が入る」（B4）を、型のテスト、Linter のルール、テストのどれかで検出する。
- 相互レビューは5分で行い、足りないときは3分版にする。休憩30分を削らない。

### 1:55 — 休憩から S4 へ戻る

- 全員が S4 の exercise ページを開いていることを確認する。

### 2:26 — S4 を終えて S5 へ進む

- `AppointmentNotFound` と `InvalidAppointmentState` が例外文言ではなく同期 `Result` の値として返ることを確認する。
- 必須の誤った変更3件が「検出」、正しいコード2件が「誤検知なし」になっているか確認する。
- 合格できなかった参加者は、「解答の例を見る」を開き、写した後に「検出を検証する」で判定する。失敗後に遷移しない理由を読ませる。
- 後半の残り時間を確認する。S6 の演習と peer-review ページの3分は削らない。遅れている分は Final の説明量で調整する。

### 2:44 — S5 を終えて S6 へ進む

- 必須の誤った変更3件が「検出」、正しいコード4件が「誤検知なし」になっているか確認する。S5 は業務のコードを編集しない。
- キャンセル前とキャンセル後の予約のデータの違いと、キャンセルを許す条件の1文を説明できるか確認する。
- ResolverとStoreをドメインロジックの外へ配置する理由を説明できるか確認する。
- S6 は診察開始の演習題材へ戻ることを共有する。

### 3:20 — S6 を終えて Final へ進む

- 必須の誤った変更4件が「検出」、正しいコード2件が「誤検知なし」になっているか確認する。型の列は「対象外」で、2回の保存はテストで検出する。
- Final は、講師の説明6分の後に、参加者が all-rules、own-rule-review、next-mechanism で判断することを共有する。

## 時間が押したときの進行

S6 の演習と peer-review ページの3分、休憩30分は削りません。全体が押したときは、Final の説明量を調整します。

- S1 の brief 2分: 講師が、double-billing のページの事故と、current-code のページの「開始コードの引数が Appointment で、どの状態の予約も受け取る」点だけを説明します。参加者がコードを読み通す時間には使いません。
- S3 の事前知識13分: 読み切れない分は、講師が要点だけを説明します。読み切れなければ、演習の後に読むよう案内します。
- S4 の事前知識12分: S3 と同じく、講師が要点だけを説明し、読み切れなければ演習の後に読むよう案内します。
- 相互レビュー: 短い版にします。詳細は [相互レビュー進行カード](./peer-review-card.md) の例外2に従います。S3 と S6 は3分版、S4 は4分版にします。S1 と S2 は、もともと3分なので変えません。S6 を3分版にするときは、講師が guard ページの「演習で追加した仕組みは、本番の原子性を保証できません」を読み上げます。
- 「あとで読む」のページ: 時間内に扱いません。

## 班とTAの運用

演習の時間中に、TA は各自のブラウザの画面を見て回ります。巡回には2つの目的があります。

1. 表に「すり抜け」「誤検知あり」「エラー」が残る参加者を見つけ、先に支援する。
2. [相互レビュー進行カード](./peer-review-card.md)の選定基準に沿って、1名の仕組みを選ぶ。

相互レビューの末尾1分では、仕組みが選ばれなかった参加者も、議論した内容を [シート](./review-sheet.md) へ1行記載します。シートには、自分の仕組みで検出できないことが分かる場合は、それも記載します。S1〜S4 と S6 の各回で1名を選び、5回を通して班の全員が最低1回は選ばれるよう、カード裏面の記録欄で調整します。

## 詰まった参加者の退避

- 時間内に進められなくなった参加者だけが、演習のページの「解答の例を見る」を開きます。
- 参加者は、解答の例を写した後に「検出を検証する」で判定します。
- 実行環境が起動しないときは、解答の例を読んで次へ進み、相互レビューは隣の人の画面で行います。
