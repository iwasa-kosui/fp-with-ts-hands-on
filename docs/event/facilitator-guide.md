# ファシリテーター向けガイド

このガイドは、2026年8月30日のイベントで用意した進行例です。イベントは終了していますが、別のハンズオンや社内勉強会でも使えます。以下の時刻、班の人数、TAの配置は開催時の想定です。再利用するときは、参加人数と開催時間に合わせて調整してください。

## 別のハンズオンで使うとき

1. 参加者へ [事前準備](https://fp-with-ts-hands-on.kosui.workers.dev/setup/) を共有し、ローカルで通常テストと教材サイトが動くことを確認します。連絡先や質問先は開催ごとに決めて案内します。
2. 扱うセッションと休憩を決めます。全編は学習180分と休憩30分が目安です。短い勉強会ではS0・S1で題材を共有し、選んだコード演習の前提を説明してから、その回の開始スナップショットを使います。
3. S1のボードを用意し、複数人で取り組む場合は共同編集リンクを共有します。紙と付箋でも進められます。
4. レビューは、参加者がそれぞれ考えた理由を比較できる時間を確保します。TAがいない場合は進行役を決め、全員が順番に差分を見せます。
5. Finalはページの5項目に沿って参照実装を案内します。複数回に分ける場合は、次に開くセッションと作業ディレクトリを最後に共有します。

個人学習では、班での共有をメモに、相互レビューを自分の差分の振り返りに置き換えます。[ひとりで学ぶ手順](https://fp-with-ts-hands-on.kosui.workers.dev/setup/#self-study) を参照してください。

## 開催時の進行例

- 開催日時: 2026年8月30日 15:00-18:30（210分）
- 体制: 5人1班、各班にTA 1名
- 対象: TypeScript の基本文法を読み書きできる初級から中級の参加者
- 題材: 動物病院の予約・カルテ管理システム
- 主線: 事前にセットアップしたローカル clone
- 退避先: S2〜S6はページの「ステップごとの解答」の `details`、S6は後続stepを含む全targetの完成ファイル、共通で WebContainer Playground

コーディングエージェントは推奨ですが必須ではありません。参加者が担うのは、事故から各セッションの問いを言語化し、Agentへの依頼文または実装メモへ変換し、型とテストで個人検証したうえで班内相互レビューを行うことです。

## テストと演習コマンドの契約

- `pnpm test`、`pnpm typecheck`、`pnpm build` は通常の健全性確認で、成功を期待します。
- S2〜S6 の開始スナップショットでは、`pnpm exercise:02`〜`pnpm exercise:06` が業務語彙を持つ `AssertionError` で意図的に失敗します。module-not-found、import error、設定エラーは意図した RED ではありません。
- 参加者が対象モジュールを直した後は、同じ exercise コマンドの成功を期待します。
- S0 は現状理解、S1 は Excalidraw 上で予約キャンセルの依頼と業務条件を逆算する班ワークです。どちらにも exercise コマンドはありません。
- S5 は同期 `Result` と `andThen`、S6 は副作用・イベント、`ResultAsync`、`andThrough`、1回の `store(event)` を扱います。

参加者ステップは S2=4件、S3=3件、S4=2件、S5=3件、S6=4件です。開始時の RED 数と同じではない出力や予期しない例外を見たら、先に環境または差分範囲を切り分けます。

## 講師の共通台本

S2〜S6 は次の順序を崩しません。

1. 要求と事故を読み、「何が壊れたか」を業務の言葉で確認する。
2. exercise コマンドを実行し、意図した assertion RED を見る。
3. 参加者が、そのセッションの具体的な問いへの回答を1文にする。
4. その1文をAgentへの依頼文へ入れる。エージェントを使わない参加者は実装メモとして使う。
5. 対象モジュールだけを変更し、同じコマンド、型、現在snapshot限定の差分、リポジトリ全体の状態で個人検証する。
6. TA が選んだ1〜2名の差分を班で相互レビューし、全員がレビュー観点シートへ1行書く。

S0では現状を読み、S1では「予約がキャンセルされた」からアクター、コマンド、確認する条件を逆算します。講師はROP基本図で3か所の失敗への切替を示します。別のユースケース図では`Appointment`集約を`Appointment.cancel`へ対応させ、User ResolverとAppointment Resolverを入力側、Event Storeを出力側へ置いた成功経路だけを確認します。どちらも修正とexercise実行を行いません。Finalは講師が `examples/final/src/useCase/startExaminationUseCase.ts` を入口に5分で案内するだけです。参加者へ `examples/final` のセットアップ、編集、Playground操作を求めません。

## S1 の Excalidraw 運用

S1の班ワークはページ上ではなくExcalidrawで行います。TAはS1が始まる前に次を終えます。

1. excalidraw.com でテンプレート `docs/event/session-01-event-storming.excalidraw` を開く。
2. 画面右上から Live collaboration を開始する。
3. 発行されたリンクを班へ共有する。

テンプレートには1件のドメインイベント、時系列の軸、ドメインイベント、コマンド、アクター、Hotspotの記入例を含みます。共同編集が30秒で復旧しない場合は、印刷したイベントと空の付箋へ切り替えます。リンク作成や復旧のために15分の進行を短縮しません。

講師と参加者の作業は次のとおりです。

1. 0:00〜2:00: 講師が「予約がキャンセルされた」を置きます。
2. 2:00〜6:00: 参加者がアクター、コマンド、権限・存在・状態・理由について確認する条件を逆算します。答えの違いはHotspotへ残します。
3. 6:00〜8:00: 講師が`Appointment`集約を加え、ビジネスユースケース、ドメインモデル、ユースケースを区別します。
4. 8:00〜10:00: ROP基本図で、成功から失敗へ切り替わる3か所を確認します。
5. 10:00〜14:00: 比較図の成功経路で、コマンド、内部のドメイン判断、一つの成功イベントを対応させます。
6. 14:00〜15:00: Resolverを入力側、Event Storeを出力側へ置くことで、解決済みの値だけを純粋なドメインロジックへ渡し、戻り値を値だけでテストできることを確認します。

## セッション間の差分基準と引き継ぎ

相互レビューで表示するのは、現在の開始snapshotディレクトリだけです。前のセッションの未commit差分が残っていても現在のレビューへ混ざらないよう、次を使います。

| セッション | 開始snapshot | 差分確認 |
| --- | --- | --- |
| S2 | `examples/session-02` | `git diff --stat -- examples/session-02` |
| S3 | `examples/session-03` | `git diff --stat -- examples/session-03` |
| S4 | `examples/session-04` | `git diff --stat -- examples/session-04` |
| S5 | `examples/session-05` | `git diff --stat -- examples/session-05` |
| S6 | `examples/session-06` | `git diff --stat -- examples/session-06` |

各回で `git status --short` も実行し、現在snapshot以外に想定外pathが増えていないかをTAが確認します。これはリポジトリ全体の異常検知であり、レビュー対象の差分量を判定するコマンドではありません。

レビュー終了後はシートへの記録を確認し、次のセッションページとexerciseコマンドへ進み、差分確認のpathだけを次のsnapshotへ切り替えます。前のセッションの未commit差分を消すための reset、stash、commit は要求しません。想定外pathがあっても自動で消さず、参加者が残したい作業を確認してから [トラブルシューティング](./troubleshooting.md) の限定手順を使います。

## Checkpoint

### 0:10 — S0 を終えて S1 へ進む

- 2件の事故（二重請求、PII流出）と legacy の該当行を対応づけられるか確認する。
- 実装を先回りして直さず、S1で予約キャンセルの業務条件を決めることを共有する。
- TAがExcalidrawのテンプレートを開き、Live collaborationのリンクを共有済みか確認する。

### 0:25 — S1 を終えて S2 へ進む

- 「受付担当者 → 予約をキャンセルする → Appointment集約 → AppointmentCanceled」の並びと、確認する条件の1文が残っているか確認する。
- ResolverとStoreをドメインロジックの外へ置いた構成図が残っているか確認する。
- S2以降は診察開始を別の演習題材として扱うことを共有する。
- [相互レビュー進行カード](./peer-review-card.md)の約束事5点を読み上げる。5回で全員を最低1回選ぶ計画をTAが記録欄へ立てる。

### 0:55 — S2 を終えて S3 へ進む

- 6状態と許可された遷移、診察結果記録前の会計禁止、キャンセル理由、`assertNever` の役割を確認する。
- 4ステップを完走できない参加者は、ページの「ステップごとの解答」の `details` を開いて同じ型を読める状態にする。
- 相互レビュー7分は落とさない。時間超過時は2人目の比較枠2分を落とし、1名の5分版へ切り替える。

### 1:25 — S3 を終えて休憩へ入る

- `AppointmentId` と `VeterinarianId` が互いに代入できず、予約の6状態と `startExamination` の引数まで同じ型が通っていることを確認する。
- 参加者ステップは catalog の3件である。時間が足りなければ、末尾の型テストを講師デモへ切り替える。
- 相互レビュー7分は残し、必要な場合だけ2人目の比較枠を落とす。休憩30分を削らない。

### 1:55 — 休憩から S4 へ戻る

- HTTPから受け取った予約IDと担当獣医師IDが、両方とも検証に成功した場合だけ `StartExaminationInput` になることを確認する。
- 参加者ステップは catalog の2件である。固定の「Step 3/4」が存在する前提で進行しない。
- 検査結果のschemaとPIIのマスキングは時間外の補足であり、時間内の変更対象へ含めない。

### 2:55 — S5 を終えて S6 へ進む

- `AppointmentNotFound` と `InvalidAppointmentState` が例外文言ではなく同期 `Result` の値として返ることを確認する。
- S5の3ステップが終わらない場合は `ensure*` の解答と `andThen` pipeline を順に開き、失敗後に遷移しない理由を読ませる。
- 後半の残り時間を確認し、S6が押す見込みなら S6のステップ3（`ResultAsync` と `andThrough`）を講師デモにする。S6の相互レビューは残し、次に2人目枠、最後にFinalの説明量を調整する。

## 班とTAの運用

オープニングでエージェント有無を申告してもらい、可能な範囲で保持者と非保持者を同じ班にします。TA は保持者0名の班を把握します。

委譲時間の巡回には2つの目的があります。

1. 赤の数、型エラー、モジュール外差分から詰まりを発見し、エージェントを使わない参加者を優先して支援する。
2. [相互レビュー進行カード](./peer-review-card.md)の選定基準に沿って、学びの出る1〜2名の差分を選ぶ。

相互レビューの末尾1分では、自分の差分が選ばれなかった参加者も [レビュー観点シート](./review-sheet.md) の「型検査では確認できず、テストまたは実行時に確認すること」を書きます。2名を選ぶ回を4回以上確保し、5回を通して班の全員が最低1回は選ばれるよう、カード裏面の記録欄で調整します。

## エージェントを使わない参加者の退避

- S2〜S5はページの「ステップごとの解答」の `details` を1件ずつ開き、次スナップショットの抜粋を写して理由を読む。
- S5は「完成ファイルの解答例」の `details` を開く。各解答は後続stepを含む完成ファイルなので、表示された全target fileを反映してから同じexerciseを実行する。1stepずつの個別GREENは約束しない。
- `配布コードを読む` の Code Explorer は、実ファイルの注目行を読むためのガイドとして使う。
- `型で閉じる` の Playground は WebContainer 上で編集とコマンド実行ができる説明用・退避用環境として使う。主線にはせず、会場ネットワークに依存させない。
- Playground が起動しない場合はローカル clone へ戻る。新しいAPIキーや特定のエージェント製品は必要ない。
- 相互レビューではモジュール全体ではなく、全員が到達している1ステップ・1宣言を対象にする。解答を写した差分なら「なぜ解答はこの形か」「別の形だと何が壊れるか」と問う。

Code Explorer の専用URLはありません。各セッションの `配布コードを読む` と `型で閉じる` に埋め込まれた実体を使います。

## 事前リハーサル手順

自動検証の実測結果はP4のリハーサル記録へ残します。このガイドでは実行順と期待だけを定めます。

1. 依存関係を事前に取得し、`pnpm typecheck`、`pnpm test`、`pnpm build` が成功することを確認する。これらはS0〜S7のWebアプリも検査する。
2. `pnpm exercise:02`〜`pnpm exercise:06` を個別に実行し、開始スナップショットとして non-zero の assertion RED になり、参加者ステップが S2=4、S3=3、S4=2、S5=3、S6=4 に対応することを確認する。
3. `pnpm --filter @fp-with-ts/clinic-session-07 test` が S2〜S6 の全回帰を含めて成功することを確認する。
4. `pnpm demo:00` から `pnpm demo:07` を一つずつ起動し、`http://localhost:3000` の初期表示、通常操作、reset、未実装ダイアログを確認する。切り替える前に現在のサーバーを `Ctrl+C` で終了する。
5. 5人相当の差分で7分版を通し、問い1で沈黙しないか、2人目の比較まで収まるかを計測する。成功済みとは記録せず、実測結果をP4へ残す。
6. エージェントを使わない条件で、S2〜S5の解答 `details` またはS6の全target完成ファイルを開き、委譲時間内に進めるかを1本計測する。

スマホ表示を確認するときは開発サーバーを `0.0.0.0` で待ち受けます。現行の `pnpm dev` はこの設定を持ちます。表示された実ポートに対して `mobile-preview-url <port>` を実行し、返されたURLを使います。明示的な依頼がない限り公開トンネルは使いません。
