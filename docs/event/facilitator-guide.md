## Checkpoint

### 0:30 状態モデリングへ進む

次の点を確認してから `01-state-modeling` に進みます。

- `status: string` と optional field の組み合わせが不正な状態を許している
- `paid` から診察中へ戻る事故を赤いテストで確認できている
- キャンセル理由と再診希望を追加する要求を参加者が把握している

### 1:10 休憩へ入る

参加者が `Paid` や `Canceled` から戻れない状態表現を確認できたら休憩に入ります。休憩中に、次のセッションで使う外部検査 payload の題材を表示しておきます。

### 1:55 Result へ進む

次の点を確認してから `03-result-errors` に進みます。

- 外部入力をスキーマで検証し、ID の取り違えを型で防げている
- 飼い主の連絡先がログに出る事故と、`Sensitive` に包む目的を説明できている
- この時点では Result の設計に踏み込まず、境界の責務に集中できている

### 2:30 総合レビューへ進む

次の点を確認してから `04-agent-review` に進みます。

- 失敗理由を `throw` ではなく呼び出し元が読める値として扱えている
- 成功時だけ `ExaminationStarted` を記録し、失敗時に不要な event が残らない
- 参加者が「ここまでできたらOK」の条件を説明できている
- `pnpm exercise:04` を実行し、次の追加要求を依頼する前に checklist と prompt を全員で確認する

## 進行上の注意

- 参加者の環境トラブルは、まず [トラブルシューティング](./troubleshooting.md) の該当項目で切り分けます。
- 赤いテストを先に直してしまわず、どの不変条件が破られたかを全員で確認します。
- `04-agent-review` では、AI に任せる作業と人が確認する不変条件を分けて話します。
- `05-mini-integration` は `collectFollowUpTargets` の1関数に集中し、petId mismatch、PII、Result、domain event の観点をまとめて確認します。
- 時間が押した場合は、`05-mini-integration` の実装を講師の worked example に切り替え、設計判断の確認を優先します。
