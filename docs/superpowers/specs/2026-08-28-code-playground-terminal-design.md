# コードプレイグラウンドのターミナル化 設計

- 日付: 2026-08-28
- 状態: 設計承認済み・実装計画待ち

## 背景

現在のコードプレイグラウンドは、選択中のファイルに対応する固定コマンドを「実行」ボタンから起動し、標準出力を専用パネルへ表示している。この方式では、参加者が任意のテストや補助コマンドを試せず、コマンド履歴、補完、`Ctrl+C` などのターミナル操作も使えない。また、コマンドから作成・変更・削除したファイルがエディタとファイルツリーへ反映されないため、編集環境と実行環境が分離して見える。

固定の実行UIを、WebContainer 内で動く永続的な対話シェルとターミナルエミュレータへ置き換える。エディタとターミナルは同じ `/workspace` を共有し、参加者がコードの変更と検証を一つのプレイグラウンド内で往復できるようにする。

## 目標

- 「実行」「停止」と固定出力パネルを廃止し、任意のコマンドを入力できる対話ターミナルを提供する。
- シェルの履歴、ANSI表示、対話入力、`Ctrl+C`、画面サイズ変更を通常のターミナルとして扱えるようにする。
- エディタとターミナルが同じ WebContainer ファイルシステムを共有する。
- ターミナルから作成・変更・削除した対象テキストファイルを、ファイルツリーとエディタへ反映する。
- 初期表示を軽く保つため、WebContainer の起動は利用者の明示操作まで遅延する。
- デスクトップとモバイルの双方で、ファイルツリー、エディタ、ターミナルを無理なく利用できる配置にする。

## 対象外

- ブラウザを再読み込みした後も変更やシェル状態を永続化すること。
- ローカルPCのファイルシステム、環境変数、認証情報へアクセスすること。
- バイナリファイルや依存パッケージ、ビルド成果物をエディタで編集すること。
- ガイド表示専用の読み取り専用 Code Explorer にターミナルを追加すること。
- 複数ターミナル、タブ、分割ペイン、シェル種別の選択機能を提供すること。

## 利用者体験

### 配置

編集可能なプレイグラウンドでは、上段にファイルツリーとエディタを置き、その下に両カラムをまたぐ全幅のターミナル領域を置く。既存の「実行」「停止」ボタンと出力パネルは表示しない。

読み取り専用のガイド表示では、従来どおりファイルツリーとエディタだけを表示する。

### 起動前

初期状態ではターミナルの代わりに、ブラウザ内の隔離環境でコマンドを実行する旨と「ターミナルを起動」ボタンを表示する。ページ表示だけでは WebContainer を起動しない。

ボタンを押すと準備状態へ移り、環境起動、ファイル配置、依存関係準備など現在の段階を短いテキストで示す。準備が完了した時点で xterm.js の画面へ切り替え、`/workspace` をカレントディレクトリとする `jsh` のプロンプトを表示する。

### 起動後

ターミナルはプレイグラウンドを閉じるまで同じシェルプロセスを維持する。利用者は `pnpm exercise:02` などの既存コマンドに限らず、WebContainer 内で利用可能な任意のコマンドを実行できる。ANSIカラー、履歴、対話入力、`Ctrl+C` は端末入出力としてそのまま扱う。

シェル自体が終了した場合は終了状態と「ターミナルを再起動」操作を表示する。再起動では同じ WebContainer とファイル内容を維持し、新しい `jsh` を起動する。

## コンポーネント境界

### `CodeExplorer`

- 初期ファイル、現在のファイル一覧、選択中のパス、編集内容を管理する。
- 編集可能なプレイグラウンドだけに `TerminalPanel` を配置する。
- エディタの変更をターミナルセッションへ書き込み、ファイルシステム側の変更通知を React の状態へ投影する。
- 選択ファイルの削除や新規ファイルのリセット可否を解決する。

### `TerminalPanel`

- 未起動、準備中、利用可能、終了、失敗の表示を担当する。
- xterm.js の生成、破棄、キー入力転送、出力描画を担当する。
- `@xterm/addon-fit` と `ResizeObserver` を使い、表示領域の変更を端末の列数・行数と PTY へ伝える。
- WebContainer 固有の処理やファイル同期規則は持たない。

### ターミナルランナー

- WebContainer の起動、初期ファイルのマウント、依存関係の準備、型定義ファイルの配置を行う。
- `/workspace` の再帰監視を開始し、ファイル変更イベントを上位へ通知する。
- `/workspace` を作業ディレクトリとして、端末サイズ付きで `jsh` を PTY 起動する。
- シェルへの入力、サイズ変更、再起動、終了、リソース解放を一つのセッション境界として提供する。
- UIが WebContainer API を直接操作しなくてよいように、既存の `CodeRunner` を対話セッション向けの境界へ置き換える。

### ワークスペース投影

- WebContainer のファイル変更イベントを直列化し、対象パスの存在と内容をファイルシステムから読み直す。
- 表示対象の UTF-8 テキストだけを Code Explorer のファイル一覧へ投影する。
- エディタ由来の書き込みが監視イベントとして戻った場合も、現在値との比較で不要な状態更新を避ける。

## 起動とデータフロー

1. 利用者が「ターミナルを起動」を押す。
2. その時点のエディタ内容を含む現在のワークスペースを、WebContainer の `/workspace` へマウントする。
3. `/workspace` で依存関係を準備し、Monaco が参照する型定義を既存の方法で配置する。準備中の進捗は状態テキストとして表示し、シェル出力とは混在させない。
4. 依存関係の生成物を初期ファイルと誤認しないよう、準備完了後に `/workspace` の再帰監視を開始する。
5. xterm.js の初期サイズを取得し、`/workspace` をカレントディレクトリとして `jsh` を起動する。
6. PTY の出力を加工せず xterm.js へ書き込み、xterm.js の入力を PTY の入力ストリームへ転送する。
7. エディタ編集時は同じ WebContainer パスへ書き込む。ターミナルからのファイル操作時は監視イベントを通じて一覧と選択中のエディタ内容を更新する。
8. コンポーネントのアンマウント時は、監視、入出力ストリーム、シェル、xterm.js、WebContainer を解放する。

WebContainer 内で最後に完了したファイル書き込みを正とする。エディタとターミナルが同じファイルをほぼ同時に更新した場合に独自のマージは行わず、監視後に読み直した最新内容を画面へ反映する。

## ファイルツリー同期規則

### 表示するファイル

- 起動前から `visibleFiles` に含まれていた既存ファイル。
- 起動後に `/workspace` 内へ新規作成された、正しい UTF-8 として読めるテキストファイル。
- 表示対象ファイルから導出されるディレクトリ階層。

### 表示しないファイル

- 初期プロジェクトに存在するが、従来の `visibleFiles` では非表示だった設定・補助ファイル。
- `node_modules` 配下。
- キャッシュ、ビルド成果物、カバレッジ成果物の配下。
- `package-lock.json`。
- UTF-8 として読めないファイル、NUL文字を含むファイルなど、バイナリと判断したファイル。

監視対象とツリー表示対象は分ける。非表示ファイルをコマンドから利用することは妨げないが、監視イベントを画面へ投影しない。

### 変更・削除・リセット

- 表示中のファイルがターミナルから変更された場合、選択中かどうかにかかわらず保持内容を更新する。選択中なら Monaco の表示も更新する。
- 表示中のファイルが削除された場合、ツリーから除外する。選択中だった場合は、安定したツリー順で最初の残存ファイルを選ぶ。残存ファイルがなければ空状態を表示する。
- 初期ファイルは従来どおり初期内容へリセットでき、起動済みならリセット内容を WebContainer にも書き込む。
- ターミナルから作成された新規ファイルには初期内容がないため、リセット操作を無効にする。

## 状態とエラー処理

ターミナル領域は次の状態を明示的に持つ。

- `unstarted`: 説明と起動ボタンを表示する。
- `preparing`: 起動段階を表示し、重複起動を受け付けない。
- `ready`: xterm.js と稼働中のシェルを表示する。
- `exited`: シェル終了を表示し、同じワークスペースで再起動できる。
- `failed`: 利用者向けの原因説明と再試行操作を表示する。

WebContainer に必要なブラウザ機能または分離設定が利用できない場合は、対応ブラウザで開くための案内を表示する。準備処理が失敗した場合は不完全なセッションを解放し、再試行時に WebContainer の起動からやり直す。シェルコマンドの非ゼロ終了はターミナル内の通常結果として扱い、セッション全体の失敗にはしない。

## セキュリティと隔離

任意コマンドはブラウザ内の WebContainer だけで実行する。ホストOSのファイル、環境変数、SSH鍵、認証情報はマウントせず、アプリケーションから秘密情報を注入しない。WebContainer が提供するネットワーク機能は利用可能だが、ブラウザの隔離境界を越える機能は追加しない。

画面上でも「ブラウザ内の隔離環境」であることを起動前に示し、利用者がローカル端末と誤認しないようにする。

## アクセシビリティとレスポンシブ対応

- xterm.js の `screenReaderMode` を有効にし、端末領域と起動・再試行・再起動操作へ明確なラベルを付ける。
- 状態変化と起動失敗は支援技術へ通知できる領域で示す。
- フォーカス表示を維持し、起動後はキーボードだけで端末へ移動・入力できるようにする。
- デスクトップではターミナルを上段の全幅で揃え、コード表示幅を狭めない。
- モバイルではファイルツリー、エディタ、ターミナルを縦に積み、端末に実用的な最小高さを与える。領域変更時は FitAddon で再計算する。

## 依存関係と既存実装の移行

- 端末描画に `@xterm/xterm`、サイズ追従に `@xterm/addon-fit` を追加する。
- 固定コマンドを選ぶ `run-command`、プレーンテキスト出力用の `OutputPanel`、ファイル単位の `run` APIを廃止する。
- ANSIを除去して文字列へ正規化する経路は廃止し、PTY出力を xterm.js に渡す。
- 既存の WebContainer 起動、依存関係準備、型定義配置の責務はターミナルランナーへ移し、同等の初期化結果を維持する。
- 既存のプレイグラウンド密度改善を維持し、ターミナル追加によってエディタ幅を再び狭めない。

## テスト方針

### 単体テスト

- ターミナルランナーの起動順、現在の編集内容のマウント、依存関係準備、PTY入出力、サイズ変更、シェル再起動、解放を WebContainer のテストダブルで検証する。
- ファイル監視について、新規テキストの追加、既存ファイルの変更・削除、非表示既存ファイル、`node_modules`、キャッシュ、`package-lock.json`、バイナリの除外を検証する。
- 監視イベントの直列化と同値内容の再通知抑止を検証する。

### Reactコンポーネントテスト

- 起動前、準備中、利用可能、終了、失敗と再試行の表示遷移を検証する。
- 編集可能なプレイグラウンドだけにターミナルがあり、読み取り専用表示には現れないことを検証する。
- ターミナル由来の追加・変更・削除がツリー、選択ファイル、エディタ、リセット可否へ反映されることを検証する。
- 従来の「実行」「停止」と固定出力パネルが存在しないことを検証する。

### ブラウザテスト

- 実際の WebContainer 対応ブラウザでターミナルを起動し、`pwd` と教材コマンドを入力して出力を確認する。
- ターミナルからテキストファイルを作成し、ツリーから選択して編集できることを確認する。
- エディタで保存された内容をターミナルから読み出せること、ターミナルからの変更・削除がエディタへ戻ることを確認する。
- デスクトップとモバイルで端末が収まり、エディタ幅を損なわず、リサイズ後も列数・行数が追従することを Playwright のビジュアルテストで確認する。
- 手動確認では少なくとも `pnpm exercise:02` を実行し、教材で意図した assertion failure が端末に表示されることを確認する。

## 受け入れ条件

- 編集可能なコードプレイグラウンドに「実行」「停止」ボタンがなく、「ターミナルを起動」操作がある。
- 起動後の端末で、固定リストにない任意の WebContainer コマンドを入力できる。
- 同じシェルで複数コマンドを続けて実行でき、履歴、ANSI表示、対話入力、`Ctrl+C`、リサイズが機能する。
- エディタ変更が WebContainer へ反映され、ターミナルからの対象テキストファイルの追加・変更・削除がツリーとエディタへ反映される。
- 生成物、依存関係、非表示設定、ロックファイル、バイナリによってファイルツリーが汚染されない。
- 新規ファイルではリセットが無効になり、選択ファイル削除時にも操作不能な状態へ残らない。
- 読み取り専用 Code Explorer の表示と教材の通常閲覧には影響しない。
- 起動失敗とシェル終了から利用者が回復でき、画面を離れたときにプロセスと監視が残らない。
- 対象の単体テスト、Reactテスト、ブラウザテスト、ビルドが成功する。

## 検討して採用しなかった方式

### コマンドごとに WebContainer プロセスを起動する

入力欄からコマンド文字列を受け取り、実行ごとに `spawn` する方式は実装量が少ない。しかし、シェル状態、履歴、対話入力、`Ctrl+C`、端末サイズを維持できず、今回求めるターミナル体験にならないため採用しない。

### 入力フォームと `<pre>` で端末風に表示する

既存の出力パネルを拡張する方式では、ANSI制御、カーソル、複数行入力、対話プログラム、支援技術向け端末表現を独自実装する必要がある。端末エミュレーションの複雑さと互換性リスクが高いため、xterm.js を採用する。
