# Issue 123 教材用語と学習導線の設計

## 背景

[Issue 123](https://github.com/iwasa-kosui/fp-with-ts-hands-on/issues/123) では、教材全体で使っている「業務判断」と「守るべき不変条件」が何を指すのか分かりにくいこと、永続化境界の理由、`Discriminated Union` の表記揺れ、TA の選定基準、S4 のコード例とパース対象について指摘されています。

設計の基準は `origin/main` の `e4d776f` です。この時点では、S1 の `Repository` に読み書きと監査記録がまとまり、後続 snapshot で `Resolver`、ドメインロジック、`Store` の責任が段階的に分かれます。S6 の完了後に使う `examples/session-07` では、状態とイベントを transaction 内で記録します。

個別の文言だけを直すと、セッションページ、コード、運営資料の説明が再びずれます。本設計では、ビジネス上の目的からソフトウェアの処理へ抽象度を下げる順序と、各セッションで扱う問題を教材全体で揃えます。

## 目標

- ビジネスユースケース、ユースケース、ドメインロジックの違いを、コード上の責任と対応させます。
- `Resolver` と `Store` をドメインロジックの外に置く理由を、ドメインロジックを pure に保つためと説明します。
- S2 から S6 の演習では、共通の抽象語ではなく、そのセッションで防ぐ問題を具体的に示します。
- `Discriminated Union` の表記を統一します。
- S4 では、小さな schema を組み合わせて入力オブジェクト全体をパースする流れを示します。
- TA が差分を選ぶ目的と基準を、参加者と TA の双方が確認できるようにします。

## 対象外

- `examples/session-*` と `examples/final` の実装動作は変更しません。
- 新しいセッションページや用語集は追加しません。
- EventStorming、ROP、transaction の教材範囲そのものは変更しません。
- S1 の予約キャンセルと、S2 以降の診察開始という既存シナリオの構成は変更しません。

## 用語

### ビジネスユースケース

ビジネスユースケースは、アクターが達成したい業務上の目的です。「受付担当者が予約をキャンセルする」「獣医師が診察を開始する」が該当します。技術構成から独立しているため、`Resolver`、`Store`、データベース API は説明に含めません。

### ユースケース

ユースケースは、ビジネスユースケースをソフトウェアで実現する処理です。`src/useCase` の関数と対応し、入力を受け取って `Resolver`、ドメインロジック、`Store` を呼び出します。処理順序、成功結果、失敗後にどこまで実行するかを担当します。

既存資料の「業務ワークフロー」がこのソフトウェア処理を指す箇所では、「ユースケース」へ変更します。ROP の一般的な処理経路を説明する場合は、特定の用語へまとめず、成功時の処理順序や失敗時の分岐を具体的に書きます。

### ドメインロジック

ドメインロジックは、取得済みの値だけを受け取り、状態遷移や結果を返す純粋な処理です。データベース API、現在時刻、ID 生成を直接呼び出しません。状態遷移の条件は「受付済みだけが診察を開始できる」のように具体的に書き、「業務判断」や「業務ルール」という総称へ置き換えません。

### Resolver と Store

`Resolver` は、ユースケースが必要とする現在状態を取得します。`Store` は、ユースケースが成功した後の状態やイベントを記録します。教材上の境界名には「読み込み」「保存」ではなく `Resolver` と `Store` を使います。処理内容を説明する文章では、「取得する」「状態を記録する」のように具体的な動詞を使います。

### 不変条件

不変条件は S2 の状態遷移で、具体例の後に導入します。「受付済みでない予約から診察中へ遷移できない」を示した後で、状態が変化しても成立し続ける条件を不変条件と呼ぶと説明します。S3 から S6 をまとめる共通語にはしません。

### Discriminated Union

参加者向けの表記は `Discriminated Union` に統一します。「判別共用体」は使いません。最初の説明では、すべての型に共通する `kind` と、それぞれ異なるリテラル値を使って現在の型を絞り込める Union と説明します。

## 学習導線

### S1: ビジネス上の目的からソフトウェアの処理へ写す

EventStorming では、アクター、コマンド、集約、イベントからビジネスユースケースを捉えます。ソフトウェアの処理へ移る箇所でユースケースを導入し、ドメインモデルとの責任を分けます。

S1 のコードでは `Repository` が取得、状態の記録、監査記録を担当しており、ユースケースも時刻と ID を直接生成します。この時点で完成形を説明せず、後続セッションで分離する対象として扱います。図では次の責任を区別します。

- ビジネスユースケース: アクターが達成したい目的と成功時の出来事
- ユースケース: 入力、処理順序、失敗、成功結果
- ドメインロジック: 集約の状態遷移
- `Resolver` と `Store`: 外部との入出力

`Resolver` と `Store` をドメインロジックの外に置く主な理由は、ドメインロジックを pure にし、値だけでテストできるようにすることです。不正な途中状態を記録しないこと、保存先を差し替えやすいこと、出来事を追跡できることは、その構造から得られる効果として説明します。ユースケース全体まで pure であるとは説明しません。

### S2: 起きてはいけない状態遷移

「受付済みでない予約から診察中へ遷移できない」を最初に示します。`Discriminated Union` が状態の候補を表し、遷移関数の引数型が許可された遷移を表すことを説明します。その後で、この条件を不変条件と呼びます。

### S3: 取り違えてはいけない値

`AppointmentId` と `VeterinarianId` の取り違えを、実行前の型検査で止めることに絞ります。「守る不変条件」という成果物は求めません。

### S4: 境界で拒否する入力

ID や Email の schema を再利用可能な小さな schema として示し、それらを `StartExaminationInputSchema` や `OwnerContactSchema` に組み込みます。外部入力全体を一度パースし、成功後は検証済みの入力オブジェクトとして扱う流れを説明します。

`brand` と `transform` を説明するときは、両方を含むコードを直前に表示します。`brand` は値の取り違えを型検査で止め、`transform` は `Sensitive` へ変換して意図しないログ出力を防ぐという違いを、コードと同じ順序で説明します。

### S5: 失敗後に実行してはいけない処理

予約が存在しない場合と状態が不正な場合を、異なる失敗として扱います。`Result` が失敗した後は状態遷移と `Store` 呼び出しが実行されないことを、ユースケースの処理順序として説明します。

ドメイン上の失敗は `Result` の値で扱い、`Store` の障害は外部 I/O の失敗として区別します。教材の説明を直すだけで、既存コードの失敗契約は変更しません。

### S6: 一緒に記録する必要がある値

時刻とイベント ID を外から受け取り、状態とイベントの対応を明示します。状態とイベントを別々に記録すると、片方だけが成功する可能性があることを失敗経路として示します。

S6 完了後の `examples/session-07` では、transaction を持つ `Store` が状態とイベントを原子的に記録します。新しい S7 ページは作らず、S6 の before と after の比較として扱います。

## 相互レビューと運営資料

### 参加者用レビューシート

共通の「守る不変条件の1文」を廃止し、セッションごとに次の見出しを使います。

- S2: 起きてはいけない状態遷移
- S3: 取り違えてはいけない値
- S4: 境界で拒否する入力
- S5: 失敗後に実行してはいけない処理
- S6: 一緒に記録する必要がある値

残りの成果物は「Agent への依頼文」と「型検査では確認できず、テストまたは実行時に確認すること」に揃えます。「型で守れなかった残り」は使いません。

### TA の選定基準

参加者向け資料には、次の趣旨を短く示します。

> TA は、同じ課題に対して設計判断が異なる差分を選びます。完成度や技能による選出ではありません。

TA 用カードには、現在の詳細な優先順位と、全員を最低 1 回選ぶための記録欄を残します。優先順位は、型と実行時チェックの違い、`as` の有無、変更範囲、依頼文、テストでは検出できない設計判断の違いです。

### 講師ガイド

講師ガイドでは、抽象度に応じてビジネスユースケース、ユースケース、ドメインロジックを使い分けます。「業務判断」は使いません。状態遷移の条件は、実際の条件をそのまま読み上げられる文章にします。

## 受け入れ条件

- ビジネスユースケースは技術構成から独立した業務上の目的として説明されています。
- ユースケースは `Resolver`、ドメインロジック、`Store` の処理順序と失敗を扱うソフトウェアの処理として説明されています。
- 実装上のユースケースを「業務判断」「業務フロー」「業務ワークフロー」と呼んでいません。
- ドメインロジックを pure に保つことが、外部 I/O を分ける主な理由として書かれています。
- S2 以外では「不変条件」を共通の成果物として要求していません。
- `Discriminated Union` の表記が参加者向け資料で統一されています。
- S4 で schema の組み合わせと入力オブジェクト全体のパースを確認できます。
- TA の選出目的と基準を参加者が事前に確認できます。
- 最新 `main` の snapshot 構造と異なる架空の API を教材へ追加していません。
