# Session 1: ROPとEventStormingをつなぐ設計

設計更新日: 2026-08-30

## 背景

Session 1では、EventStormingから関数型の業務ワークフローへ進む考え方を扱います。現行案には次の問題があります。

1. EventStormingの集約と業務ワークフローが対応するように見えます。集約は整合性を守るドメインモデルであり、ワークフロー全体ではありません。
2. 診察開始は主な業務条件が「受付済みか」に限られ、複数の失敗をつなぐROPの題材として単純すぎます。
3. 一つの比較図でROPの読み方と業務への適用を同時に説明しているため、線路の意味を知らない参加者が対応関係を追えません。

この設計では、ROP自体を紹介する図と、EventStormingを業務ワークフローへ写す図を分けます。具体例は、複数の業務条件と二つの成功イベントを持つ「診察結果を確定する」へ変更します。

## 目的

参加者が15分の終了時に、次の4点を説明できる状態を目指します。

- ROPには成功レールと失敗レールがあり、各処理が予想できる失敗を返すと失敗レールへ切り替わります。
- コマンドは業務ワークフローの入力、ドメインイベントは成功出力です。
- 集約はワークフローと対応するものではなく、ワークフロー内から呼ばれるドメイン判断と整合性の単位です。
- 読み込みと保存はワークフローの両端に置き、成功イベントをEvent Storeへ渡します。

コードは編集しません。`Result`、`andThen`、`map`などのAPIは後続セッションで扱います。

## 採用する題材

具体例は「診察結果を確定する」です。既存の参照実装にある `RecordExamResultUseCase` と同じ業務を、参加者向けには次の言葉で扱います。

- アクター: 担当獣医師。管理者が代行できるかはHotspotとして残せます。
- コマンド: 診察結果を確定する。
- 主な業務条件:
  - 対象の予約と実行者が存在します。
  - 予約は診察中です。
  - 実行者は担当獣医師または管理者です。
  - 入力された動物と予約の動物が一致します。
- ドメイン判断:
  - `ExamResult.create` が診察結果を作ります。
  - `Appointment.completeExamination` が予約を会計待ちへ進めます。
- 成功イベント:
  - `ExamResultRecorded`
  - `AppointmentExaminationCompleted`

一つのコマンドが複数のドメイン判断を調整し、二つのイベントを成功出力にするため、集約とワークフローの違いを示せます。認可、状態、動物の一致という独立した失敗があるため、ROPの複数の切替点も業務上の理由を持ちます。

## 15分の進行

### 0:00〜2:00: 起きた出来事から業務を始める

講師は「診察結果が記録された」と「診察が完了した」の二つのイベントを事前に置きます。参加者は、画面やテーブルではなく、業務で起きた出来事を出発点にすることを確認します。

### 2:00〜6:00: コマンドと条件を逆算する

班は二つのイベントから、アクター、コマンド、必要な条件を逆算します。最後に次の内容を業務の言葉で確認します。

> 担当者が、診察中の正しい動物についてだけ、診察結果を確定できます。

アクターの権限や管理者代行について答えが分かれた場合はHotspotとして残します。

### 6:00〜8:00: 集約とワークフローを区別する

講師は `ExamResult` と `Appointment` を加えます。これらをワークフロー全体の名前にはしません。ワークフローが二つのドメインモデルを呼び、結果の記録と診察完了を調整することを説明します。

### 8:00〜10:00: ROPのレールを読む

講師は業務固有の名前を含まない「ROPの基本」SVGを示します。図には次の要素だけを置きます。

- InputとOutput
- 上側の成功レール
- 下側の失敗レール
- 「入力を検査する」「対象を取得する」「業務条件を確認する」「結果を作る」の4工程
- 検査、取得、業務条件の3工程から失敗レールへ切り替わる線

一度失敗レールへ移った値は、後続の成功処理を実行せず、そのままOutputへ進みます。成功レールから失敗レールへの切替を1回だけにせず、少なくとも3か所示します。

この図にはDB、メール、HTTP、`Result`、`andThen`、`map`を載せません。線路の読み方と特定の実装技術を分離します。

### 10:00〜14:00: EventStormingを業務ワークフローへ写す

二つ目のSVGで、EventStormingと業務ワークフローを比較します。

- コマンドからワークフローの入力へ対応線を引きます。
- `ExamResult` と `Appointment` から、ワークフロー内の `ExamResult.create` と `Appointment.completeExamination` へ対応線を引きます。
- 二つのドメインイベントから、ワークフローの成功出力へ対応線を引きます。
- 集約からワークフロー全体へは対応線を引きません。
- 認可、診察状態、動物の一致から型付きエラーへ切り替わる流れを示します。

### 14:00〜15:00: 永続化境界を確認する

入力側ではUser ResolverとAppointment Resolverが必要な現在状態を読みます。出力側では、成功時に返された二つのイベントをEvent Storeが同じ整合性境界で受け取ります。失敗時は新しい出来事が起きていないため、イベントを追記しません。

Event StoreはDomain Modeling Made Functionalの必須要件ではありません。このハンズオンでは、ワークフローと永続化をドメインイベントでつなぐ設計判断として採用します。

Web向けユースケースは保存後にイベントの `aggregateState` をレスポンスへ変換できます。この変換は業務ワークフローのイベント出力とは区別します。

## 図の構成

### 図1: ROPの基本

一枚のSVGに緑の成功レールと赤の失敗レールを描きます。4工程を左から右へ並べ、最初の3工程には成功から失敗へ降りる切替線を持たせます。

```text
Input ── 検査 ── 取得 ── 業務条件 ── 結果を作る ── Output
          ╲        ╲          ╲
失敗 ─────╲────────╲──────────╲────────────── Output
```

切替線は別々の失敗が起こり得ることを表します。分岐後に成功レールへ戻る線は描きません。

### 図2: EventStormingと業務ワークフロー

上段にEventStorming、下段に業務ワークフローを置きます。

```text
担当者 → 診察結果を確定する → ExamResult / Appointment
                                   ↓
                    結果が記録された + 診察が完了した

Resolver → 入力 → 検査のROP → ドメイン判断 → Domain Events → Event Store
                    ↓     ↓
                  型付きエラー
```

永続化境界は左右の背景色と破線で示します。中心のワークフロー領域にはResolverとEvent Storeを置きません。

両SVGはアクセシブルな`title`と`desc`を持たせます。モバイルでは図の内側だけを横スクロールでき、ページ全体は横にはみ出しません。デスクトップでは横スクロールなしで全体を表示します。

## 参加者が残す成果物

1. アクター、コマンド、二つのドメインモデル、二つの成功イベントを並べたEventStormingの図
2. 診察結果を確定できる条件とHotspot
3. 集約をドメイン判断へ対応させ、ResolverとEvent Storeを外側へ置いた業務ワークフロー図

S2〜S6で実装する部分の一覧はS1の参加者向けページに表示しません。S1の題材を後続セッションの実装対象と同一にすることも、この変更の要件には含めません。

## 範囲外

- ROPのAPIや関数合成の実装
- Event SourcingをDMMFの一般要件として教えること
- 集約とワークフローを一対一で対応させること
- S2〜S6の演習題材やコードの変更
- Finalの参照実装の変更
- ポリシー、読み取りモデル、外部システムを含む完全なEventStorming

## 受け入れ条件

- ROP紹介図に成功レールと失敗レールがあり、成功から失敗への切替点が3か所以上あります。
- ROP紹介図にDB、メール、HTTP、ライブラリAPIを含めません。
- 参加者が、一度失敗すると後続の成功処理を飛ばすことを説明できます。
- EventStormingの集約は、業務ワークフロー全体ではなく、内部のドメイン判断へ対応しています。
- 業務ワークフローの成功出力は `ExamResultRecorded` と `AppointmentExaminationCompleted` です。
- ResolverとEvent Storeはワークフローの外側にあります。
- Event Storeがこのハンズオン固有の設計判断であることを明記します。
- 「S2〜S6で実装する部分を確認する」を参加者向けページに表示しません。
- モバイルでSVGの右端まで内側スクロールでき、ページ全体に横スクロールが発生しません。
- デスクトップではSVG全体が図の枠内に収まります。
