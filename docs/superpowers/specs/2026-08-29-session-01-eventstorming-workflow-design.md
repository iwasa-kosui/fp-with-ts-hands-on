# Session 1: EventStormingから診察開始を定義する設計

設計確認日: 2026-08-29

## 目的

Session 1では、業務の説明が曖昧な状態から次の順序で設計を進められることを示します。

1. EventStormingで、誰の依頼によって何が起きるかを確かめます。
2. `Appointment.startExamination` を実行できる事前条件を業務の言葉で決めます。
3. EventStormingの並びと、入力、業務判断、成功イベント、型付きエラーを返すROPを対応させます。
4. Appointment Resolverによる読み込みとEvent Storeへの保存を、ワークフローの両端へ分けます。

S1は15分の班ワークです。コードは編集しません。参加者がS1で作る設計を、S2〜S6で同じ `startExamination` に適用します。

## 採用する構成

一日の出来事をゼロから書き出す方法は採用しません。講師が4つのドメインイベントを先に並べ、参加者は「診察が開始された」に関係するアクター、コマンド、確認すべき条件だけを追加します。

この構成には次の意図があります。

- 参加者はEventStormingを実際に行いますが、散文の転記に時間を使いません。
- 一連の業務を見たうえで、`startExamination` だけを詳しく扱います。
- 15分の後半を、EventStormingとROPの比較、成功イベント、永続化境界の説明に使えます。
- 集約名を当てる作業ではなく、診察開始の事前条件を決める作業に集中できます。

## 15分の進行

### 0:00〜1:30: 事故と業務の順番を確認する

講師は、S0で確認した「会計済みの予約でも診察開始を実行できる」事故を示します。その後、同じ予約について次のドメインイベントを時系列に並べた状態を見せます。

1. 来院が受け付けられた
2. 診察が開始された
3. 診察が完了した
4. 会計が完了した

この4枚は事前に配置します。参加者に散文から転記させません。

### 1:30〜3:00: 今回使う付箋を説明する

講師は次の4種類だけを説明します。

- ドメインイベント: 業務で起きたことを過去形で書きます。
- アクター: コマンドを出す人や役割を書きます。
- コマンド: 何をしてほしいかを命令形で書きます。
- Hotspot: 決める必要があることや、担当者によって答えが異なることを書きます。

ポリシー、読み取りモデル、外部システムは扱いません。集約はこの時点では説明しません。

### 3:00〜7:00: 出来事から依頼と事前条件を逆算する

講師は「診察が開始された」を示し、次の順に質問します。

1. 「この出来事は、誰が、どんな依頼を出したために起きましたか」
2. 「その依頼を受け付ける前に、予約がどうなっている必要がありますか」
3. 「会計済みとキャンセル済みの場合はどうなりますか」

参加者はアクターとコマンドを付箋に書きます。アクターは獣医師を正解として配りません。獣医師、看護師、受付など、班によって答えが異なる場合は、責任が決まっていないことをHotspotとして残します。

班は最後に次の事前条件を1文にします。

> 受付を済ませた予約だけ、診察を始められます。

### 7:00〜9:00: 班の答えを比べ、集約を加える

講師は1〜2班のアクターとコマンドを比較します。正解を一つに決めることより、責任の認識が揃っているかを確認します。

事前条件を確認した後、講師がコマンドとドメインイベントの間に「予約」を置きます。予約は、診察を開始できる状態かどうかを判断し、状態を一貫させる単位として説明します。

参加者に集約名を当てさせません。複数のイベントを囲って集約を分類する作業も行いません。

### 9:00〜15:00: EventStormingをROPへ写す

講師は同じ付箋を使い、EventStormingと `Appointment.startExamination` をSVGで比較します。

- 入力: 診察開始のコマンドと予約の現在状態
- 業務判断: 予約が受付済みなら診察開始を受け付ける
- 成功時の出力: `ExaminationStarted`
- 失敗時の出力: `StartExaminationError`

Appointment Resolverによる現在状態の取得は入力側、Event Storeへの成功イベントの追記は出力側へ置きます。中心の業務ワークフローである `Appointment.startExamination` はデータベースへ接続しません。失敗時は新しい出来事が起きていないため保存しません。外側のWeb向けユースケースはResolverとStoreを組み立て、保存後にイベントの `aggregateState` をレスポンスへ使えます。

Event StoreはDomain Modeling Made Functionalに必須の永続化方式ではありません。このハンズオンでは、EventStormingで合意したイベントをワークフローと永続化の共通の契約にするために採用します。S2〜S6の実装項目はS1の参加者向けページに列挙しません。

## EventStormingの完成図

診察開始について、次の並びを完成形とします。

```text
アクター → 「診察を始める」 → 予約 → 「診察が開始された」
                                  ↑
                    どの状態なら始めてよいか
```

アクターは班で確認します。「予約」は講師が最後に加えます。事前条件はHotspotから業務ルールへ変えます。

一日の全イベントを集約ごとに囲う図は作りません。集約はユースケース全体と同じ境界ではありません。事前条件を判断するための状態を保持し、一貫性を守る単位として扱います。

## 参加者、講師、TAの分担

### 参加者

5人班では、1人が付箋を操作し、1人が事故とイベント列を読み上げ、残りの3人がアクター、コマンド、事前条件の案を出します。人数が少ない場合は、読み上げと付箋操作を同じ人が担当します。

参加者は次の作業を行います。

- 「診察が開始された」からアクターとコマンドを逆算します。
- アクターの認識が違う場合はHotspotとして残します。
- 診察開始の事前条件を業務の言葉で1文にします。

### 講師

講師は次の作業を行います。

- 4つのドメインイベントを事前に並べます。
- アクターを正解として先に示しません。
- 班が事前条件を決めた後に予約集約を加えます。
- 同じ付箋とROPの入力、業務判断、成功イベントをSVGで比較します。
- Appointment ResolverとEvent Storeをワークフローの外へ置く理由を説明します。

### TA

TAはS1が始まる前に班のボードを開きます。Live collaborationの開始とリンク共有を15分の中で行いません。

接続や共同編集が30秒で復旧しない場合は、印刷したイベントと空の付箋へ切り替えます。デジタルツールの復旧を待って班ワークを短縮しません。

## S1で残す成果物

各班は次の3点を残します。

1. アクター、コマンド、予約、ドメインイベントを並べたEventStormingの図
2. 「受付を済ませた予約だけ、診察を始められる」という事前条件
3. Resolverを入口、Event Storeを出口に置き、成功イベントと型付きエラーへ分岐する `Appointment.startExamination` の構成図

講師はレビュー時に代表例を1枚保存します。S2〜S6のページでは、この構成図の対象部分を強調して再掲します。

## ワークフローの入出力と業務判断

S1の参加者向け説明では業務の言葉だけを使います。設計上は、次の契約へつながります。

```ts
type StartExaminationInput = Readonly<{
  appointmentId: AppointmentId;
  veterinarianId: VeterinarianId;
}>;

type DecideStartExamination = (
  checkedIn: CheckedIn,
  veterinarianId: VeterinarianId,
  context: EventContext,
) => ExaminationStarted;

type StartExaminationError =
  | AppointmentNotFound
  | InvalidAppointmentState
  | AppointmentConflict;

type StartExaminationOutput = ResultAsync<
  ExaminationStarted,
  StartExaminationError
>;
```

この契約では、中心の業務ワークフローである `Appointment.startExamination` の成功出力は `ExaminationStarted` です。外側のWeb向けユースケースでレスポンスが必要な場合は、保存後にイベントが持つ `InExamination` から組み立てます。

予約が存在しない場合は、読み込み結果を受けたユースケースが `AppointmentNotFound` を返します。受付済みでない場合は、事前条件の検査が `InvalidAppointmentState` を返します。保存時の業務競合は `AppointmentConflict` を返します。データベース停止などの技術的な異常は業務エラーへ変換せず、外側の例外処理へ渡します。

## 境界とI/O

最終的なユースケースは次の順序で処理します。

1. HTTP境界で文字列の予約IDと獣医師IDを検査します。
2. `AppointmentId` と `VeterinarianId` を持つ入力を作ります。
3. Appointment Resolverを通して予約の現在状態を読み込みます。
4. 予約が存在することと、受付済みであることを確認します。
5. `EventContext` と受付済みの予約から `ExaminationStarted` を作ります。
6. Event Storeを通してドメインイベントを1回保存し、参照用の現在状態も同じトランザクションで更新します。
7. 保存したイベントが持つ診察中の予約を成功値として返します。

入力の検査自体は純粋な変換ですが、外部の値をドメインへ入れる境界に置きます。予約の読み込み、時刻とイベントIDの取得、保存はI/Oです。業務判断はこれらの値を引数で受け取る純粋関数にします。

## S2〜S6への接続

この節は教材実装を揃えるための内部資料です。S1の参加者向けページには表示しません。

| Session | 扱う部分 | 参加者が実装する内容 | 現行教材からの変更 |
| --- | --- | --- | --- |
| S2 | 事前条件と状態遷移 | `CheckedIn` だけを受け取る `startExamination` | 6状態と他の遷移は、禁止状態を説明するために残します |
| S3 | 入力の識別子 | `AppointmentId` と `VeterinarianId` を区別する | 中心課題を `PetId` と `OwnerId` から変更します |
| S4 | 外部入力の境界 | HTTPの文字列を検査して `StartExaminationInput` を作る | `ExamResult` とPIIを時間内の演習から外します |
| S5 | 予想できる失敗 | 予約なしと状態不正をResultで返す | 現行の `startExamination` を継続します |
| S6 | I/Oと保存 | Clock、EventIdGenerator、resolver、storeを外から渡す | `ExaminationStarted` を1回だけ保存する現行方針を継続します |

S2では、予約の6状態と状態追加時の網羅性を残します。これらは、受付済み以外を拒否する理由を理解するために必要です。ただし、S1からの接続は `startExamination` を入口として説明します。

S3では、予約IDと獣医師IDを中心課題に変えます。現在は両方が手本として型付け済みのため、開始スナップショットと演習テストも組み直します。ペットID、飼い主ID、検査IDは時間外の補足へ移します。

S4では、`ExamResult` の検査とPIIのマスキングを時間内の演習から外します。S4ページの時間外の補足として残し、exerciseの失敗件数、参加者の修正対象、レビュー観点には含めません。入力検証とPIIを同じ30分で扱う構成にはしません。

S5とS6は現在の `startExamination` を利用できます。ただし、各ページの冒頭でS1の構成図を再掲し、その回で変更する部分を強調します。

## アクターと認可

S1では、アクターを確認して業務上の責任を明確にします。S2〜S6では、アクターの権限判定を追加しません。権限判定まで同時に扱うと、各回の中心課題が増えるためです。

`actorUserId` と「獣医師本人または管理者だけが診察を開始できる」という認可は、Finalの参照実装で扱います。S1では、アクターの違いを責任のHotspotとして残せるところまでを範囲とします。

## 閉じたPR #98から採用する点と採用しない点

[PR #98](https://github.com/iwasa-kosui/fp-with-ts-hands-on/pull/98)は、予約患者と急患を並行して扱い、誰が診察保留を記録するかをHotspotとして残す案でした。

次の点を採用します。

- アクターを最初から正解として固定せず、担当者の認識差を確認します。
- 答えが決まっていない箇所をHotspotとして残します。
- 集約を状態と業務判断の単位として説明します。

次の点は採用しません。

- 予約患者と急患の2レーン
- 7件のドメインイベント
- 急患優先、診察保留、受付への連絡を同時に扱う構成

2レーンを扱うと、15分の中心が優先順位と責任分担になります。今回の目的である `startExamination` の事前条件、入出力、I/Oの分離まで進む時間が残りません。

## 範囲外

次の内容はS1で扱いません。

- ポリシー、読み取りモデル、外部システムのEventStorming記法
- 集約を参加者に分類させる作業
- 急患と予約患者の並行処理
- neverthrow、Zodの実装方法
- アクターの認可ルール
- コード編集とexerciseコマンド

## 受け入れ条件

設計どおりに進行できたかを、会場リハーサルで次の条件から確認します。

- 1分30秒で事故と4つのドメインイベントを確認できます。
- 1分30秒で4種類の付箋を説明できます。
- 5人班が4分以内にアクター、コマンド、Hotspotを追加できます。
- 班が「受付を済ませた予約だけ、診察を始められる」と1文にできます。
- 講師が9分経過時点で入力、業務判断、出力の説明へ移れます。
- 参加者が終了時に、`startExamination` の事前条件と出力イベントを説明できます。
- 参加者が予約の読み込み、時刻とIDの取得、保存を業務判断の外に置く理由を説明できます。
- Live collaborationを使えない班が30秒以内に印刷カードへ切り替えられます。
