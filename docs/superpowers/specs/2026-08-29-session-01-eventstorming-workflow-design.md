# Session 1: ROPとEventStormingをつなぐ設計

設計更新日: 2026-08-30

## 背景

Session 1では、EventStormingから関数型の業務ワークフローへ進む考え方を扱います。現行案には次の問題があります。

1. EventStormingの集約と業務ワークフローが対応するように見えます。集約は整合性を守るドメインモデルであり、ワークフロー全体ではありません。
2. 診察開始は主な業務条件が「受付済みか」に限られ、複数の失敗をつなぐROPの題材として単純すぎます。
3. 一つの比較図でROPの読み方と業務への適用を同時に説明しているため、線路の意味を知らない参加者が対応関係を追えません。
4. 複数の集約と複数のイベントを一度に出す題材は、S1で説明したいワークフロー境界よりも整合性やイベント連携へ注意を逸らします。

この設計では、ROP自体を紹介する図と、EventStormingを業務ワークフローへ写す図を分けます。具体例は、一つの`Appointment`集約と一つの成功イベントで完結し、複数の失敗理由を持つ「予約をキャンセルする」とします。

## 目的

参加者が15分の終了時に、次の4点を説明できる状態を目指します。

- ROPには成功レールと失敗レールがあり、各処理が予想できる失敗を返すと失敗レールへ切り替わります。
- コマンドは業務ワークフローの入力、ドメインイベントは成功出力です。
- ポリシーは業務条件、集約は整合性を守るドメインモデルとして分け、集約はワークフロー全体と対応しません。
- 読み込みと保存はワークフローの両端に置き、成功イベントをEvent Storeへ渡します。

コードは編集しません。`Result`、`andThen`、`map`などのAPIは後続セッションで扱います。

## 採用する題材

具体例は「予約をキャンセルする」です。既存の参照実装にある`CancelAppointmentUseCase`と同じ業務を、参加者向けには次の言葉で扱います。

- アクター: 受付担当者。管理者以外の代行を認めるかはHotspotとして残せます。
- コマンド: 予約をキャンセルする。
- ポリシー:
  - 実行者が存在し、予約を管理する権限を持ちます。
  - 対象の予約が存在します。
  - 予約は`Scheduled`または`CheckedIn`です。
  - キャンセル理由があります。
- ドメイン判断: `Appointment.cancel`が予約をキャンセル済みへ遷移させます。
- 成功イベント: `AppointmentCanceled`

一つの集約だけで終わるため、複数集約の整合性やワークフロー間連携を持ち込みません。一方、入力、認可、取得、状態、理由、保存には独立した失敗があるため、ROPの複数の切替点には業務上の理由があります。

## 15分の進行

### 0:00〜2:00: 起きた出来事から業務を始める

講師は「予約がキャンセルされた」イベントを事前に置きます。参加者は、画面やテーブルではなく、業務で起きた出来事を出発点にすることを確認します。

### 2:00〜6:00: コマンドと条件を逆算する

班は一つのイベントから、アクター、コマンド、必要な条件を逆算し、ポリシーとしてまとめます。最後に次の内容を業務の言葉で確認します。

> 予約を管理できる担当者が、診察開始前の予約だけを、理由を残してキャンセルできます。

診察直前のキャンセル可否について答えが分かれた場合はHotspotとして残します。

### 6:00〜8:00: ポリシー、集約、ワークフローを区別する

講師はポリシーと`Appointment`集約を別ノードで加えます。ポリシーは業務条件、集約は状態の整合性を守るドメインモデル、ワークフローはResolver、ポリシー確認、集約の判断、イベント出力を調整する関数です。題材に集約が一つしかなくても、集約とワークフローは同じ概念ではありません。

### 8:00〜10:00: ROPのレールを読む

講師は業務固有の名前を含まない「ROPの基本」SVGを示します。図には次の要素だけを置きます。

- InputとOutput
- 上側の成功レール
- 下側の失敗レール
- 「入力を検査する」「対象を取得する」「業務条件を確認する」「結果を作る」の4工程
- 検査、取得、業務条件の3工程から失敗レールへ切り替わる線

一度失敗レールへ移った値は、後続の成功処理を実行せず、そのままOutputへ進みます。成功レールから失敗レールへの切替を1回だけにせず、少なくとも3か所示します。

この図にはDB、メール、HTTP、`Result`、`andThen`、`map`を載せません。線路の読み方と特定の実装技術を分離します。

### 10:00〜14:00: EventStormingを業務ワークフローへ写す

二つ目のSVGで、EventStormingと業務ワークフローを比較します。

- コマンドからワークフローの入力へ対応線を引きます。
- ポリシーからワークフロー内の確認処理へ対応線を引きます。
- `Appointment`集約からワークフロー内の`Appointment.cancel`へ対応線を引きます。
- 一つのドメインイベントからワークフローの成功出力へ対応線を引きます。
- `Appointment.cancel`はワークフロー内のドメイン判断として置きます。
- 集約からワークフロー全体へは対応線を引きません。
- 具体図は成功経路と永続化境界へ集中させ、失敗レールと切替はROP基本図だけで説明します。

### 14:00〜15:00: 永続化境界を確認する

入力側ではUser ResolverとAppointment Resolverが必要な現在状態を読みます。出力側では、成功時に返された`AppointmentCanceled`をEvent Storeが受け取ります。失敗時は新しい出来事が起きていないため、イベントを追記しません。

Event StoreはDomain Modeling Made Functionalの必須要件ではありません。このハンズオンでは、ワークフローと永続化をドメインイベントでつなぐ設計判断として採用します。

Web向けユースケースは保存後にイベントの`aggregateState`をレスポンスへ変換できます。この変換は業務ワークフローのイベント出力とは区別します。

## 図の構成

### 図1: ROPの基本

一枚のSVGに緑の成功レールと赤の失敗レールを描きます。4工程を左から右へ並べ、最初の3工程には成功から失敗へ降りる切替線を持たせます。

```text
Input ── 検査 ── 取得 ── 業務条件 ── 結果を作る ── Output
          ╲        ╲          ╲
失敗 ─────╲────────╲──────────╲────────────── Output
```

切替線は別々の失敗が起こり得ることを表します。分岐後に成功レールへ戻る線は描きません。

### 図2: EventStormingと業務ワークフロー

上段にEventStorming、下段に業務ワークフローを置きます。

```text
受付担当者 → 予約をキャンセルする → ポリシー → Appointment集約 → 予約がキャンセルされた

Resolver → 入力 → 権限・存在・状態・理由 → Appointment.cancel
                                                ↓
                                    AppointmentCanceled → Event Store
```

永続化境界は左右の背景色と破線で示します。中心のワークフロー領域にはResolverとEvent Storeを置きません。

ROPを使う顧客上の理由は、どの条件で止まってもキャンセルや保存へ進まず、一部だけ処理された状態を防ぎ、受け付けられなかった理由を返せることです。技術上の理由は、成功処理の途中に分岐を散らさず、変更箇所とテスト観点を対応させられることです。

永続化を両端へ置く顧客上の理由は、条件を通過したキャンセルだけを保存し、誰がいつ取り消したかを追えることです。技術上の理由は、業務判断をデータベースAPIから切り離して値だけでテストし、読み方や保存先の変更を境界内へ閉じ込められることです。

モバイルでは図の内側だけを横スクロールでき、ページ全体は横にはみ出しません。デスクトップでは横スクロールなしで全体を表示します。

## 参加者が残す成果物

1. アクター、コマンド、ポリシー、`Appointment`集約、一つの成功イベントを分けて並べたEventStormingの図
2. 予約をキャンセルできるポリシーとHotspot
3. `Appointment.cancel`を内部へ置き、ResolverとEvent Storeを外側へ置いた業務ワークフロー図

## 受け入れ条件

- ROP紹介図に成功レールと失敗レールがあり、成功から失敗への切替点が3か所以上あります。
- ROP紹介図にDB、メール、HTTP、ライブラリAPIを含めません。
- 参加者が、一度失敗すると後続の成功処理を飛ばすことを説明できます。
- 具体例は`Appointment`集約一つと`AppointmentCanceled`イベント一つで完結します。
- EventStorming図でポリシーと集約を別ノードにし、ワークフロー内の条件確認と`Appointment.cancel`へそれぞれ対応させます。
- 集約は、業務ワークフロー全体ではなく、内部のドメイン判断として説明します。
- 具体的な業務ワークフロー図には失敗レールを含めず、成功経路と永続化境界だけを示します。
- ResolverとEvent Storeはワークフローの外側にあります。
- Event Storeがこのハンズオン固有の設計判断であることを明記します。
- 「S2〜S6で実装する部分を確認する」を参加者向けページに表示しません。
- 参加者向けページの節見出しに進行時刻を表示しません。
- モバイルでSVGの右端まで内側スクロールでき、ページ全体に横スクロールが発生しません。
- デスクトップではSVG全体が図の枠内に収まります。
