# Session 00 先人のコードを引き継ぐオンボーディング設計

## 背景

現在の Session 00 は、動物病院の業務紹介、事故の再現、追加要求の整理を 00-A と 00-B の2ページで扱っている。参加者が新任エンジニアとして既存システムを引き継ぐシナリオに対し、事故対応が冒頭から具体化されすぎており、業務領域、アプリケーション、既存設計の全体像を把握する時間になっていない。

Session 00 を、退職した先人のコードを引き継ぐための30分のオンボーディングへ再構成する。参加者はまだ実装を変更せず、動物病院の仕事とアプリケーションの役割を理解し、後続セッションで扱う設計課題の所在をコード上で概観する。

## 目的

- Session 00 のタイトルを「オンボーディング: 退職した先人のコードを引き継ぐ」に変更する。
- 参加者が動物病院へ採用された経緯を、吹き出し付きの物語として伝える。
- 業務領域、アプリケーションの機能、来院の状態遷移、既存コードの対応関係を紹介する。
- 1つのガイド付き Code Explorer で、既存設計にある5つの課題をコード上から確認できるようにする。
- 問題が顕在化する前に迂闊なリファクタリングを行わず、業務、仕様、設計の理解に留める判断を参加者へ伝える。
- 00-B を廃止し、Session 00 から Session 01 へ直接進む構成にする。

## 対象外

- Session 00 では事故報告、事故再現、失敗するテスト、`pnpm exercise:00` を参加者へ提示しない。
- `examples/session-00` の legacy 実装や演習テストは変更しない。後続 snapshot の基点として維持する。
- Session 00 ではコードを編集・実行せず、設計課題を解決しない。
- Session 01 以降の実行可能な Code Explorer は `modern-monaco` へ移行しない。
- 後続セッションの要求、実装対象、演習コマンドは変更しない。

## セッション構成

### タイトル、番号、URL

- タイトル: `オンボーディング: 退職した先人のコードを引き継ぐ`
- シーケンス表示: `00`
- 所要時間: 30分
- 正規 URL: `/sessions/00-onboarding/`

既存の `/sessions/00-break-the-app/`、廃止する `/sessions/00-read-the-incident/`、従来の `/module-00` は、いずれも正規 URL へ恒久的にリダイレクトする。ブックマークや過去資料からアクセスした参加者を404ページへ送らない。

### 冒頭の物語

セッションのヒーロー直後、業務説明より前に、次の3つの吹き出しを順番に表示する。

1. **先人の獣医**

   「この動物病院のシステムは、診療の合間にすべてバイブコーディングで作りました！」

2. **院長**

   「その偉大な獣医さんが退職してしまいました。システムのことを詳しく知る人がいません……」

3. **院長**

   「そこで採用されたエンジニアが、あなたです。まずは病院の仕事と先人のコードを知るところから始めてください」

物語全体を会話としてグループ化し、内容を表す `aria-label` を付ける。各発言は話者名と本文を同じまとまりで表す。先人の獣医と院長は配置と背景色を変えるが、色だけに依存せず話者名を常に表示する。吹き出しのしっぽは CSS で描画し、既存サイトの太い罫線、角丸、レモン色とミント色を踏襲する。

### 着任初日のオンボーディング

物語の後は、次の順に既存システムを紹介する。

1. 動物病院が飼い主と動物へ提供する価値
2. 飼い主、受付スタッフ、獣医師、会計担当の役割
3. 予約、受付、診察・カルテ、会計、フォロー連絡、申し送りを支えるアプリケーション
4. 予約から会計までの来院状態と、業務上の出来事による遷移
5. 業務上の概念と `examples/session-00/src` のコードの対応

事故、障害、赤いテストを起点にせず、「何を支えるアプリケーションで、コードはそれをどう表しているか」を理解する順序にする。

## ガイド付き Code Explorer

### 役割

Session 00 専用の読み取り専用 Code Explorer を1つ表示する。5つの課題カードから1つを選ぶと、対応するファイルを開き、該当行を中央へスクロールして強調する。カードの隣には「現在の設計」と「将来困り得ること」を短く表示する。

編集、リセット、実行、WebContainer、出力パネルは表示しない。目的はコードを修正することではなく、後続セッションで調べる場所を知ることである。

### 紹介する設計課題

1. **状態を任意の文字列で表している**

   `LegacyAppointment.status` と `updateStatus` の `newStatus` が `string` であり、業務で使う状態の種類と許可する遷移を型から読み取れない。

2. **状態固有の情報が optional field に広がっている**

   `LegacyStatusExtra` に診察、会計、キャンセルの情報が同居し、どの状態で何が必須なのかを型から読み取れない。

3. **用途の異なる ID がすべて `string` である**

   予約、動物、飼い主、獣医師の ID が同じ型であり、値の用途を TypeScript が区別できない。

4. **予期可能な失敗を `throw` している**

   予約が見つからない場合の処理が例外であり、呼び出し側が扱うべき失敗の種類を関数の型から判断できない。

5. **個人情報を含む値をそのままログへ渡している**

   連絡先を含む予約オブジェクトを `logger.info` へ渡しており、ログへ出してよい情報の境界が値や型に表れていない。

課題定義は、識別子、タイトル、説明、対象ファイル、1つ以上の強調範囲を持つ読み取り専用データとして管理する。強調範囲は実ファイル内に存在し、対象となるコードを含むことをテストで検証する。

### `modern-monaco` と Shiki

Session 00 のガイド付き Code Explorer に限り、`modern-monaco` の lazy mode と Shiki を使用する。

- 最初の表示は Shiki で TypeScript を色付けし、選択中の課題に対応する行へ強調クラスを付ける。
- `modern-monaco` の読み込み後は同じファイルを読み取り専用で開き、Monaco decoration で同じ範囲を強調する。
- 課題を切り替えたときは、Shiki の事前表示と Monaco の表示が同じファイル、範囲、説明を示す。
- TypeScript grammar とテーマはアプリへ含め、既定の外部 CDN へ実行時に依存しない。
- `modern-monaco` は API 変更の可能性が明記されているため、依存バージョンを固定する。
- 既存の実行可能な `CodeExplorer` と `MonacoEditor` は変更せず、今回の読み取り専用ビューに移行範囲を限定する。

Shiki のカスタム line transformer は課題定義の範囲から強調用のクラスを出力し、スタイル自体は提供しないため、既存サイトの配色に合う強調スタイルを CSS で定義する。教材 source に強調用コメントは埋め込まない。ハイライトの意味は色だけに任せず、選択中の課題名と説明を常にテキストで示す。

参考資料:

- [modern-monaco](https://github.com/esm-dev/modern-monaco)
- [Shiki Transformers](https://shiki.style/packages/transformers)

### 操作とアクセシビリティ

- 課題一覧は順序付きリストとボタンで表し、選択中の項目を `aria-pressed` で伝える。
- ファイル名、課題名、説明はエディタの描画前から読めるようにする。
- 課題を選択すると視覚的には対象行を表示するが、キーボードフォーカスを強制的にエディタへ移動しない。
- Shiki の事前表示を、JavaScript が利用できない場合の読み取り可能なフォールバックとして残す。
- 狭い画面では課題一覧、説明、コードの順に縦積みし、横方向のコードスクロールを許容する。

## セッションの締め

5つの課題を紹介した後、次の判断を参加者へ伝える。

> しかし、まだ問題は顕在化していません。迂闊にリファクタリングすれば、既存仕様を壊してしまうかもしれません。今日は業務、仕様、設計の理解に留め、明日から実際の開発に着手しましょう。

Session 00 の完了条件は、実装を変更することではない。アプリケーションが支える業務と、既存設計で後から確認すべき5つの場所を説明できることである。次のナビゲーションは Session 01「状態遷移を型にする」へ直接つなぐ。

## 00-B 廃止と周辺の同期

- `00-read-the-incident` のページ、カタログ項目、Code Explorer workspace、ページテスト、静的ビルド対象、E2E 対象を削除する。
- Session 00 のシーケンス型から `00-A` と `00-B` を除き、`00` を追加する。
- Session 01 の前セッションを新しい Session 00 に変更する。Session 01 はページ内で要求と状態遷移を説明しているため、00-B の本文を移植しない。
- ファシリテーターガイドの 0:10-0:40 を、業務・アプリケーション・設計課題を理解する30分のオンボーディングへまとめる。
- 0:30 のチェックポイントを、業務の流れと5つの設計課題を説明できることへ変更する。
- トップページの Session 00 タイトル、概要、最初の仕事をオンボーディングへ同期し、事故を再現するよう促す文言を削除する。
- 過去の完了済み設計書と実装計画は履歴として変更しない。

## 受け入れ条件

- Session 00 の H1 とトップページの紹介に「オンボーディング: 退職した先人のコードを引き継ぐ」が表示される。
- Session 00 の冒頭に、先人の獣医、院長、院長の順で3つの吹き出しが表示される。
- Session 00 は業務領域、アプリケーション、来院状態、コードの対応を説明する。
- Session 00 に事故報告、事故再現、失敗するテスト、`pnpm exercise:00` の案内が表示されない。
- 読み取り専用 Code Explorer には5つの課題があり、選択すると対応するファイルと範囲が強調される。
- JavaScript の読み込み前または利用不可の状態でも、Shiki で色付けしたコードと選択中の課題を読める。
- 読み取り専用 Code Explorer に編集、リセット、実行、停止、出力パネルが表示されない。
- 5つの課題を確認した後に、迂闊なリファクタリングを避けて理解に留める判断が表示される。
- `00-read-the-incident` がセッションカタログと静的ページから削除され、旧URLは新しい Session 00 へリダイレクトされる。
- Session 00 から Session 01 へ直接移動できる。
- `pnpm typecheck`、`pnpm test`、`pnpm build` が成功する。

## 検証方針

- Session 00 のページテストで、タイトル、会話グループ、話者、発言順、業務 overview、5つの設計課題、締めの判断、事故説明と演習コマンドの不在を検証する。
- 課題定義の単体テストで、識別子の一意性、対象ファイルの存在、強調範囲の妥当性、期待するコード断片との対応を検証する。
- 読み取り専用 Code Explorer のコンポーネントテストで、初期課題、課題切り替え、ファイル切り替え、選択状態、操作ボタンの不在を検証する。
- Shiki の出力テストで、TypeScript の色付けと対象行の強調クラスを検証する。
- カタログ、前後ナビゲーション、静的ページ一覧、worker route のテストで、00-B の廃止と旧URLのリダイレクトを検証する。
- 既存の Session 01 以降の Code Explorer テストを維持し、実行・編集機能へ影響がないことを確認する。
