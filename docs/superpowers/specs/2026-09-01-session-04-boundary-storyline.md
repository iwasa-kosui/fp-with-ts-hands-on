# Session 04 境界設計の筋書き

## 目的

Session 04を、一件の診察開始事故を調査しながら入力と出力の境界を直す演習へ変更します。中心となる原則は「外部から入る値は検証し、外部へ出す値は必要な項目へ絞る」です。

## 業務上の出来事

2026-08-30 15:20、猫のムギが受付を終えました。15:30になると勤務表連携から診察開始要求が届きますが、獣医師IDにはUUIDではなく `night-shift` が入っています。

開始時点の実装は入力を検証しないため、予約を `CheckedIn` から `InExamination` へ変更します。調査のため監査記録を開くと、不正な担当者IDに加えて、飼い主の氏名、メールアドレス、電話番号も保存されています。

病院責任者からの要求は次の2点です。

- 不正な診察開始要求では、予約状態も監査記録も変更しません。
- 診察開始の監査記録には、予約ID、獣医師ID、診察開始時刻だけを保存します。

## 学習の流れ

### 1. 入力を検証します

HTTPから届く値は `unknown` として受け取ります。予約IDと獣医師IDをまとめて検証し、成功時だけ `StartExaminationInput` を返します。失敗時は、問題の項目を示す `path` と理由を示す `message` を保持します。

### 2. HTTP境界で処理を止めます

検証失敗を例外へ変換せず、HTTP 422として返します。予約の読み込み、状態遷移、保存、監査追加には進みません。テストではレスポンスだけでなく、SQLiteの予約状態と監査件数が変わらないことも確認します。

### 3. 監査データを必要な項目へ絞ります

予約全体から機密項目を引き算するのではなく、診察開始の監査に必要な3項目を明示的に組み立てます。教材で利用しない飼い主の連絡先は予約テーブルにも保持しません。初期監査には予約IDだけを保存します。

## 演習の受け入れ条件

- 正しい2種類のIDだけが `StartExaminationInput` になります。
- 不正な入力では、すべての検証問題を参照できます。
- 不正なHTTP要求は422を返します。
- 不正なHTTP要求では予約状態と監査記録が変わりません。
- 正常な診察開始要求は303を返し、予約を `InExamination` にします。
- 診察開始の監査データは予約ID、獣医師ID、診察開始時刻の3項目だけです。
- 監査記録と予約テーブルに飼い主の連絡先を保存しません。

## 隣接セッションとの分担

Session 03はプログラム内部で識別子を取り違えない設計を扱います。Session 04は外部との境界を扱います。予約なしや状態不正など予測できる業務上の失敗はSession 05、状態保存と監査追加の整合性や保存障害はSession 06で扱います。

Session 04で検証するのはJSONとして読み取れた診察開始入力です。壊れたJSONやContent-Typeの誤りをHTTPエラーへ正規化する処理は対象外とします。

`Sensitive` は補足に置きます。正当な理由で読み込んだ機密値の誤出力を防ぐ追加策として説明し、不要な情報を収集または保存しない設計の代わりにはしません。
