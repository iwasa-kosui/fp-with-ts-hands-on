**第3版（2026-08-12）**: 表中心の記述を見出しと段落へ書き直した。**内容の変更はない。** 判断、理由、数字、ファイルパス、捨てた案、未検証事項の記載はすべて第2版のまま維持しており、変えたのは表現形式だけである。表として残したのは、全体タイムテーブル（§3.1）と31概念の取捨一覧（§2.2）の2つだけで、それ以外の表はすべて散文または箇条書きへ展開した。

### 第2版で何を、なぜ変えたか

第2版の変更は8点ある。

**1. 「最大2関数」を廃止し、§1 の新しいスコープ制約へ置き換えた。** ユーザーからの指摘「原則2関数という制約そのものに明確な根拠があるとは思えない」は妥当である。事実確認の結果、`docs/prd/prd-001.md:286` のリスク表に「扱う概念が多く認知負荷が高い／手を動かすだけで判断過程が残らない」への対策と書かれているだけで、**「2」という数字自体の根拠は全文書のどこにもなかった**。L18 / L175 / L198 / L216 / L275 / L286 / L299、`AGENTS.md:24`、`docs/event/facilitator-guide.md:10` は、いずれも数字を反復しているだけである。なお、数字を 2 から 5 へ緩めるという案も検討したが、根拠がないまま別の数字になるだけで指摘の趣旨を満たさないため採らない。

**2. 演習スコープを関数単位からモジュール単位へ拡大した。** エージェントが書くのであればタイピング量は制約にならない。制約すべきは「参加者が一度に負う判断の数」であって「打鍵量」ではない。

**3. PRD の狙いを反転して読み直した。** エージェント前提では「認知負荷の管理」は判断点の数で管理でき、「判断過程を残す」ことの重要度はむしろ上がる。参加者の仕事は「2関数を書く」ことから「不変条件を言語化する → 依頼文に落とす → 生成差分を型に照らしてレビューする」ことへ移る。これは `prd-001.md:152`「設計判断をAIエージェントへの依頼と人間のレビューへ転用する」および L202「AIエージェントは主目的にせず、設計判断を依頼文とレビューへ転用する題材として扱う」と正面から一致する。

**4. 到達点を引き上げた。** `ResultAsync`（概念 #15）ほか3件を、お土産または「読む」から演習へ移した。判断と理由は §2.2 に書く。31概念の内訳は、演習16／読む4／お土産11 から **演習19／読む4／お土産8** へ変わった。

**5. 時間配分を組み替えた。** 180分は不変である。引き上げの原資は、Final ツアーを10分から5分へ、Session 00 を20分から15分へ削って捻出した。検算は §3.1 に示す。

**6. 「エージェントレビュー」を廃止から復活させた。** ただし独立セッションとしてではなく、全セッションの背骨（ADV ループ）と、まとめ枠の成果物として復活させる。判断と理由は §1.2 および §1.5 に書く。初版の廃止理由は、答えが `exercises/agent-review.test.ts:7-16` に逐語で書かれているという現行実装の欠陥に対するものであって、概念の欠陥に対するものではなかった。`prd-001.md:190` が定める成果物「依頼文、レビュー観点、検証可能なチェックリスト」は、エージェント前提の教材では中核になる。

**7. エージェント非保持者向けのフォールバックを各セッションに定義した。** §0.1 の暫定前提（エージェントは推奨だが必須ではない）に対応する措置である。具体的な提示単位は §1.4 と §4 の各セッションに書いた。

**8. 波及する既存文書の改訂一覧を新設した（§7）。** 「最大2関数」の廃止によって実体と矛盾することになる既存記述を、書き換え案つきで列挙した。

## 背景

2026-08-30 15:00-18:00（180分、connpass、オフライン開催、5人1班＋各班 TA 1名）のイベントに向けて、`examples/` と `apps/docs` をゼロベースで設計し直す。残り18日である。

現行教材（`examples/session-00`〜`session-05` の6スナップショットと `apps/docs` の7ページ）には、調査で確認した次の構造的な問題がある。

- **演習量が制約を破っている。** 実際の演習は白紙からのファイル新規作成であり、生成すべきコードは exercise:01 が 114 行、exercise:02 が 8 ファイル 114 行、exercise:03 が 8 ファイル新規＋7 ファイル改修の 185 行に達する。25〜30分では完走しない。
- **演習形式が4種類に割れている。** 事故デモ（00）、白紙からの新規作成（01/02/03/05）、TODO 穴埋め（04）が混在しており、04 は 20分枠に対して実質5分で終わる。
- **演習が完了不能なものがある。** `examples/session-02/package.json` の依存は `vitest` のみだが exercise:02 は Zod を要求する。`examples/session-03/package.json` は `zod` のみだが exercise:03 は neverthrow の `isOk()` を要求する。いずれも実ファイルで確認済みである。
- **セッション間の連鎖に断絶がある。** session-03 から 04 にかけて `safeParse` から `parse` への破壊的変更が7ファイル分「隠れ改修」として入っている。session-04 の演習は 04 から 05 への実差分（dual-write 解消、Timestamp branding、port 分割）を一切カバーしていない。session-05 演習の `collectFollowUpTargets` は `examples/final` にシグネチャが存在せず、解答の参照先がない。
- **番号がずれている。** `examples/session-01/README.md` は「Session 01 で実装する型付き状態モデル」と書いているのに対し、`examples/session-02/README.md` は同じ主題を「Session 02: 型で状態遷移を閉じる」と名乗っている。
- **`exercises/**` が typecheck の対象外である。** 全セッションの `tsconfig.json` の include は `["src/**/*.ts", "test/**/*.ts", "vitest.config.ts"]` である。型で教える教材でありながら、参加者が最も読むファイルの型が検証されていない。
- **`examples/final` との距離が埋まらない。** session-05 と final は src+test の行数で28倍の開きがあり、未紹介の概念が15種以上ある。`durationMinutes: 10` の「完成例を眺める」枠では橋渡しにならない。

**さらに第2版では、制約そのものに問題があると判断した。** 上に挙げた演習量の超過は「2関数に収まっていない」ことが問題なのではなく、**参加者が一度に負う判断の数と、判断が記録に残らないこと**が問題である。関数の個数はその代理指標として不正確であり、しかも「2」という値に根拠がない。本設計は制約を張り替えたうえで、上の問題群を解く。

## 目的

- 演習スコープの制約を、根拠のある形（PRD が守ろうとしていた狙いを直接測る形）で定義し直す。
- 180分で参加者が到達する地点を、`examples/final` と明確に区別して定義する。
- 全セッションの演習を「配布されたモジュールを型で守られた形にする」1形式に統一し、**言語化 → 委譲 → 検証**（ADV）の3手順を全セッション共通の骨格にする。
- セッション間の連鎖（N の完成形が N+1 の出発点になること）を、人手の同期ではなくテストで機械的に担保する。
- `apps/docs` のセッションページを catalog 駆動の共通骨格へ移し、文言の literal 一致に依存したテストを構造検証へ置き換える。
- 調査で判明した既知の欠陥を、実装フェーズのどの段階で直すかを確定する。
- 制約の張り替えによって実体と矛盾する既存文書を列挙し、書き換え案を示す。

## 対象外

- **`examples/final` は変更しない。** 到達点ではなく参照実装かつお土産として扱い、当日は読む／見せるだけにする。参加者は final の環境構築をしない。
- 白紙からのファイル新規作成を求める演習は採らない。モジュールは**必ず素朴な実装として配布済み**であり、参加者は既存ファイルを書き換える。
- 過去に却下済みの方針は蒸し返さない。具体的には、サーバー側での参加者コード実行、編集内容の永続化・共有 URL・localStorage、Safari / Firefox の正式対応、Markdown parser の導入、Git tag による章管理、セッション間で共有する内部 package、外部 CDN 依存の Shiki である。
- Astro Content Collections / MDX / 外部 CMS は導入しない。理由は §6.1 に書く。
- event sourcing、projection、永続イベントストア、認証・認可、HTTP アダプタの詳細設計は、当日手を動かす範囲から外す（PRD 非ゴール）。
- 通常の再診フロー、および `examples/final` の UI 方針（Operator Console）には触れない。
- **特定のコーディングエージェント製品への依存**（設定ファイル、専用プロンプト形式、API キー）は作らない。§0.1 の暫定前提による。

## 1. 演習スコープ制約の再定義

### 1.1 何を制約すべきか

PRD-06「最大2関数」が守ろうとしていたものは、`prd-001.md:286` のリスク表に1箇所だけ書かれている。

> | 扱う概念が多く認知負荷が高い | 手を動かすだけで判断過程が残らない | コード編集を行うモジュールでは編集範囲を最大2関数に限定し、最終演習では新しい概念を増やさない |

狙いは2つである。**(A) 認知負荷の管理**と、**(B) 判断過程を残すこと**である。「2関数」はこの2つの代理指標にすぎず、しかも次の4点で不正確である。

第一に、**代理指標が (A) を測れていない。** 2関数であっても、Zod の brand・transform・`schemaResult` を同時に扱えば判断は3つ以上になる（現行 S2 がまさにこれである）。逆に、同じ規約の遷移関数4本は判断1つで済む。

第二に、**代理指標が (B) を全く測っていない。** 関数の個数は、判断が記録に残ったかどうかについて何の情報も持たない。現行 exercise:04 は「2関数以内」を満たしているが、答えがテストに逐語で書かれているため判断が一切残らない。

第三に、**エージェント前提では (A) の意味が変わる。** 打鍵量は制約でなくなり、残る負荷は「読む差分の量」と「下す判断の数」になる。

第四に、**エージェント前提では (B) の重要度が上がる。** 差分を生成させる以上、**言語化とレビューが参加者の仕事の本体**になるからである。

したがって、(A) は「判断の数」と「読む差分の量」で直接測り、(B) は「成果物を必ず残す」ことで直接強制する。

### 1.2 新しい制約

> **演習スコープ制約（第2版）**
>
> 1. **1演習 = 1モジュール。** 参加者が編集するファイルは `exerciseModule.dir` が指す1ディレクトリの中に閉じる。モジュール外は配布・読むのみとする。
> 2. **1演習 = 最大4ステップ。** ステップは「1つの宣言（関数・型・schema）を完成させる」粒度である。エージェント非保持者向けの解答提示単位でもある（§1.4）。
> 3. **1演習 = 最大3判断点。** 判断点は `{ 守る不変条件, 型でどう表すか, 型で守れない残り }` の3つ組として catalog に宣言する（PRD-04 / PRD-05 に直結する）。
> 4. **差分予算 = 最大5ファイル・実効80行。** 実効行はコメントと空行を除く。解答スナップショット間の差分から機械的に測る。
> 5. **ADV 三点セットを必ず残す。** 各演習は「**言語化**（不変条件を1文）→ **委譲**（依頼文に落として差分を作る）→ **検証**（型・テストに照らして差分をレビューする）」の3手順を含み、3つの成果物が残る。

#### 各条項が何を担保するか

**条項1（1モジュール）** は、「今どこを見ればよいか」を1ディレクトリに固定する。現行の「8ファイル新規＋7ファイル改修」のような散らばりを構造的に禁じるためである。認知負荷の主因は編集量ではなく探索範囲であり、これは `prd-001.md:229`「次に何を観察し、何を実行し、何を確認するかを各段階で一つに絞る」と同じ思想である。

**条項2（4ステップ）** は、進捗を4分割し、途中で止まっても「ここまで」が明確になるようにする。PRD-12 の代替進行の切り替え点にもなる。根拠は `prd-001.md:278`「進行が遅れた場合、実装を解答済み例の読解へ切り替えられるようにする」である。

**条項3（3判断点）** は、(A) 認知負荷を**判断の数**で直接測る。「2関数」という代理指標を捨てて本体を測るということである。根拠は `prd-001.md:286` の狙い (A) である。

**条項4（差分予算）** は、読む量の上限を定める。エージェントが生成した差分を12〜17分でレビューできる大きさに保つためである。数字の根拠は後述する。

**条項5（ADV）** は、(B) 判断過程を残すことを**成果物の存在**によって強制する。根拠は `prd-001.md:152` / `:190` / `:202` である。

#### 「80行」の根拠（推定であることを明記する）

- 現行 exercise:01 は 114 行を白紙から30分で書かせて完走しない（実測ではなく行数の実カウントである）。
- 初版の「2関数」は 20〜30 行相当と見積もっていた。
- 新スコープはその中間より上を採る。エージェント保持者は1依頼で生成して差分を読む。非保持者は4ステップ×平均20行を、ステップごとの解答提示に支えられて打つ。
- **この 80 という値は実施実績のない推定値である。** リハーサル（§10 の P4）で較正する。ただし「2」と違い、(a) 測定可能であり、(b) 何を測っているかが明示されており、(c) 較正手順が決まっている点で性質が異なる。

#### 捨てた案

関数の個数を 2 から 5 へ緩める案も検討したが、数字の根拠がないという指摘の本体が残り、何を測っているかも変わらないため採らない。

「行数だけ」で制約する案も検討したが、判断過程を残す狙い (B) を全く担保せず、現行 exercise:04 と同じ失敗を許すため採らない。

「時間だけ」で制約する（12分で終わる範囲とする）案も検討したが、教材制作時に検証できず、CI でも測れないため採らない。

モジュール外の編集も許して差分予算だけで縛る案も検討したが、探索範囲が広がって TA が「どこを見ているか」を把握できなくなり、5人班×1 TA の運用と両立しないため採らない。

### 1.3 ADV ループ（言語化 → 委譲 → 検証）

全演習セッション共通の3フェーズである。時間内訳の `exercise` 枠はこの3つに分割される。

**言語化（2分）** では、参加者は事故から守るべき不変条件を1文で書き、班内で読み合わせる。エージェントの有無で内容は変わらない。成果物は手元のシートに書かれた1文である。

**委譲（8〜10分）** では、参加者は不変条件を依頼文に落とし、モジュールに差分を作る。エージェントがある場合は依頼文をエージェントへ渡して差分を得る。ない場合はステップ単位で自分で書き、詰まったらそのステップの解答を開く。成果物は依頼文、またはステップごとの実装メモである。

**検証（4〜5分）** では、参加者は `pnpm exercise:0N` を緑にし、差分を型とテストに照らして読み、「型で守れなかった残り」を1つ挙げる。エージェントがある場合は生成差分のレビュー、ない場合は自分の差分のセルフレビューになる。成果物はレビュー観点1〜2行である。

#### 依頼文の骨子は穴あきで配布する

サイトの `#refactor` 章に次の形を置く。

```
examples/session-0N/src/<module>/ の中だけを変更してください。
守る不変条件: ____________（← 言語化フェーズで自分が書いた1文）
検証: pnpm exercise:0N が緑になること。
禁止: as によるキャスト。モジュール外のファイルの変更。
```

**穴を埋めるのは参加者である。** 依頼文を完成形で配ると、現行 exercise:04（答えが `exercises/agent-review.test.ts:7-16` に逐語で書かれていた）と同じ失敗を再生産する。埋める1文が、その回で参加者が下した判断そのものになる。

#### 検証フェーズのレビュー観点

全セッション共通の4点である。セッション固有の観点は各セッションに1つ足す。

1. `as` によるキャストが入っていないか。
2. モジュール外のファイルが変更されていないか（`git diff --stat` で見る）。
3. 不変条件が**型**で守られているか、それとも実行時の `if` で守られているか。
4. 型で守れなかった残りは何か（PRD-05）。

### 1.4 エージェント非保持者向けフォールバック

**設計方針**として、解答は**次スナップショットの `src` から機械的に切り出す**。別ファイルに解答スニペットを二重管理する案も検討したが、同期コストが生じ、`.md` や対象外の `.ts` が typecheck を外れる欠陥 #6 の再発を招くため採らない。

### 2.1 当日の到達点（`examples/session-05` スナップショット）

### 2.3 `ResultAsync`（#15）を演習へ移す判断

**結論は、移すことである。** S4 の第3ステップとして、配布済みの同期 `Result` パイプラインを非同期へ持ち上げる。

**価値**が高い。`examples/final` の30ユースケースはすべて `ResultAsync` である。ここを渡らないと「final は別世界」で終わる。お土産の4差分のうち最大の差分がこれであった。

**判断の質**も高い。判断点は「どこまでが純粋で、どこから非同期か」と「保存は `andThen` か `andThrough` か」の2つであり、どちらも**型では自動的に決まらない設計判断**である。ADV ループの題材として質が高い。

**打鍵量**は小さい。neverthrow の `andThen` は同期 `Result` も `ResultAsync` も受けるため、パイプラインの形はほぼ変わらない。差分は型別名の変更、`ok`/`err` から `okAsync`/`errAsync` への変更、port 戻り型の変更、`andThrough` の導入であり、**推定15〜25行**である（実測ではない）。

**エージェント適性**も高い。「このパイプラインを `ResultAsync` に持ち上げて。保存は値を汚さずに通して」は1依頼で通る。参加者の仕事はレビュー側に寄る。

**典型的な罠**が2つあり、これがそのままレビュー観点になる。(a) `andThrough` を `andThen` にすると `store` の戻り値がパイプラインを乗っ取り、`event` が消える。(b) Promise を返す関数を `map` に渡すと `Result<Promise<...>>` になる。**どちらも型が教えてくれるが、エラーメッセージを読めないと詰まる。**

**コスト**は S4 が30分から35分になることである。原資は §2.4 に示す。

**リスク**については、S4 の最終ステップに置いたため、押した場合は講師デモ3分へ切り替えて5分を回収できる（分離可能な設計にしてある）。

**`ResultAsync` を入れても入れないもの**がある。`ResultAsync.fromPromise` による例外の閉じ込め（#18）と、`mapErr` によるエラー写像（#17）は「読む」に留める。判断点3の上限を守るためである。

### 3.2 セッションごとの時間内訳と検算

各セッションは brief（事故・RED）、teach（解説）、exercise（ADV）、debrief（GREEN・共有）の4つに分かれる。

**S0 引き継ぎ**は brief 7分、teach 5分、exercise 0分、debrief 3分で、7+5+0+3 = 15分 ✓。
**S1 状態を型にする**は brief 4分、teach 7分、exercise 15分、debrief 4分で、4+7+15+4 = 30分 ✓。
**S2 値を型にする**は brief 4分、teach 8分、exercise 14分、debrief 4分で、4+8+14+4 = 30分 ✓。
**S3 失敗を値にする**は brief 5分、teach 8分、exercise 17分、debrief 5分で、5+8+17+5 = 35分 ✓。
**S4 副作用を外に出す**は brief 5分、teach 8分、exercise 17分、debrief 5分で、5+8+17+5 = 35分 ✓。
**Final ツアー**は brief 0分、teach 4分、exercise 0分、debrief 1分で、0+4+0+1 = 5分 ✓。

列ごとの合計は brief 25分、teach 40分、exercise 63分、debrief 22分であり、25+40+63+22 = **150分** ✓ である。

ADV 3フェーズの内訳も検算する。S1 は言語化2分・委譲9分・検証4分で 2+9+4 = 15分 ✓。S2 は言語化2分・委譲8分・検証4分で 2+8+4 = 14分 ✓。S3 は言語化2分・委譲10分・検証5分で 2+10+5 = 17分 ✓。S4 は言語化2分・委譲10分・検証5分で 2+10+5 = 17分 ✓。フェーズごとの合計は言語化8分、委譲37分、検証18分であり、8+37+18 = **63分** ✓ で exercise 枠の合計と一致する。

`timeBreakdown` は catalog に持ち、`brief + teach + exercise + debrief === durationMinutes` と `sessions の durationMinutes 合計 === 150` をテストで検算する（§6.3）。ADV 内訳も `adv: { articulate, delegate, verify }` として持ち、`articulate + delegate + verify === exercise` を検算する。

### 3.3 初版（6回 30/30/25/30/20/15）および第2版初稿から変えた理由

**セッション本編を6本から5本（うち演習ありは4本）へ減らした。** 1演習は「RED を読む → 言語化 → 委譲 → 検証 → なぜそう書くか」で最低30分かかる。6本では固定枠30分と合わせて180分を超える。

**Session 00 を30分から20分、さらに15分へ減らした。** 現行 session-00 と session-01 の src 差分は実質1行である（`diff` で確認した）。第2版ではさらに、不変条件の言語化が S1 の ADV 内に移ったため、S0 の役割が読解に純化した。

**「エージェントレビュー」を独立セッションとしては持たない。** 理由は §1.5 に書いた。これは**廃止ではなく全セッションへの溶かし込み**であり、初版の「廃止」判断は第2版で覆した。

**「ミニ総合演習」を独立セッションとして廃止した。** 15分で「既習5技法の統合＋未知のイベント設計＋`Result` の畳み込み」は不可能であり、現行ガイド自身が「押したら講師の worked example に切り替え」として完走を前提していない。さらに解答が final に存在しない。統合の体験は、S4 が S1〜S3 の成果物の上に積み上がることで代替する。

**Final を10分から5分へ減らした。** 理由は §2.4 に書いた。

**休憩を85分地点（16:25）に1回だけ置いた。** S1・S2 が連続する前半と、S3・S4 が連続する後半に分かれ、ほぼ中央で切れるためである。

## 4. 各セッションの設計

各セッションは共通の5章骨格を持つ（§6.2）。以下、章ごとの中身を定義する。差分行数は**すべて推定**であり、実装フェーズで実測して catalog の予算値と突き合わせる。

### 4.0 Session 00 — 引き継ぎ（15分・演習なし）

**要求**は、先人の獣医が診療の合間にバイブコーディングで作ったシステムを、新任エンジニアであるあなたが引き継ぐことである。

**事故**は2件で、事故報告として読む（テストは実行しない）。1件目は**二重請求**である。会計済み（`paid`）の来院が、`updateStatus(id, "in-examination")` で診察中へ戻され、会計が二度走った。2件目は **PII 流出**である。`logger.info("appointment booked", appointment)` が、飼い主の氏名・メール・電話番号を含む予約オブジェクトをそのまま JSON 化してログに残していた。

> 事故を再現する赤いテストは、**それを直す回の冒頭で走らせる**。Session 00 では事故報告（業務側の記述）とコードの対応だけを見る。2026-08-08 の「Session 00 で赤いテストを見せない」判断はこの形で維持する。

**配布する「ひどいコード」**は `examples/session-00/src/legacy/appointment.ts`（現行の `examples/session-00/src/appointment.ts` を移設したもの）である。素朴さの中身は次の5点である。

1. `status: string` になっている。業務で使う状態の種類も、許可される遷移も型から読めない。
2. `LegacyStatusExtra` の optional 6項目がある。どの状態で何が必須かが型に表れず、`cancelReason` なしでキャンセルできる。
3. ID が全部 `string` である。`petId` を渡すべき所へ `ownerId` を渡してもコンパイルが通る。
4. `throw new Error(...)` を使っている。呼び出し側が扱うべき失敗の種類が関数の型から判断できない。
5. `logger.info(msg, appointment)` を呼んでいる。ログに出してよい情報の境界が値にも型にも表れない。

**参加者の作業はない。** 読むだけである。

**エージェント有無の扱い**については、冒頭固定枠で有無を申告してもらい、班内で**混ぜて**座らせる（有りと無しが同席する）。理由は、検証フェーズの班内共有で「エージェントが書いた差分」と「自分で書いた差分」を比較でき、レビュー観点が具体化するためである。TA は班ごとの内訳を把握する。

**時間内訳**は、業務とアプリケーションの説明が7分（brief）、ガイド付き Code Explorer で5箇所を各自確認するのが5分（teach）、班内で「一番怖いのはどれか」を共有するのが3分（debrief）で、7+5+3 = **15分** ✓ である。

### 4.1 Session 01 — 状態を型にする（30分）

**要求**は、会計済み・キャンセル済みの来院をあとから診察中へ戻せないようにしたい、キャンセルには必ず理由を残したい、というものである。

**事故**は事故報告 #1（二重請求）である。`pnpm exercise:01` が赤で始まる。

**演習モジュール**は `examples/session-01/src/domain/appointment/` である。中身は3ファイルからなる。`appointment.ts` は5状態の判別共用体（`Scheduled` / `CheckedIn` / `InExamination` / `Paid` / `Canceled`）と `CancellationReason` を持ち、**配布済みで変更しない**。`transitions.ts` は `checkIn` / `startExamination` / `recordPayment` / `cancel` の4本を持ち、素朴な実装で配布して演習対象とする。`statusLabel.ts` は `toStatusLabel` を持ち、`switch` に `default: return "不明"` がある状態で配布して演習対象とする。

```ts
// transitions.ts の配布される素朴版（動くが守られていない）
export const startExamination = (
  appointment: Appointment,
  veterinarianId: string,
): Appointment => {
  if (appointment.kind === "Paid") throw new Error("cannot start");
  return {
    ...appointment,
    kind: "InExamination",
    veterinarianId,
    examinationStartedAt: new Date().toISOString(),
  } as Appointment; // ← as で押し通している
};
```

なぜ事故るかというと、遷移の可否を**実行時の `if` 1本**でしか守っておらず、`Canceled` からの遷移は素通りするからである。戻り値を `as Appointment` でキャストしているため、必須項目が欠けていてもコンパイルが通る。`toStatusLabel` の `default` は、状態が増えても何も言わない。

**ステップは4件である。** まずステップ1で「会計済みの来院は診察を開始できない」を実現する。`startExamination` の第1引数を `CheckedIn` に絞り、`as Appointment` を `as const satisfies InExamination` へ変える（推定10行）。次にステップ2で「キャンセルには必ず理由が残る」を実現する。`cancel` の第1引数を `Scheduled | CheckedIn` に絞り、`CancellationReason` を必須引数にする（推定12行）。続くステップ3では「残る2本の遷移も同じ規約に揃える」ため、`checkIn` と `recordPayment` を同じ形へ変える。ここが**エージェントに「同じ規約で残り2本」と依頼する練習**になる（推定20行）。最後にステップ4で「状態を1つ足したらコンパイルエラーになる」ようにする。`toStatusLabel` の `default` を捨て、`assertNever` で網羅にする（推定8行）。

**差分予算**は3ファイル・50行である（上限は5ファイル・80行）。ステップの推定行の合計は 10 + 12 + 20 + 8 = 50行であり、予算と一致する。

**判断点は3件である。** 判断点1は「終端状態から戻らない」を守る。型では、逆行遷移の関数を**作らない**ことと、引数型で遷移元を縛ることで表す。型で守れない残りは、呼び出し側が `as` で state を捏造すれば通ってしまうことであり、だからこそ `as` を禁止する運用が要る。判断点2は「状態ごとの必須項目が欠けない」を守る。型では、状態ごとに別の型を持つ判別共用体と `as const satisfies` で表す。型で守れない残りは、外部 JSON からの復元であり、これは S2 の境界で別途守る必要がある。判断点3は「状態が増えたら全ての分岐が見直される」を守る。型では `assertNever` による網羅性検査で表す。型で守れない残りは、`default` を書き戻せば黙ってしまうことであり、レビュー観点として残す。

**到達する型とパターン**は、判別共用体、遷移元を引数型で縛る純粋関数、`as const satisfies`、逆行遷移の関数を作らない設計、`assertNever` による網羅性検査である。

**`examples/final` の対応ファイル**は `src/domain/appointment/appointment.ts` と `src/domain/shared/assertNever.ts` である。

**GREEN の判定**は `pnpm exercise:01` が緑になることである。加えて `exercises/state-modeling.test.ts` の `// @ts-expect-error` 節が、「`Paid` を `startExamination` に渡すとコンパイルエラー」と「状態を1つ足すと `toStatusLabel` がコンパイルエラー」を型レベルで固定する。これは `exercises/**` を tsconfig の include に入れたことで初めて機能する（欠陥 #6）。

**エージェント非保持者のフォールバック**として、ステップ1から4それぞれの解答宣言を `examples/session-02/src/domain/appointment/` から切り出して `<details>` に置く。ステップ3は「1と2と同じ形」なので、詰まる場合はステップ1の解答を見て写せる構造にしてある。

**時間内訳**は brief 4分（事故報告の再確認と RED 実行）、teach 7分（判別共用体・`as const satisfies`・`assertNever`）、exercise 15分（言語化2分・委譲9分・検証4分）、debrief 4分（GREEN・解答解説・班内共有）で、4+7+15+4 = **30分** ✓ である。

### 4.2 Session 02 — 値を型にする（30分）

**要求**は、外部の検査ラボから届く JSON をカルテに取り込みたい、フォロー電話のために飼い主の連絡先を扱いたい、というものである。

**事故**は2件ある。1件目は**他人のカルテに検査結果が付いた**というものである。ラボの JSON の識別子を `petId` として受け取る箇所へ `ownerId` を渡していた。全部 `string` なのでコンパイルは通っていた。2件目は **PII 流出**（事故報告 #2）であり、`logger.info` に渡した値に電話番号とメールが平文で含まれていた。

**演習モジュール**は `examples/session-02/src/boundary/` である。`examResult.ts` は検査結果の取り込みを担い、素朴版で配布して演習対象とする。`ownerContact.ts` は飼い主連絡先の取り込みを担い、同じく素朴版で配布して演習対象とする。`boundary.test-types.ts` は ID 取り違えを固定する型テストであり、空ファイルで配布してステップ4の演習対象とする。

モジュール外に**配布済みで変更しない**ものとして、`src/shared/sensitive.ts`（`[Symbol.for("nodejs.util.inspect.custom")]` 付き）、`src/shared/schemaResult.ts`、`src/domain/ids/*.ts`（branded ID 5種。うち1つは完成例として `AppointmentId` を置く）がある。

```ts
// examples/session-02/src/boundary/examResult.ts（配布される素朴版）
export const parseExamResult = (raw: any): ExamResult => ({
  examId: raw.examId,
  petId: raw.petId,
  items: raw.items ?? [],
  needsFollowUp: !!raw.needsFollowUp,
});
```

```ts
// examples/session-02/src/boundary/ownerContact.ts（配布される素朴版）
export const parseOwnerContact = (raw: any): OwnerContact => ({
  ownerId: raw.ownerId,
  name: raw.name,
  email: raw.email,   // 素の string のまま
  phone: raw.phone,   // 素の string のまま
});
```

なぜ事故るかというと、`any` を通しているので外部 JSON の形が変わっても気づかず、ID が `string` なので取り違えを型が止められず、連絡先が素の `string` なので `JSON.stringify` すればどこにでも漏れるからである。

**ステップは4件である。** まずステップ1で「形の違う JSON はドメイン型にならない」ようにする。`parseExamResult` の `raw: any` を `raw: unknown` に変え、`ExamResultSchema` を組み、`schemaResult(...)` を返す（推定18行）。次にステップ2で「電話番号とメールはログに出ない」ようにする。`parseOwnerContact` の `email` と `phone` の schema に `.brand<...>().transform(Sensitive.of)` を足し、`schemaResult` を通す（推定16行）。続くステップ3では「手書きの型と schema がずれない」ようにする。`ExamResult` と `OwnerContact` の手書き型を捨て、`z.infer<typeof Schema>` から導く（推定8行）。最後にステップ4で「ID の取り違えはコンパイルで止まる」ようにする。`boundary.test-types.ts` に `@ts-expect-error` の型テストを2本書く（`ownerId` を `petId` の位置に渡す等。推定10行）。

**差分予算**は3ファイル・52行である（上限は5ファイル・80行）。ステップの推定行の合計は 18 + 16 + 8 + 10 = 52行であり、予算と一致する。

**判断点は3件である。** 判断点1は「外部入力は境界を1箇所しか通れない」を守る。型では、`unknown` 引数と schema と smart constructor（parse, don't validate）で表す。型で守れない残りは、境界を迂回して直接オブジェクトリテラルを作る経路であり、これは型では塞げないためモジュール境界の運用ルールが要る。判断点2は「種類の違う ID は入れ違わない」を守る。型では用途別 branded type で表す。型で守れない残りは、DB 上は同じ `TEXT` であることであり、永続化からの復元時に再度 parse が要る（final の #28 へ繋がる）。判断点3は「PII は既定でマスクされ、剥がす場所が1箇所」を守る。型では `Sensitive<T>` と `unwrap()` の呼び出し箇所を数えることで表す。型で守れない残りは、`unwrap()` した後の値が普通の `string` であることであり、剥がした先での取り扱いは型では守れない。

**到達する型とパターン**は、Zod `.brand<...>()` による nominal typing、`schema` + `parse` のコンパニオンオブジェクト（smart constructor）、Standard Schema から `Result` へのブリッジ、`Sensitive<T>`、parse don't validate、`@ts-expect-error` による型テストである。

**`examples/final` の対応ファイル**は `src/domain/shared/schemaResult.ts`、`src/domain/shared/sensitive.ts`、`src/domain/appointment/appointmentId.ts`、`src/domain/owner/ownerPhone.ts`、`src/domain/examResult/examResult.ts` である。

### 4.3 Session 03 — 失敗を値にする（35分）

**要求**は、診察開始に失敗したときに画面へ理由を出したい、というものである。

**事故**は、予約が見つからないときに投げていた例外のメッセージ文言を変えたところ、UI が 404 ではなく 500 を返すようになり、受付が原因を追えなくなったというものである。

**演習モジュール**は `examples/session-03/src/useCase/` である。`errors.ts` は `StartExaminationError` の union と `ensureAppointmentFound` / `ensureCheckedIn` を持ち、union 定義は配布して2関数は `// TODO` にする。`startExamination.ts` はユースケース本体であり、`try/catch` の素朴版で配布して演習対象とする。`startExamination.fake.test.ts` はフェイク port による失敗経路テストであり、1本だけ配布して2本目を参加者が書く（ステップ4）。

なぜ事故るかというと、失敗の種類が関数の型に現れないため、呼び出し側はメッセージ文字列でしか分岐できないからである。文言を変えると分岐が静かに壊れ、コンパイラは何も言わない。

**判断点は3件である。** 判断点1は「予期できる失敗は戻り値に現れる」を守る。型では `Result<T, E>` と `kind` を持つ plain object の union で表す。型で守れない残りは、ネットワーク断など予期できない失敗が依然として例外であることであり、「予期できる／できない」の線引きは人が決める。判断点2は「呼び出し側は文言でなく `kind` で分岐する」を守る。型ではエラー union と呼び出し側の `assertNever` で表す。型で守れない残りは、エラーメッセージの文言そのものが型の外にあることであり、i18n や UI 文言はレビュー対象になる。判断点3は「失敗経路では副作用が起きない」を守る。これは型では守れず、**テストで守る**（ステップ4）。ここが「型で守れない残り」の代表例であり、だからこそ検証可能なチェックリスト（テスト）が要る。

### 4.4 Session 04 — 副作用を外に出す（35分）

**要求**は、誰がいつ診察を開始したかをあとから追えるようにしたい、というものである。保存は外部ストレージへの非同期呼び出しになる。

**事故**は2件ある。1件目は**テストが日によって落ちる**というものである。`new Date().toISOString()` と `crypto.randomUUID()` がユースケースの中にあり、期待値を固定できなくなっていた。2件目は**記録のない状態変更**である。保存が「状態を保存」と「記録を追加」の2回に分かれており、間で失敗すると状態だけ変わって記録が残らない予約が生まれた（dual-write）。

**演習モジュール**は `examples/session-04/src/useCase/` である。`startExamination.ts` はユースケース本体であり、S3 の解答（同期 `Result`）に非決定性と dual-write を加えた素朴版で配布して演習対象とする。`dependencies.ts` は `Dependencies` の型であり、素朴版（`store` と `eventLog` の2つ）で配布して演習対象とする。`startExamination.fake.test.ts` は決定性と原子性を固定するテストであり、1本配布して1本を参加者が書く（ステップ4）。

モジュール外（**配布済みで変更しない**）には、`src/domain/aggregate/{clock,eventIdGenerator,eventContext}.ts`、`src/domain/appointment/examinationStarted.ts`（5フィールドの具体イベント）、`src/adaptor/inMemoryAppointmentStore.ts`（非同期であり `ResultAsync.fromPromise` を1箇所含む。#18 を読む素材）、`src/main.ts`（合成ルート。#21 を読む素材）がある。

```ts
// examples/session-04/src/useCase/startExamination.ts（配布される素朴版・抜粋）
    const event = {
      kind: "ExaminationStarted",
      eventId: crypto.randomUUID(),          // ← 非決定性がユースケースの中
      occurredAt: new Date().toISOString(),  // ← 同上
      appointmentId: next.appointmentId,
      veterinarianId: input.veterinarianId,
    };
    deps.store.save(next);        // ① 状態を保存
    deps.eventLog.push(event);    // ② 記録を追加。ここで落ちると①だけが残る
    return ok(next);
```

なぜ事故るかというと、非決定性がドメイン側にあるためテストが決定的にならず、書き込みが2回に分かれているため片方だけ成功した中間状態が観測できてしまうからである。

**ステップは4件である。** まずステップ1で「テストが日によって落ちない」ようにする。`Dependencies` に `clock` と `eventIdGenerator` を足し、`EventContext` を組んで純粋な `Appointment.startExamination(context)(checkedIn, veterinarianId)` を呼ぶ（推定18行）。次にステップ2で「記録のない状態変更が起きない」ようにする。`Dependencies` の `store` と `eventLog` を1つの `ExaminationStartedStore` に畳み、保存を `store.store(event)` 1回にする（推定12行）。続くステップ3では「保存が非同期でもパイプラインが1本のまま」であるようにする。戻り値を `ResultAsync<InExamination, StartExaminationError>` へ持ち上げ、保存を **`andThrough`** で通す（推定20行）。最後にステップ4で「保存が失敗したら何も残らないことを固定する」。保存が失敗するフェイク store と固定 `clock` を渡すテストを1本書く（推定15行）。

**差分予算**は3ファイル・65行である（上限は5ファイル・80行）。ステップの推定行の合計は 18 + 12 + 20 + 15 = 65行であり、予算と一致する。5本中で最も厚い。

**判断点は3件である。** 判断点1は「ドメイン関数は決定的である」を守る。型では、非決定性を1メソッド port（`Clock` / `EventIdGenerator`）として引数に出すことで表す。型で守れない残りは、port を注入し忘れて直接 `Date` を呼ぶ経路であり、これは型では塞げないため lint やレビュー観点になる。判断点2は「状態と記録は同時に残るか、どちらも残らない」を守る。型では、書き込み口を `store(event)` の1つに絞り、`event.aggregateState` を同梱することで表す。型で守れない残りは、in-memory では「同時」を実装で保証しているだけであることであり、本当の原子性は transaction が要る（final の #25 / #26 へ繋がる）。判断点3は「保存は値を汚さずに通る」を守る。型では `andThrough`（`andThen` ではない）で表す。型で守れない残りは、`andThrough` を `andThen` に変えても型が通る場合がある（戻り値型が一致すると気づけない）ことであり、**レビュー観点として明示する**。

**到達する型とパターン**は、1メソッド port、非決定性の注入、`(context) => (state) => Event` のカリー化、最小の型付きドメインイベント、dual-write の解消、**`ResultAsync` と `andThrough`** である。合成ルート（#21）、`ResultAsync.fromPromise` による例外の閉じ込め（#18）、`mapErr` によるエラー写像（#17）は配布コード中で読む。

**`examples/final` の対応ファイル**は `src/domain/aggregate/clock.ts`、`src/domain/aggregate/eventIdGenerator.ts`、`src/domain/aggregate/eventContext.ts`、`src/domain/aggregate/aggregateStore.ts`、`src/domain/appointment/appointmentStores.ts`、`src/useCase/startExaminationUseCase.ts`（**当日の成果物とほぼ同じ形になる**）、`src/app.ts` である。

**GREEN の判定**は `pnpm exercise:04` が緑になることである。判定条件は、(a) 偽 `clock` と偽 `eventIdGenerator` を渡すと結果が完全に決定的であること、(b) 保存を失敗させるフェイクを渡すと状態も記録も残らないこと、(c) 保存成功時の戻り値が `store` の戻り値ではなく `event.aggregateState` であること（`andThrough` を `andThen` にすると落ちる）である。

**エージェント非保持者のフォールバック**として、ステップ1から3の解答宣言を `examples/session-05/src/useCase/` から切り出す。ステップ3（`ResultAsync` 化）は**行数は少ないが読み替えが多い**ため、`<details>` に「変更前 → 変更後」の並置を置く（このセッションだけ提示形式を変える）。

現行の3分割と、`vitest.config.ts`（`test/**` のみ）／ `vitest.exercises.config.ts`（`exercises/**` のみ）の2ファイル構成は**そのまま維持する**。理由は3つある。

- `apps/docs` の `run-command.ts` が、`exercises/**` と `test/**` でコマンドを出し分ける実装に依存している。

変更するのは中身の規約だけである。

**`src/`** は、現行では演習で参加者が**新規作成**する（つまり存在しない）が、新構成では演習モジュールのファイルは**必ず存在**し、素朴な実装または `// TODO` の穴が入っている。

**`exercises/`** は、現行では未存在ファイルへの dynamic import であり赤の理由がモジュール解決エラーだが、新構成では実在ファイルを static import し、赤の理由が assertion 失敗になる。加えて**ステップ単位で `describe` を分け、どこまで進んだかが赤の数で読める**ようにする。

**`test/`** は、現行ではセットアップ確認のみだが、新構成ではセットアップ確認に加えて**前セッションの演習テストを回帰として持ち越す**。

**`tsconfig.json` の include** は、現行では `src` / `test` / `vitest.config.ts` だが、新構成では `exercises/**/*.ts` と `vitest.exercises.config.ts` を追加する。

**`package.json` の script** は、現行では `build` / `typecheck` / `test` / `exercise` だが、新構成では `build` を削除する（`tsc --noEmit` の別名でしかなく、final の `build` と意味が違うためである）。

**依存**は、現行では演習に必要な依存が入っていない回があるが、新構成では S2 以降に `zod`、**S3 以降に `neverthrow`**、S2 以降に `@types/node`（`util.inspect` 検証のため）を宣言する。

### 5.3 セッション間の連鎖の担保（初版から維持）

**規約**は、`session-0N/exercises/**` の期待値が `session-0(N+1)/src/**` に対して緑になることである。

**担保方法**は、`session-0(N+1)/test/regression/` に `session-0N` の演習テストを回帰テストとして**そのまま持ち越す**ことである。これにより次の3つが得られる。

- 「session-03 → 04 の `safeParse` → `parse` 隠れ改修」（調査 #7）のような差分は、持ち越した回帰テストが落ちるので混入できない。

### 5.4 差分予算テスト（第2版で新設）

新スコープ制約の条項4を機械的に強制する。実体は `apps/docs/src/test/examples/exercise-budget.test.ts`（純ロジックであり、レンダリングしない）である。

各演習セッション `N` について、次を行う。

1. `examples/session-0N/src/<module.dir>/` と `examples/session-0(N+1)/src/<module.dir>/` を読む。
2. ファイル単位で行を比較し、**追加＋変更行数**（コメント行・空行を除く）を数える。
3. 変更ファイル数が `module.fileBudget`（5以下）以下であり、実効行数が `module.lineBudget`（80以下）以下であることをアサートする。
4. `steps[].targets` の全ファイルが `module.dir` 配下にあることをアサートする。
5. `steps.length` が4以下、`decisions.length` が3以下であることをアサートする。

**この方式には次の限界があり、明記しておく。**

- 行単位の比較であり、TypeScript の構文は解釈しない。整形の違いを差分として数える。**正確な値ではなく予算の上限監視である**ことを前提にする。
- `module.dir` の外に配布される「次セッション用の新規ファイル」は予算に入らない。これは意図した設計（演習スコープはモジュール内に閉じるという条項1そのもの）だが、「モジュール外に本質を逃がす」抜け道でもある。**§5.3 の回帰テスト持ち越しが、この抜け道で連鎖が壊れることを防ぐ**という二重の守りになっている。
- 比較は「素朴版 → 解答版」を測っており、参加者が実際に打つ量とは一致しない（エージェント使用時はさらに乖離する）。**測っているのは「読む差分の量」である。**

### 5.5 演習の RED を「情報のある赤」にする

現行の RED はモジュール解決エラーであり、`expect` が何を要求しているかはテスト本文を読まないと分からない。新構成では演習対象ファイルが必ず存在するので、赤は必ず assertion 失敗になる。加えて演習テストは次を守る。

- **`describe` をステップに1対1で対応させる。** ステップ1が緑になればブロック1が緑になる。TA は「今どのステップか」を赤の数で把握できる。
- 各 `it` の名前を業務の言葉で書く（例: 「会計済みの来院は診察を開始できない」）。
- 型レベルの禁止は `// @ts-expect-error` で表明し、`pnpm typecheck` で検証する（`exercises/**` を include に入れたことで初めて機能する）。
- 副作用が**起きていないこと**を明示的にテスト名に書く（例: 「失敗時は store へ書かない」）。`examples/final` のテスト命名規約を踏襲する。

## 6. `apps/docs` の再構成

### 6.1 content collection を導入するか — 導入しない（初版から維持）

**判断は、導入しないことである。** ユーザーが挙げた痛み（セッション数を変えるとページを手で足す）は、content collection ではなく **catalog 駆動の動的ルート**で解く。理由は4つある。

第一に、2026-08-06 に「Astro Content Collections、MDX、外部 CMS による本文構造化」を明示的に対象外と決定済みであり、その理由（各セッションを教材として改善する自由度を優先し、本文を先回りして共通スキーマへ閉じ込めない）は今も有効である。

第二に、教材本文は Markdown/MDX の表現力を超えている。吹き出し会話（`.onboarding-story`）、来院タイムライン（`.visit-timeline`）、ガイド付き Monaco、WebContainer playground は、いずれも `.astro` のテンプレートと island で書かれている。

第三に、content collection のスキーマ定義には `zod` が要るが、`apps/docs` の依存は現在 `@astrojs/react` / `@webcontainer/api` / `astro` / `monaco-editor` / `react` / `react-dom` の6つであり zod を含まない。残り18日で依存とビルドの検証を増やす利得がない。

第四に、ページ数の手作業は動的ルートで消える。本文の置き場所を変える必要はない。

**代わりに採る案（フェーズ2）**は次の通りである。`src/pages/sessions/[slug].astro` を1枚だけ置き、`getStaticPaths` を `catalog.ts` から生成する。本文は `src/sessions/content/<slug>.astro` に置き、`import.meta.glob("../../sessions/content/*.astro", { eager: true })` で対応コンポーネントを解決して描画する。これで catalog が唯一の真実になり、`site-contract.test.ts` の「ページ glob と catalog が一致すること」というテスト自体が不要になる。

**リスクと退避**についても書いておく。Astro 4 で `.astro` を `import.meta.glob` の eager import で受け取り動的コンポーネントとして描画する経路は、本設計時点で実機検証していない（推測を含む）。実装フェーズの最初に技術検証を行い、通らなければ**フェーズ1の形（セッションごとに1枚の `.astro`、計6枚）で確定する**。フェーズ1でも catalog スキーマ刷新・章骨格の構造化・テストの作り直しはすべて成立するので、当日までのクリティカルパスには乗せない。

### 6.2 セッションページのテンプレート／セクション骨格

全セッション共通の5章とする。`SessionLayout` が章定義を受け取り、**TOC を自動生成する**（現行の手書き `<ol slot="toc">` を廃止する）。

**第1章 `#incident`「何が起きたか」** には、要求、事故、**守る不変条件（`decisions[].invariant` から生成する）**、今回のミッションを置く。全 kind で必須である。

**第2章 `#legacy`「配布コードを読む」** では、素朴な実装のどこが素朴かを `SessionCodeOverview`（読み取り専用ガイド）で指す。**演習モジュールの範囲を明示する。** 全 kind で必須である。

**第3章 `#red`「失敗を再現する」** には、`CommandBlock phase="red"`、**演習モジュールと4ステップの表（`exerciseModule` と `steps` から生成する）**、先に読むファイルを置く。`exercise` の kind のみに置く。

**第4章 `#refactor`「型で閉じる」** には、**ADV の3フェーズ**、依頼文の骨子（穴あき）、ステップごとの `<details>` 解答（`steps[].solution` から次スナップショットの実ソースを切り出す）、編集可能な `SessionCodePlayground`、`CommandBlock phase="green"` を置く。`exercise` の kind のみに置く。

**第5章 `#review`「レビューと持ち帰り」** には、**共通4点＋固有1点のレビュー観点**、**`decisions[].notByType`（型で守れない残り）**、完了条件、`examples/final` の対応ファイル（`finalReferences` から生成する）、振り返り、代替進行を置く。全 kind で必須である。

現行の Session 00 と Final が他5ページと非対称だった問題（調査所見 #3）は、`kind` で章の有無を宣言することで解消する。`orientation` と `reference` は3章、`exercise` は5章である。並びと id は kind ごとに固定する。

**第2版での要点**は次の通りである。初版は「編集する2関数を本文へ機械的に出す」ことが要点だった。第2版では **ADV の3成果物（不変条件・依頼文・レビュー観点）が全演習ページに必ず現れる**ことをテストで強制する。`decisions` が空のセッションはビルドが通らない。**制約が運用ルールではなくビルドの制約になる**という初版の狙いはそのままに、対象を「関数の個数」から「判断と成果物」へ移した。

### 6.3 `catalog.ts` の新スキーマ

```ts
export type SessionKind = "orientation" | "exercise" | "reference";

/** 演習で参加者が編集してよい範囲。1演習1ディレクトリ。 */
export type ExerciseModule = Readonly<{
  dir: string;          // "examples/session-01/src/domain/appointment"
  fileBudget: number;   // <= 5
  lineBudget: number;   // <= 80（実効行）
}>;

/** 1つの宣言を完成させる粒度。エージェント非保持者向けの解答提示単位でもある。 */
export type ExerciseStep = Readonly<{
  id: string;                     // "s1-narrow-argument"
  goal: string;                   // 業務の言葉で1文
  targets: readonly string[];     // 触るファイル（すべて module.dir 配下）
  solution: Readonly<{
    path: string;                 // "examples/session-02/src/domain/appointment/transitions.ts"
    symbol: string;               // "startExamination"
    lines: readonly [number, number];
  }>;
}>;

/** 参加者が下す設計判断。1演習3件まで。PRD-04 / PRD-05 に対応。 */
export type Decision = Readonly<{
  invariant: string;   // 守る不変条件（1文）
  byType: string;      // 型でどう表すか
  notByType: string;   // 型で守れない残り
}>;

export type AdvBreakdown = Readonly<{
  articulate: number;  // 言語化
  delegate: number;    // 委譲
  verify: number;      // 検証
}>;

export type TimeBreakdown = Readonly<{
  brief: number;      // 事故提示と RED
  teach: number;      // 技法の解説
  exercise: number;   // 参加者が手を動かす（= adv の3値の和）
  debrief: number;    // GREEN・解答解説・振り返り
}>;

export type SessionSummary = Readonly<{
  slug: string;
  snapshot: ExampleSnapshot;
  sequence: "00" | "01" | "02" | "03" | "04" | "Final";
  kind: SessionKind;
  title: string;
  durationMinutes: number;
  timeBreakdown: TimeBreakdown;
  adv?: AdvBreakdown;                          // kind === "exercise" のみ
  animal: Readonly<{ name: string; type: string; avatar: string }>;
  summary: string;
  incident: string;                            // 事故の1行
  exerciseCommand?: string;                    // "pnpm exercise:01"
  exerciseModule?: ExerciseModule;             // kind === "exercise" のみ
  steps: readonly ExerciseStep[];              // 0 または 1〜4 件
  decisions: readonly Decision[];              // 0 または 1〜3 件
  finalReferences: readonly string[];          // examples/final の対応ファイル
}>;

export type ExampleSnapshot =
  | "session-00" | "session-01" | "session-02"
  | "session-03" | "session-04" | "session-05" | "final";
```

#### 現行および初版案からの差分と理由

- **`label` を削除する。** `animal.name` と重複しており、どのページ・レイアウトからも参照されていない死にフィールドである。`final` だけ値が食い違っている。
- **`kind` を追加する。** Session 00 と Final の非対称を「例外」ではなく「宣言された種別」にするためである。
- **`timeBreakdown` と `adv` を追加する。** 時間配分を facilitator-guide と二重管理せず、catalog を唯一の真実にするためである。§3.2 の検算をテストで固定する。
- **`incident` を追加する。** 「技法からではなく要求・事故から始める」ことをデータで強制するためである。
- **`exerciseTargets` を廃して `exerciseModule` + `steps` + `decisions` へ置き換える（第2版）。** 初版は `{ path, functionName, form }` を最大2件持つ設計だった。新制約に合わせて「範囲（モジュール）」「進め方（ステップ）」「判断（decisions）」の3つに分解する。**関数名を数える設計をやめた。**
- **`invariant: string` を `decisions[].invariant` へ移動する（第2版）。** 不変条件は1演習に最大3つあり、それぞれに「型で守る手段」と「型で守れない残り」が対応する（PRD-04 / PRD-05）。1文フィールドでは PRD-05 を表現できていなかった。
- **`exerciseCommand` を optional にする。** `kind !== "exercise"` の回にコマンドが無いことを型で表すためである。
- **`sequence` から `"05"` を削除する。** セッションが5本になるためである。
- **`snapshot` に `"session-05"` を残す。** 到達点スナップショットおよびステップ解答の切り出し元として参照するためである。catalog の `sessions` 配列には含めない。

#### カタログ不変条件テスト（純ロジック、文言非依存）

アサーションは13件である。

1. slug と sequence が一意であり、配列の順が表示順である。
2. すべての要素で `timeBreakdown` の4値の和が `durationMinutes` と一致する。
3. `kind === "exercise"` の要素で `adv` の3値の和が `timeBreakdown.exercise` と一致する。
4. `sessions` の `durationMinutes` の合計が **150** である（固定枠30分を足して180になることを、コメントではなくアサーションで示す）。
5. `kind === "exercise"` であることと、`exerciseCommand !== undefined` かつ `exerciseModule !== undefined` であることが同値である。
6. `kind === "exercise"` ならば `1 <= steps.length <= 4` かつ `1 <= decisions.length <= 3` である。
7. `kind !== "exercise"` ならば `steps.length === 0` かつ `decisions.length === 0` かつ `exerciseModule === undefined` である。
8. `incident` と `decisions[].{invariant,byType,notByType}` が空文字でない。
9. `exerciseModule.fileBudget <= 5` かつ `exerciseModule.lineBudget <= 80` である。
10. `steps[].targets` の全パスが `exerciseModule.dir` 配下である。
11. `steps[].solution.path` / `targets[]` / `finalReferences[]` が実ファイルとして存在し、`solution.symbol` が `solution.path` の `solution.lines` 範囲内に現れる。
12. `snapshot` に対応する `examples/<snapshot>/package.json` が存在する。
13. （§5.4）実際の差分が `fileBudget` / `lineBudget` に収まる。
