## 背景

2026-08-30 15:00-18:00（180分、connpass、オフライン開催、5人1班＋各班 TA 1名）のイベントに向けて、`examples/` と `apps/docs` をゼロベースで設計し直す。残り18日である。

現行教材（`examples/session-00`〜`session-05` の6スナップショットと `apps/docs` の7ページ）には、調査で確認した次の構造的な問題がある。

- **演習量が制約を破っている。** 実際の演習は白紙からのファイル新規作成であり、生成すべきコードは exercise:01 が 114 行、exercise:02 が 8 ファイル 114 行、exercise:03 が 8 ファイル新規＋7 ファイル改修の 185 行に達する。25〜30分では完走しない。
- **演習形式が4種類に割れている。** 事故デモ（00）、白紙からの新規作成（01/02/03/05）、TODO 穴埋め（04）が混在しており、04 は 20分枠に対して実質5分で終わる。
- **演習が完了不能なものがある。** `examples/session-02/package.json` の依存は `vitest` のみだが exercise:02 は Zod を要求する。`examples/session-03/package.json` は `zod` のみだが exercise:03 は neverthrow の `isOk()` を要求する。いずれも実ファイルで確認済みである。
- **セッション間の連鎖に断絶がある。** session-03 から 04 にかけて `safeParse` から `parse` への破壊的変更が7ファイル分「隠れ改修」として入っている。session-04 の演習は 04 から 05 への実差分（dual-write 解消、Timestamp branding、port 分割）を一切カバーしていない。session-05 演習の `collectFollowUpTargets` は `examples/final` にシグネチャが存在せず、解答の参照先がない。
- **番号がずれている。** `examples/session-01/README.md` は「Session 01 で実装する型付き状態モデル」と書いているのに対し、`examples/session-02/README.md` は同じ主題を「Session 02: 型で状態遷移を閉じる」と名乗っている。
- **`exercises/**` が typecheck の対象外である。** 全セッションの `tsconfig.json` の include は `["src/**/*.ts", "test/**/*.ts", "vitest.config.ts"]` である。型で教える教材でありながら、参加者が最も読むファイルの型が検証されていない。
- **`examples/final` との距離が埋まらない。** session-05 と final は src+test の行数で28倍の開きがあり、未紹介の概念が15種以上ある。`durationMinutes: 10` の「完成例を眺める」枠では橋渡しにならない。

**さらに第2版では、制約そのものに問題があると判断した。** 上に挙げた演習量の超過は「2関数に収まっていない」ことが問題なのではなく、**参加者が一度に負う判断の数と、判断が記録に残らないこと**が問題である。関数の個数はその代理指標として不正確であり、しかも「2」という値に根拠がない。本設計は制約を張り替えたうえで、上の問題群を解く。

## 目的

- 演習スコープの制約を、根拠のある形（PRD が守ろうとしていた狙いを直接測る形）で定義し直す。
- 180分で参加者が到達する地点を、`examples/final` と明確に区別して定義する。
- 全セッションの演習を「配布されたモジュールを型で守られた形にする」1形式に統一し、**言語化 → 委譲 → 検証**（ADV）の3手順を全セッション共通の骨格にする。
- **検証を個人で閉じさせず、各演習に班内の相互レビューを1回置く**（第4版）。TA が班の5人から1〜2名の差分をピックアップし、班の全員が同じ画面を見て意見を述べる。**180分を延ばさずに、既存の枠の統合で実現する。**
- セッション間の連鎖（N の完成形が N+1 の出発点になること）を、人手の同期ではなくテストで機械的に担保する。
- `apps/docs` のセッションページを catalog 駆動の共通骨格へ移し、文言の literal 一致に依存したテストを構造検証へ置き換える。
- 調査で判明した既知の欠陥を、実装フェーズのどの段階で直すかを確定する。
- 制約の張り替えによって実体と矛盾する既存文書を列挙し、書き換え案を示す。

## 対象外

- **`examples/final` は変更しない。** 到達点ではなく参照実装かつお土産として扱い、当日は読む／見せるだけにする。参加者は final の環境構築をしない。
- 白紙からのファイル新規作成を求める演習は採らない。モジュールは**必ず素朴な実装として配布済み**であり、参加者は既存ファイルを書き換える。
- 過去に却下済みの方針は蒸し返さない。具体的には、サーバー側での参加者コード実行、編集内容の永続化・共有 URL・localStorage、Safari / Firefox の正式対応、Markdown parser の導入、Git tag による章管理、セッション間で共有する内部 package、外部 CDN 依存の Shiki である。
- Astro Content Collections / MDX / 外部 CMS は導入しない。理由は §6.1 に書く。
- event sourcing、projection、永続イベントストア、認証・認可、HTTP アダプタの詳細設計は、当日手を動かす範囲から外す（PRD 非ゴール）。
- 通常の再診フロー、および `examples/final` の UI 方針（Operator Console）には触れない。
- **特定のコーディングエージェント製品への依存**（設定ファイル、専用プロンプト形式、API キー）は作らない。§0.1 の暫定前提による。

## 0. 前提

### 0.1 暫定前提（ユーザー未回答。実装フェーズ前に確認が必要）

> **以下3項目は暫定である。** ユーザーからの明示的な回答を得ていないため、本設計はこの前提の上に立つ。前提が覆る場合の影響範囲を各項目に併記する。

#### 前提1: コーディングエージェントは「推奨だが必須ではない」

根拠は、`docs/event/participant-setup.md:12`「データベース、Docker、外部サービスの API キーは必要ありません」と `docs/prd/prd-001.md:231`（同文の品質要件）が、すでに参加者へ約束されていることである。connpass の募集もこの前提で出ている。イベントまで18日しかなく、必須化は告知変更を伴う。

この前提が覆って必須化するなら、§1.4 のフォールバックを削ることができ、演習の差分予算を80行から150行程度まで広げられる。逆に「エージェント言及なし」へ戻すなら、§1.2 の ADV ループを「不変条件 → 実装メモ → セルフレビュー」に読み替える（構造は変わらない）。

#### 前提2: 参加者の作業場所はローカルクローンが主線

根拠は、`docs/event/participant-setup.md:31` ですでに `git clone` + `pnpm install` + `pnpm dev` を踏ませていることである。

この前提が覆り、`apps/docs` の WebContainer Playground を主線にするなら、`npm install` のネットワーク負荷とエージェント連携不能の2点によって本設計は成立しない。

#### 前提3: `apps/docs` の Playground は説明用・退避先である

根拠は前提2と同じである。オフライン会場の帯域に主経路を依存させない。覆った場合の影響も前提2と同じである。

#### エージェントを必須化する案は却下した

理由は、前提1に挙げた告知済みの前提に加えて、`prd-001.md:202`「AIエージェントは主目的にせず、設計判断を依頼文とレビューへ転用する題材として扱う」に反するためである。エージェントを持たない参加者が「本編に参加できない」状態は、この一文と両立しない。

### 0.2 不変の前提（初版から変更なし）

- `examples/final` は変更しない。
- 題材は動物病院の予約・カルテ管理システムである。予約の状態は5つとし、`AwaitingPayment` を持たない（初版 8.3 #2 の判断を維持する）。

## 1. 演習スコープ制約の再定義

### 1.1 何を制約すべきか

PRD-06「最大2関数」が守ろうとしていたものは、`prd-001.md:286` のリスク表に1箇所だけ書かれている。

> | 扱う概念が多く認知負荷が高い | 手を動かすだけで判断過程が残らない | コード編集を行うモジュールでは編集範囲を最大2関数に限定し、最終演習では新しい概念を増やさない |

狙いは2つである。**(A) 認知負荷の管理**と、**(B) 判断過程を残すこと**である。「2関数」はこの2つの代理指標にすぎず、しかも次の4点で不正確である。

第一に、**代理指標が (A) を測れていない。** 2関数であっても、Zod の brand・transform・`schemaResult` を同時に扱えば判断は3つ以上になる（現行 S2 がまさにこれである）。逆に、同じ規約の遷移関数4本は判断1つで済む。

第二に、**代理指標が (B) を全く測っていない。** 関数の個数は、判断が記録に残ったかどうかについて何の情報も持たない。現行 exercise:04 は「2関数以内」を満たしているが、答えがテストに逐語で書かれているため判断が一切残らない。

第三に、**エージェント前提では (A) の意味が変わる。** 打鍵量は制約でなくなり、残る負荷は「読む差分の量」と「下す判断の数」になる。

第四に、**エージェント前提では (B) の重要度が上がる。** 差分を生成させる以上、**言語化とレビューが参加者の仕事の本体**になるからである。

したがって、(A) は「判断の数」と「読む差分の量」で直接測り、(B) は「成果物を必ず残す」ことで直接強制する。

### 1.2 新しい制約

> **演習スコープ制約（第2版）**
>
> 1. **1演習 = 1モジュール。** 参加者が編集するファイルは `exerciseModule.dir` が指す1ディレクトリの中に閉じる。モジュール外は配布・読むのみとする。
> 2. **1演習 = 最大4ステップ。** ステップは「1つの宣言（関数・型・schema）を完成させる」粒度である。エージェント非保持者向けの解答提示単位でもある（§1.4）。
> 3. **1演習 = 最大3判断点。** 判断点は `{ 守る不変条件, 型でどう表すか, 型で守れない残り }` の3つ組として catalog に宣言する（PRD-04 / PRD-05 に直結する）。
> 4. **差分予算 = 最大5ファイル・実効80行。** 実効行はコメントと空行を除く。解答スナップショット間の差分から機械的に測る。
> 5. **ADV 三点セットを必ず残す。** 各演習は「**言語化**（不変条件を1文）→ **委譲**（依頼文に落として差分を作る）→ **検証**（型・テストに照らして差分をレビューする）」の3手順を含み、3つの成果物が残る。
> 6. **検証は個人で閉じない（第4版で追加）。** 各演習は**班内相互レビューを1回**持つ。TA が班の5人から1〜2名の差分をピックアップし、班の全員が同じ画面を見て、共通4観点のうち観点3（型で守ったか、実行時の `if` か）を判定する。所要は7〜8分であり、独立した枠を持つ。

#### 各条項が何を担保するか

**条項1（1モジュール）** は、「今どこを見ればよいか」を1ディレクトリに固定する。現行の「8ファイル新規＋7ファイル改修」のような散らばりを構造的に禁じるためである。認知負荷の主因は編集量ではなく探索範囲であり、これは `prd-001.md:229`「次に何を観察し、何を実行し、何を確認するかを各段階で一つに絞る」と同じ思想である。

**条項2（4ステップ）** は、進捗を4分割し、途中で止まっても「ここまで」が明確になるようにする。PRD-12 の代替進行の切り替え点にもなる。根拠は `prd-001.md:278`「進行が遅れた場合、実装を解答済み例の読解へ切り替えられるようにする」である。

**条項3（3判断点）** は、(A) 認知負荷を**判断の数**で直接測る。「2関数」という代理指標を捨てて本体を測るということである。根拠は `prd-001.md:286` の狙い (A) である。

**条項4（差分予算）** は、読む量の上限を定める。エージェントが生成した差分を12〜17分でレビューできる大きさに保つためである。数字の根拠は後述する。

**条項5（ADV）** は、(B) 判断過程を残すことを**成果物の存在**によって強制する。根拠は `prd-001.md:152` / `:190` / `:202` である。

**条項6（相互レビュー）** は、(B) をもう一段強制する。個人のセルフレビューは「読んだつもり」で通過できるが、班の前で「この不変条件を型で守っている行を1行指してください」と問われると通過できない。**判断が言語化されたかどうかを、他人の耳が検証する**ということである。同時に、`prd-001.md:190` が定める3成果物（依頼文、レビュー観点、検証可能なチェックリスト）が実際に使われる場を作る。相互レビューがなければ、依頼文もレビュー観点も「書いたが誰にも読まれないメモ」で終わる。設計の詳細は §1.6 に書く。

#### 「80行」の根拠（推定であることを明記する）

- 現行 exercise:01 は 114 行を白紙から30分で書かせて完走しない（実測ではなく行数の実カウントである）。
- 初版の「2関数」は 20〜30 行相当と見積もっていた。
- 新スコープはその中間より上を採る。エージェント保持者は1依頼で生成して差分を読む。非保持者は4ステップ×平均20行を、ステップごとの解答提示に支えられて打つ。
- **この 80 という値は実施実績のない推定値である。** リハーサル（§10 の P4）で較正する。ただし「2」と違い、(a) 測定可能であり、(b) 何を測っているかが明示されており、(c) 較正手順が決まっている点で性質が異なる。

#### 捨てた案

関数の個数を 2 から 5 へ緩める案も検討したが、数字の根拠がないという指摘の本体が残り、何を測っているかも変わらないため採らない。

「行数だけ」で制約する案も検討したが、判断過程を残す狙い (B) を全く担保せず、現行 exercise:04 と同じ失敗を許すため採らない。

「時間だけ」で制約する（12分で終わる範囲とする）案も検討したが、教材制作時に検証できず、CI でも測れないため採らない。

モジュール外の編集も許して差分予算だけで縛る案も検討したが、探索範囲が広がって TA が「どこを見ているか」を把握できなくなり、5人班×1 TA の運用と両立しないため採らない。

### 1.3 ADV ループ（言語化 → 委譲 → 検証）

全演習セッション共通の3フェーズである。**第4版で検証フェーズを2段に分けた。** 時間内訳の `exercise` 枠に入るのは言語化・委譲・**個人検証**の3つであり、検証の後段である**班内相互レビュー**は独立した `review` 枠を持つ（§3.2）。ADV という3手順の骨格は変えていない。変えたのは「検証が個人の内側で終わらない」ことである。

**言語化（2分）** では、参加者は事故から守るべき不変条件を1文で書き、班内で読み合わせる。エージェントの有無で内容は変わらない。成果物は手元のシートに書かれた1文である。

**委譲（8〜10分）** では、参加者は不変条件を依頼文に落とし、モジュールに差分を作る。エージェントがある場合は依頼文をエージェントへ渡して差分を得る。ない場合はステップ単位で自分で書き、詰まったらそのステップの解答を開く。成果物は依頼文、またはステップごとの実装メモである。**この8〜10分は第4版でも1分も削っていない**（§3.5）。TA はこの巡回中に、次の相互レビューで誰の差分をピックアップするかを決める（§1.6）。

**検証（第1段・個人検証、2〜3分）** では、参加者は `pnpm exercise:0N` を緑にし、`git diff --stat -- examples/session-0N`（Nは現在の開始snapshot）で今回の差分を確認する。さらに `git status --short` でリポジトリ全体の想定外pathを確認する。前のセッションの未commit差分は残してよく、次の回ではpathだけを切り替える。reset、stash、commitを開始条件にしない。**ここで行うのは機械で判定できることだけである。** 成果物は緑のテスト結果と、現在snapshotに限定した差分の統計1行である。第2版・第3版ではこの枠が4〜5分あり、「差分を型に照らして読む」「型で守れなかった残りを1つ挙げる」まで個人で行う設計だったが、**その後段は班活動へ移した**。

**検証（第2段・班内相互レビュー、7〜8分）** では、TA が班の5人から1〜2名の差分をピックアップし、班の全員が同じ画面を見て、共通4観点に沿って意見を述べる。成果物は、参加者それぞれがレビュー観点シートへ書く「型で守れなかった残り」1行である。進行、選定基準、問いの設計は §1.6 に書く。

**なぜ後段を班へ移したか。** 「この差分は不変条件を型で守っているか、実行時の `if` で守っているか」という観点3は、**見比べないと判定できない**性質の問いである。1人で自分の差分だけを見ていると「テストが緑だから守れている」で通過してしまう。これは現行 exercise:04 が「2関数以内を満たしているのに判断が残らなかった」のと同じ失敗である。5人分の差分のうち2つを並べれば、同じ不変条件に対して型の設計が割れていることが目に見える。**個人検証で4〜5分かけても得られないものが、班で7〜8分かけると得られる**というのが移動の理由である。

#### 依頼文の骨子は穴あきで配布する

サイトの `#refactor` 章に次の形を置く。

```
examples/session-0N/src/<module>/ の中だけを変更してください。
守る不変条件: ____________（← 言語化フェーズで自分が書いた1文）
検証: pnpm exercise:0N が緑になること。
禁止: as によるキャスト。モジュール外のファイルの変更。
```

**穴を埋めるのは参加者である。** 依頼文を完成形で配ると、現行 exercise:04（答えが `exercises/agent-review.test.ts:7-16` に逐語で書かれていた）と同じ失敗を再生産する。埋める1文が、その回で参加者が下した判断そのものになる。

#### 検証フェーズのレビュー観点

全セッション共通の4点である。セッション固有の観点は各セッションに1つ足す。

1. `as` によるキャストが入っていないか。
2. 現在snapshot内でモジュール外のファイルが変更されていないか（scoped diffで見る）。リポジトリ全体の想定外pathはstatusで別に見る。
3. 不変条件が**型**で守られているか、それとも実行時の `if` で守られているか。
4. 型で守れなかった残りは何か（PRD-05）。

**第4版では、この4点を個人検証と相互レビューへ振り分けた。** 観点1と観点2は機械で判定できる（`as` の全文検索、現在snapshotへ限定した `git diff --stat -- examples/session-0N`、全体を見る `git status --short`）ので、**個人検証で各自が済ませ、相互レビューでは TA が画面上で1分で再確認する**だけにする。観点3は見比べないと判定できないので、**相互レビューの本体**に置く。観点4は観点3の議論の帰結として出るので、**相互レビューの末尾1分で各自がシートに書く**。振り分けの詳細と分単位の進行は §1.6 に書く。

### 1.4 エージェント非保持者向けフォールバック

**設計方針**として、解答は**次スナップショットの `src` から機械的に切り出す**。別ファイルに解答スニペットを二重管理する案も検討したが、同期コストが生じ、`.md` や対象外の `.ts` が typecheck を外れる欠陥 #6 の再発を招くため採らない。

提示は3層で行う。**ヒント層**はステップ1つ（1宣言）を単位とし、サイトの `#refactor` 章に `<details>` を4つ置いて、各ステップの解答宣言を `examples/session-0(N+1)/src/...` から行範囲で切り出して表示する。**TA 補助層**も同じくステップ1つを単位とし、同内容を印刷した解答カードを各班1部配る（オフライン開催の利点である）。**全体層**はモジュール全体を単位とし、`examples/session-0(N+1)/src/<module>/` そのものを `#review` 章から「答え合わせ」としてリンクする。

行範囲の切り出しには、既存の `src/code-explorer/code-guide.ts`（ガイド強調の行範囲データモデル）と `code-guides/*.test.ts`（「強調行範囲を実ソースから切り出し、期待するコード断片を含むこと」を検証する）の仕組みをそのまま使う。TypeScript パーサは導入しない。catalog には行範囲と宣言名の両方を持たせ、**宣言名が対象ファイルに現れること**をテストで固定して、行番号のずれを検出する。

**エージェントなしで完走できるか**については、次のように推定している。4ステップ × 平均20行 = 80行を、委譲フェーズ8〜10分で打つ。1ステップあたり2〜2.5分である。ステップの解答が1クリックで開けるため、詰まっても止まらない。**これは実測ではない。** リハーサルではエージェントなしの条件を必ず1本計測する（§10）。

**第4版でも委譲フェーズの8〜10分は1分も削っていない。** 相互レビューの原資を探すにあたって委譲フェーズは候補から明示的に外した。理由は、上の推定が委譲時間に直接依存しており、**未実測の推定値をさらに厳しい側へ動かすことになる**ためである（§3.5 の候補A）。エージェント非保持者が相互レビューでピックアップされた場合の扱い（進度の違い、解答を写した差分の扱い）は §1.6 に書く。

### 1.5 「エージェントレビュー」の扱い — 復活させる。ただし独立セッションにはしない

**判断は、全セッションの背骨（ADV ループ）として復活させ、まとめ枠（10分）で成果物に畳むことである。独立セッションとしては復活させない。**

初版の廃止理由は「答えが演習テストに逐語で書かれており5分で終わる」であった。これは**現行実装の欠陥であって概念の欠陥ではない**という指摘は正しい。`prd-001.md:190` はこのモジュールの成果物を「依頼文、レビュー観点、検証可能なチェックリスト」と定義しており、エージェント前提の教材ではこの3つは周辺ではなく中核である。

#### 独立セッションとして復活させる案は却下した

20分枠の独立セッションとして復活させる案 (a) は却下する。`prd-001.md:202`「AIエージェントは主目的にせず、設計判断を依頼文とレビューへ転用する題材として扱う」に反するためである。独立枠を設けることは主目的化そのものである。また、チェックリストを書く演習には RED がなく、PRD-03「問題を再現するテストまたは観察可能な失敗」を満たせない（現行 04 が5分で終わった構造的な原因はここにある）。さらに180分の枠内で20分を取ると、S3 と S4 のどちらかを潰すことになる。

#### 全セッションに溶かし込む案を採用した

案 (b) として、ADV ループの形で全セッションに溶かし込み、4回反復する。習慣化には反復が要る。1回20分の講義より、4回×3分の実践のほうが `prd-001.md:190` の3成果物を確実に残す。

#### まとめ枠で成果物に畳む案も併用する

案 (c) として、(b) と併用でまとめ枠に畳む。既存のまとめ枠10分の性格を「質疑」から「今日の4つの不変条件を、明日の依頼文とレビュー観点のチェックリストへ畳む」に変える。追加時間はゼロである。PRD-10（業務で見直す箇所と最初の行動を記述できる）と PRD-08（振り返り設問）を同時に満たす。

**第4版でこの枠の性格をもう一度調整した。** 相互レビューが4回入ることで、シートの「型で守れなかった残り」欄は**各回の相互レビューの末尾1分で1行ずつ埋まる**（§1.6）。したがって、まとめ枠でシートを白紙から埋める作業はなくなる。まとめ枠4分の中身は「4回分の記述を読み返し、明日の業務に持ち帰る1つを選ぶ」に変わる。**時間は10分のまま変えていない**（内訳は §4.6）。この変更は、第2版の「まとめ枠でシートを完成させる」という決定と矛盾しない。**完成させる場所は変わらず、埋め方が一度にまとめてから4回の分割払いになっただけ**である。分割払いのほうが、記憶が新しいうちに書けるという点で質が高い。

#### 成果物の具体形

A4 片面1枚の「レビュー観点シート」を各参加者へ配る（印刷、オフライン開催）。4セッション分の行（不変条件 / 依頼文の1文 / 型で守れなかった残り）と、まとめ枠で書く「明日の業務で最初に見る箇所」1行からなる。持ち帰りの実体は、このシートと、自分のローカルクローンの `git log` である。

**第4版で、シートの「型で守れなかった残り」欄の書き込みタイミングを固定した。** 各回の相互レビューの最後の1分に書く。**自分の差分がピックアップされていなくても書く**（班で見た差分から学んだことを、自分の差分に当てはめて書く）。これによって、シートは「自分が下した判断の記録」に加えて「班で見た他人の判断との差の記録」になる。4回分が埋まった状態でまとめ枠に入る。

**「検証可能なチェックリスト」のコード側の実体**は、S3 と S4 の第4ステップで参加者自身が書く**フェイク port テスト1本**とする（概念 #31。§2.2 で「読む」から「演習」へ移した理由がこれである）。文章のチェックリストではなく、機械が実行できる形で残る。

**第4版での接続**は次の通りである。`prd-001.md:190` の3成果物は、相互レビューの場で**全部使われる**。差分を映した参加者が最初に読み上げるのが「依頼文」であり、班が差分に当てる物差しが「レビュー観点」であり、S3・S4 で書いたフェイク port テストが「検証可能なチェックリスト」として画面に映る。第2版は3成果物を「残す」ところまでを設計していたが、**残したものが読まれる場を持っていなかった**。相互レビューはその場である。

### 1.6 班内相互レビュー（第4版で新設）

**要求**は、ユーザーからの「それぞれの演習について相互レビューの時間をとりたい。TA が1-2名の実装をピックアップして、それを見ながらメンバーが意見をする」である。

**判断は、これを新しい枠の追加ではなく、既存の検証フェーズと debrief 枠の統合として実現することである。** 時間の出どころは §3.5 に数字で示す。以下は中身の設計である。

#### TA は何を基準にピックアップするか

**「よくできた実装」を選ばない。** よくできた実装を見せる会は、模範解答の解説と情報量が変わらず、それなら TA が1つ用意して見せるほうが速い。相互レビューが独立枠を持つ価値は、**同じ不変条件に対して班の中で判断が割れていることを見せられる**点にしかない。したがって選定基準は「学びが出る差分」である。

優先順つきで5件を定める。TA は委譲フェーズ（8〜10分）の巡回中に班の5画面を1周し、上から順に当てはまるものを探す。

**基準1（最優先）— 同じ不変条件を、型で守った差分と、実行時の `if` で守った差分の対。** これが見つかったら他を探さずに2名を確定する。共通観点3を実物で対比できる唯一の形であり、相互レビューの本命である。S1 なら「引数型を `CheckedIn` に絞った差分」対「引数は `Appointment` のまま `if (a.kind !== "CheckedIn") throw` を残した差分」が典型である。

**基準2 — `as` によるキャストが残っている差分。** 観点1が実物で出る。`as Appointment` を消すのが S1 の主題であるのに、エージェントは型エラーを黙らせるために `as` を足すことがある。**これはエージェントの出力の典型的な癖であって、書いた人の技能ではない。**

**基準3 — モジュール外のファイルが変更されている差分。** 観点2が実物で出る。現在snapshotへ限定したdiffが「3 files changed」と「9 files changed」で並ぶと、依頼文の「モジュール外の変更禁止」の1行が効いているかどうかが一目で分かる。snapshot外の想定外pathは `git status --short` で拾い、このファイル数比較には混ぜない。

**基準4 — 依頼文の1文が他と明確に違う2名。** 言語化フェーズの1文が違えば差分が違う。**依頼文と生成物の因果を見せる**ための選定であり、`prd-001.md:152`「設計判断をAIエージェントへの依頼と人間のレビューへ転用する」に最も近い。

**基準5 — テストは緑だが、判断点3件のうち1件を落としている差分。** 「緑＝守れている」ではないことを示す。ステップ4（型テストやフェイク port テスト）を飛ばしても基本ケースが緑になる回で起きやすい。

**選定を4回にわたって記録する。** ピックアップは1回1〜2名、4回で延べ6〜8名分になる。班は5人なので、**2名選ぶ回を3回以上作れば全員が最低1回は当たる**。TA は誰を何回選んだかを手元に記録し、4回を通じて偏らせない。これは公平性のためだけでなく、**「選ばれた＝できていない」という読みを構造的に潰す**ためである（§後述の心理的安全性）。

#### 参加者は何を発言するか — 問いを3つ用意する

「意見をどうぞ」では沈黙する。オフラインで初対面の5人班ならなおさらである。**問いを定型化し、サイトの `#review` 章と TA の進行カードの両方に印刷する。** 問いは全セッション共通の3件である。

**問い1「この差分は、不変条件を型で守っていますか、実行時の `if` で守っていますか。守っている行を1行、画面上で指してください。」** 答えが二択であり、かつ**行を指すという物理的な動作**を求めるので、沈黙しにくい。指せない場合は「守れていない」という答えがそのまま出る。これが共通観点3である。

**問い2「この状態を壊すコードを1行書くとしたら、どう書きますか。それはコンパイルを通りますか。」** 参加者を攻撃側に立たせる。守る側の視点は「書けているか」しか見えないが、攻撃側の視点は「型の穴」を探す。これは `examples/final` の `@ts-expect-error` 型テストと同じ思考であり、S2 のステップ4で自分が書くことになる思考でもある。答えが「通ってしまう」なら、それがそのまま共通観点4（型で守れなかった残り）になる。

**問い3「自分の差分と違うところを1つ挙げてください。どちらが良いかは言わなくてよいです。」** 1人目と2人目の対比、あるいは自分の差分との対比に使う。**「どちらが良いかは言わなくてよい」という免除を問いの本文に埋め込んである**のが要点である。優劣の判定を求められていないと明示されていれば、発言の心理的コストが下がる。

**TA が締めに使う問い**は「では、この差分が型で守れていない残りは何ですか」である。ここで各自がレビュー観点シートの1行を書く。

#### 分単位の進行

**7分版（S1・S2）** は次の通りである。

- **0:00–0:30** TA が1人目の差分を画面に映す。**本人は説明しない。**
- **0:30–1:00** 本人が「依頼文の穴に入れた1文」だけを読み上げる。実装の弁明はしない。読むのは自分が書いた1文であって、コードではない。
- **1:00–2:00** TA が画面上で観点1と観点2を機械的に確認する（`as` の全文検索、現在snapshot限定のdiff、全体のstatus）。判断を要さないので1分で足りる。
- **2:00–4:00** 問い1と問い2を回す。TA が2名を指名する。挙手を待たない。（2分）
- **4:00–6:00** 2人目の差分を映し、問い3だけを回す。**2人目には問い1・2を繰り返さない。** 対比のためだけに映す。（2分）
- **6:00–7:00** 各自がレビュー観点シートに「型で守れなかった残り」を1行書く。TA が1名に読ませて締める。（1分）

合計は 0.5 + 0.5 + 1 + 2 + 2 + 1 = **7分** ✓ である。

**8分版（S3・S4）** は、問い1・問い2の枠を2分から3分へ広げたものである。`Result` のパイプラインと `ResultAsync` への持ち上げは、差分を読み解くだけで時間がかかるためである。合計は 0.5 + 0.5 + 1 + 3 + 2 + 1 = **8分** ✓ である。

**1名しかピックアップできない場合**（時間が押した、基準に当たる差分の対が見つからなかった、班にエージェント保持者が1名しかいない）は、2人目の枠2分を落として **5分版／6分版**にする。**これが押した場合の吸収枠である。** 相互レビューそのものを落とすことはしない（4回の反復が習慣化の条件であり、1回落とすと反復が3回になるため）。

#### コードをどう見せるか — 会場設備への要求

5人が同じ画面を同時に読める必要がある。**会場設備は本設計時点で未確認であり、§10.4 に未確認事項として挙げた。** 想定は3案である。

**第一案（推奨）は、班ごとに外部ディスプレイ1台である。** 24インチ程度、HDMI 入力、USB-C 変換アダプタを添える。ピックアップされた参加者が自分のラップトップを繋ぐ。映すのは `git diff` の出力ではなく、**エディタで対象ファイルを開いた状態**である。理由は、型エラーの波線とホバーの型表示が相互レビューの本体（観点3）に必要だからである。現在snapshot限定のdiff statと全体のstatusだけは端末に切り替えて見せる。必要数は「班数 × 1台」であり、班数は参加人数が未確認のため確定していない。

**第二案（外部ディスプレイがない場合）は、ピックアップされた参加者のラップトップを島の中央へ向けて置くことである。** 本人は操作だけを担い、説明はしない（進行の約束事4と整合する）。ただし13〜14インチの画面を5人で囲むと3人目以降は読めない。補償として、**TA はピックアップの対象を1ファイル・20行以内に絞る**。ステップ単位の差分（§1.4 のステップ1つ = 1宣言）はこの制約に自然に収まる。エディタのフォントサイズを一時的に上げることも進行カードに書く。

**第三案（退避先）は、TA が該当箇所を口頭で読み上げることである。** これは観点1（`as` の有無）と観点2（変更ファイル数）には足りるが、**観点3（型で守ったか実行時 `if` か）には足りない**。型は目で追わないと分からない。**採らない前提で設計し、機材が全滅した場合の退避先としてのみ記す。**

**却下した案**が2つある。画面共有ツール（会場 Wi-Fi への依存が増え、§10.1 の帯域リスクと衝突する。当日の主経路をローカル実行にした §0.1 の前提2とも整合しない）と、印刷して配る案（差分は当日その場で生成されるので物理的に不可能である）である。

#### 心理的安全性

自分のコードが班に晒される形式は、参加者によっては負担になる。**設計で軽くする。**

**事前告知する。** connpass の当日案内と `docs/event/participant-setup.md` に「各演習のあとに、班内で1〜2名の差分を見ながら話す時間があります」と書く（§7.4）。当日その場で知る状態を作らない。

**進行上の約束事を5点定め、TA が S1 の相互レビューの冒頭で読み上げ、印刷して島に置く。**

1. **見るのは差分であって人ではない。** 発言は「この差分は」で始める。「〜さんは」で始めない。
2. **良し悪しを判定しない。** 問い3の本文に「どちらが良いかは言わなくてよいです」と書いてある通りである。
3. **4回で全員が最低1回は当たる。** 延べ6〜8枠を5人で分ける。**選ばれることは評価ではない。** TA は初回冒頭にこれを明言する。
4. **本人は弁明しない。** 読み上げるのは依頼文の1文だけである。コードの説明責任を本人に負わせない。
5. **TA は「よくできた実装」を選ばない。** 選定基準5件（上記）は参加者にも開示する。何を基準に選ばれたかが分かっていれば、選ばれたこと自体の意味が読める。

**エージェント差分をレビューする形式は、この負担を構造的に軽くする。** エージェント保持者の差分は「自分が書いたコード」ではなく「**自分が出した依頼文に対するエージェントの出力**」である。批判の矛先がコーディング技能から離れ、依頼文と生成物のずれへ向かう。「`as` が入っているのはエージェントの癖である」と言うことに、人格的な含意がない。この性質を進行に織り込むため、次の2つを設計に入れた。

- **進行の最初に読み上げるのが「依頼文の1文」であること**（0:30–1:00 の枠）。レビューの対象が依頼文から始まると宣言する装置である。
- **TA は原則としてエージェント保持者の差分を優先してピックアップすること。** 特に **S1 の1回目は必ずエージェント保持者から選ぶ**。形式に慣れるまでは、最も負担の軽い側から始める。

#### エージェント非保持者の差分をピックアップする場合

非保持者は進度が違う可能性がある（ステップ2までしか進んでいない、など）。4点で扱う。

**ピックアップの単位を「モジュール全体の差分」ではなく「ステップ1つ分の差分」にする。** ステップ1は全員が到達している。TA は演習テストの赤の数で誰がどこまで進んだかを把握できる（§5.5 で `describe` をステップと1対1にしてあるため）ので、班の最小到達点に合わせてステップを選べる。**未完成であることを前提にした単位を用意しておく**ということである。

**解答を写した差分になっている場合は、問いを読み替える。** 非保持者はステップ解答の `<details>` を開いて写している可能性がある。この場合、問い1は「解答そのもの」への問いになる。TA は「なぜ**解答は**この形なのか」「この形でないとどこが壊れるか」へ読み替える。**この読み替えを TA の進行カードに明記する。** 写した差分でも観点3の判定は成立するので、レビューとしては壊れない。

**非保持者を選ぶのは S3 または S4 で1回に限る。** S1・S2 は形式に慣れる段階であり、また非保持者は序盤ほど遅れやすい。慣れた後、かつステップ解答を写した形が「解答の読み解き」として扱える段階で当てる。

**班にエージェント保持者が0名の場合**（S0 の申告で TA が把握できる。§4.0 では混在配置を狙うが、全体の保持率次第では成立しない班が出る）は、4回とも非保持者から選ぶ。このときピックアップ単位を常に「ステップ1つ分」に固定し、選定基準1（型で守った差分と `if` で守った差分の対）を優先する。**基準1は、解答を写した参加者と自力で書いた参加者の間でも成立する**ので、この班でも相互レビューの本体は失われない。

#### catalog とサイトへの反映

相互レビューは運用ルールではなく**データ**として持つ。`peerReview: { minutes, pickCount, questions }` を catalog に持たせ（§6.3）、`kind === "exercise"` の全セッションで必須にする。3つの問いはサイトの `#review` 章に本文として現れ、テストで欠落を検出する（§6.5）。**運用の申し送りではなくビルドの制約にする**という第2版からの方針をそのまま適用したものである。

## 2. 到達点の再定義

### 2.1 当日の到達点（`examples/session-05` スナップショット）

180分後に参加者の手元にあるのは、**単一集約（予約）を、型で守られた非同期パイプラインとして表現した約 500 行の TypeScript プロジェクト**である（初版は「同期パイプライン・約400行」であった）。具体的には次を満たす。

- 予約は5状態の判別共用体で表され、状態ごとに必須項目が違う。`Paid` / `Canceled` から戻る遷移関数は存在しない。状態表示は `assertNever` で網羅されており、状態を1つ足すとコンパイルエラーになる。
- 外部入力（検査ラボ JSON、飼い主連絡先）は Zod schema と smart constructor を通してのみドメイン型になる。ID は用途別 branded type であり、取り違えがコンパイルエラーになる。
- 個人情報は `Sensitive<T>` に包まれ、`JSON.stringify` / `console.log` / `util.inspect` のいずれでも `[REDACTED]` になる。
- 予期可能な失敗は `throw` ではなく `Result<T, E>` の tagged union で返り、呼び出し側が `kind` で網羅的に分岐できる。
- 時刻と ID は port として注入され、ドメイン関数は決定的である。状態と監査記録は1つの `store(event)` で同時に保存され、片方だけ残ることがない。
- **ユースケースは `ResultAsync` の1本のパイプラインであり、保存は `andThrough` を通る。** `examples/final` の30ユースケースと**同じ形**をしている（第2版で追加した到達点である）。
- **失敗経路を固定するフェイク port テストを、参加者自身が書いている**（第2版で追加した到達点である）。

**これは `examples/final` ではない。** final は7集約・30ユースケース・Hono/Inertia/React/Drizzle/SQLite を含む 23,000 行超のアプリケーションであり、180分で到達できる規模ではない。final は「学んだ型が実アプリでどう使われるか」を示す参照実装として、当日は講師デモ5分で見せ、帰宅後の自習材とする。

**第2版で到達点を上げた効果**は次の通りである。初版の到達点と final の最大の距離は「同期 vs 非同期」であった。`examples/final/src/useCase/startExaminationUseCase.ts` の骨格（`.andThen(...).andThen(...).andThrough(store).map(...)`）を当日の成果物が持つことで、「帰って final を開いたら同じ形だった」という接続が生まれる。これがスコープ拡大で最も価値の高い1手である。

### 2.3 `ResultAsync`（#15）を演習へ移す判断

**結論は、移すことである。** S4 の第3ステップとして、配布済みの同期 `Result` パイプラインを維持したまま、別名の効果付き経路を `ResultAsync` で組み立てる。

**価値**が高い。`examples/final` の30ユースケースはすべて `ResultAsync` である。ここを渡らないと「final は別世界」で終わる。お土産の4差分のうち最大の差分がこれであった。

**判断の質**も高い。判断点は「どこまでが純粋で、どこから非同期か」と「保存は `andThen` か `andThrough` か」の2つであり、どちらも**型では自動的に決まらない設計判断**である。ADV ループの題材として質が高い。

**打鍵量**は小さい。neverthrow の `andThen` は同期 `Result` も `ResultAsync` も受けるため、パイプラインの形はほぼ変わらない。差分は型別名の変更、`ok`/`err` から `okAsync`/`errAsync` への変更、port 戻り型の変更、`andThrough` の導入であり、**推定15〜25行**である（実測ではない）。

**エージェント適性**も高い。「このパイプラインを `ResultAsync` に持ち上げて。保存は値を汚さずに通して」は1依頼で通る。参加者の仕事はレビュー側に寄る。

**典型的な罠**が2つあり、これがそのままレビュー観点になる。(a) `andThrough` を `andThen` にすると `store` の戻り値がパイプラインを乗っ取り、`event` が消える。(b) Promise を返す関数を `map` に渡すと `Result<Promise<...>>` になる。**どちらも型が教えてくれるが、エラーメッセージを読めないと詰まる。**

**コスト**は S4 が30分から35分になることである。原資は §2.4 に示す。

**リスク**については、S4 の最終ステップに置いたため、押した場合は講師デモ3分へ切り替えて5分を回収できる（分離可能な設計にしてある）。

**`ResultAsync` を入れても演習targetへ入れないもの**がある。`ResultAsync.fromPromise` による例外の閉じ込め（#18）はsession-05 adapterで読む。一方、`mapErr` による内部失敗から公開エラーへの写像（#17）は、PII境界を構造型だけで隠さないためS4 Step 4で演習・検証する。

### 3.5 相互レビュー30分の原資（第4版）

**180分は不変である。** 相互レビューを4セッションに入れると素朴には20〜30分の追加が要る。以下、どこから出したかを数字で示す。

#### まず置き換えを探した

第2版の設計には、**同じ作業を二度やっている箇所があった**。ADV ループの検証フェーズ（S1 4分 / S2 4分 / S3 5分 / S4 5分 = 18分）は「差分を型とテストに照らして読み、型で守れなかった残りを1つ挙げる」ことを個人でやる枠であり、直後の debrief 枠（S1 4分 / S2 4分 / S3 5分 / S4 5分 = 18分）は「GREEN・解答解説・班内共有」をやる枠である。**この2つは連続しており、後者は前者の結果を班で言い合う場だった。** 相互レビューは、この2枠を1本の班活動に統合したものとして構成できる。

統合の結果、個人に残すのは**機械で判定できることだけ**（`pnpm exercise:0N` を緑にする、現在snapshot限定のdiffと全体のstatusを見る）とし、S1・S2 で2分、S3・S4 で3分に縮めた。合計 2+2+3+3 = 10分であり、18分から **−8分**である。

したがって置き換えで得られるのは、旧 debrief **18分**＋検証フェーズの短縮分 **8分** = **26分**である。

#### それでも4分足りない

相互レビューに必要なのは 7 + 7 + 8 + 8 = **30分**である。26分では **4分足りない**。§1.6 の進行を分単位で組んだ結果、7分（S1・S2）と8分（S3・S4）が下限だと判断した。これより短くすると、2人目の対比（2分）か、問い1・2を回す枠（2〜3分）のどちらかが消える。前者が消えると「判断が割れていることを見せる」という相互レビューの存在理由そのものが消え、後者が消えると発言が起きない。

不足4分の候補を5つ検討した。

**候補A: 委譲フェーズ（合計37分）の圧縮。** 4セッションから1分ずつ取れば足りる。**採らない。** §1.4 でエージェント非保持者の完走可能性を「4ステップ × 平均20行 = 80行を委譲フェーズ8〜10分で打つ。1ステップあたり2〜2.5分」と推定しており、この推定は委譲時間に直接依存している。1分削ると1ステップあたり15秒短くなり、S2 では 8分 → 7分で1ステップ1.75分になる。**まだ実測していない推定値を、さらに厳しい側へ動かすことになる。** §10.4 に「エージェントなし条件は一度も検証していない」と書いてある以上、ここは触らない。**委譲37分を1分も削らなかったのは、この判断による。**

**候補B: S0（15分）のさらなる圧縮。** **採らない。** §10.1 で「Session 00 の15分が薄い」を既にリスクとして登録しており、「業務理解が不足したまま S1 に入ると、S1 の言語化フェーズが機能しなくなる」と書いている。言語化フェーズが機能しないと、相互レビューの 0:30–1:00 で読み上げる「依頼文の1文」が空になる。**相互レビューを入れるために S0 を削るのは、相互レビューの前提を壊す**という自己矛盾になる。

**候補C: オープニング（10分）の圧縮。** **採らない。** この枠には環境確認（`pnpm test` が緑であること）と**エージェント有無の申告**が入っている。申告は班の混在配置（§4.0）の入力であり、混在配置は相互レビューのピックアップ設計（§1.6）の前提である。ここを削ると相互レビューの運用が崩れる。**むしろ相互レビューの導入によって、この枠の重要度は上がった。**

**候補D: まとめ枠（10分）の圧縮。** **採らない。** 相互レビューが4回入ると、レビュー観点シートには4回分の記述が溜まる。まとめ枠はそれを読み返して1つを選ぶ枠になる（§1.5 / §4.6）。**入力が増えた枠を削るのは逆方向である。** PRD-10（業務で見直す箇所と最初の行動を記述できる）を満たす唯一の枠でもある。

**候補E（採用）: teach 枠の圧縮、4セッションから1分ずつ。** S1 は7分から6分、S2 は8分から7分、S3 は8分から7分、S4 は8分から7分とする。合計 31分 → 27分、**−4分**である。

#### なぜ teach を選んだか

**落とすのは「典型的な罠の予告」だからである。** 現行の teach 枠には、これから起きる失敗を先回りして口頭で説明する部分が含まれている。相互レビューは**その失敗が実際に起きた差分を画面に映して扱う場**なので、予告は重複になる。抽象的な予告を落とし、実物で扱う。原則は「**罠の説明を、講義から実物のレビューへ移す**」である。

具体的に何を落とすかは次の通りである。**S1 では `as` ではなく `satisfies` を使う理由の一般論**を落とす（相互レビューの選定基準2「`as` が残っている差分」で実物として扱う）。**S2 では `Sensitive<T>` の実装解説**（`Symbol.for("nodejs.util.inspect.custom")` の仕組み）を落とし、配布コードのコメントへ移す（実装は読むだけで書かせないため、口頭解説の費用対効果が最も低い）。**S3 では `map` と `andThen` の使い分けの例示**を落とし、1行ルール（§10.2 の「関数が `Result` を返すなら `andThen`、素の値を返すなら `map`」）のスライド常掲に置き換える。**S4 では `andThrough` を `andThen` にすると event が消える罠 (a) の説明**を落とす（GREEN 判定 (c) が機械的に捕まえ、相互レビューの観点3で扱う）。

**コストは明記しておく。** teach が4分短くなることで、参加者は「先に聞いてから書く」量が減り、「書いてから見比べて気づく」量が増える。**これは失敗の量が増える設計である。** RED → 試す → 見比べる、という順序を選んだということであり、講義で先回りするより記憶に残るという仮説に賭けている。**この仮説は検証していない。** §10.4 に未検証事項として追加した。teach 短縮が S2（3技法で最も密）で成立するかがリハーサル（P4）の確認項目である。

#### 検算

相互レビュー30分 = 旧 debrief **18分** + 検証フェーズの短縮 **8分** + teach の短縮 **4分** = **30分** ✓ である。全体は動かず180分のままである（§3.1）。

#### 演習セッションを4本から3本へ減らす案は却下した

不足4分どころか、1本減らせば30分前後が浮く。**採らない。** 落ちるものを数えると割に合わないためである。

**S4 を落とす場合。** 演習から外れるのは #4（カリー化のうち `(deps) => (input) => ResultAsync` の側）、**#15（`ResultAsync` と `andThrough`）**、#19（1メソッド port）、#20（非決定性の注入）、#24（型付きドメインイベント）、#25（状態と監査の同時保存）の**6件**である。加えて S4 で「読む」としていた #17（エラー型の写像）と #18（例外の閉じ込め）は読む場所が消えるのでお土産へ落ちる。集計は**演習19 → 演習13、読む4 → 読む2、お土産8 → お土産16**（13 + 2 + 16 = 31 ✓）となる。**`ResultAsync` は演習に残せない。** §2.3 で「`examples/final` の30ユースケースはすべて `ResultAsync` である。ここを渡らないと『final は別世界』で終わる」「スコープ拡大で最も価値の高い1手」と判断した到達点が、そのまま失われる。§2.1 の到達点から「ユースケースは `ResultAsync` の1本のパイプライン」と「フェイク port テストを参加者自身が書いている」の2項目が消え、第2版の引き上げが丸ごと巻き戻る。**4分のために取り消す変更としては大きすぎる。**

### 4.1 Session 01 — 状態を型にする（30分）

**要求**は、会計済み・キャンセル済みの来院をあとから診察中へ戻せないようにしたい、キャンセルには必ず理由を残したい、というものである。

**事故**は事故報告 #1（二重請求）である。`pnpm exercise:01` が赤で始まる。

**演習モジュール**は `examples/session-01/src/domain/appointment/` である。中身は3ファイルからなる。`appointment.ts` は5状態の判別共用体（`Scheduled` / `CheckedIn` / `InExamination` / `Paid` / `Canceled`）と `CancellationReason` を持ち、**配布済みで変更しない**。`transitions.ts` は `checkIn` / `startExamination` / `recordPayment` / `cancel` の4本を持ち、素朴な実装で配布して演習対象とする。`statusLabel.ts` は `toStatusLabel` を持ち、`switch` に `default: return "不明"` がある状態で配布して演習対象とする。

```ts
// transitions.ts の配布される素朴版（動くが守られていない）
export const startExamination = (
  appointment: Appointment,
  veterinarianId: string,
): Appointment => {
  if (appointment.kind === "Paid") throw new Error("cannot start");
  return {
    ...appointment,
    kind: "InExamination",
    veterinarianId,
    examinationStartedAt: new Date().toISOString(),
  } as Appointment; // ← as で押し通している
};
```

なぜ事故るかというと、遷移の可否を**実行時の `if` 1本**でしか守っておらず、`Canceled` からの遷移は素通りするからである。戻り値を `as Appointment` でキャストしているため、必須項目が欠けていてもコンパイルが通る。`toStatusLabel` の `default` は、状態が増えても何も言わない。

**ステップは4件である。** まずステップ1で「会計済みの来院は診察を開始できない」を実現する。`startExamination` の第1引数を `CheckedIn` に絞り、`as Appointment` を `as const satisfies InExamination` へ変える（推定10行）。次にステップ2で「キャンセルには必ず理由が残る」を実現する。`cancel` の第1引数を `Scheduled | CheckedIn` に絞り、`CancellationReason` を必須引数にする（推定12行）。続くステップ3では「残る2本の遷移も同じ規約に揃える」ため、`checkIn` と `recordPayment` を同じ形へ変える。ここが**エージェントに「同じ規約で残り2本」と依頼する練習**になる（推定20行）。最後にステップ4で「状態を1つ足したらコンパイルエラーになる」ようにする。`toStatusLabel` の `default` を捨て、`assertNever` で網羅にする（推定8行）。

**差分予算**は3ファイル・50行である（上限は5ファイル・80行）。ステップの推定行の合計は 10 + 12 + 20 + 8 = 50行であり、予算と一致する。

**判断点は3件である。** 判断点1は「終端状態から戻らない」を守る。型では、逆行遷移の関数を**作らない**ことと、引数型で遷移元を縛ることで表す。型で守れない残りは、呼び出し側が `as` で state を捏造すれば通ってしまうことであり、だからこそ `as` を禁止する運用が要る。判断点2は「状態ごとの必須項目が欠けない」を守る。型では、状態ごとに別の型を持つ判別共用体と `as const satisfies` で表す。型で守れない残りは、外部 JSON からの復元であり、これは S2 の境界で別途守る必要がある。判断点3は「状態が増えたら全ての分岐が見直される」を守る。型では `assertNever` による網羅性検査で表す。型で守れない残りは、`default` を書き戻せば黙ってしまうことであり、レビュー観点として残す。

**到達する型とパターン**は、判別共用体、遷移元を引数型で縛る純粋関数、`as const satisfies`、逆行遷移の関数を作らない設計、`assertNever` による網羅性検査である。

**`examples/final` の対応ファイル**は `src/domain/appointment/appointment.ts` と `src/domain/shared/assertNever.ts` である。

**GREEN の判定**は `pnpm exercise:01` が緑になることである。加えて `exercises/state-modeling.test.ts` の `// @ts-expect-error` 節が、「`Paid` を `startExamination` に渡すとコンパイルエラー」と「状態を1つ足すと `toStatusLabel` がコンパイルエラー」を型レベルで固定する。これは `exercises/**` を tsconfig の include に入れたことで初めて機能する（欠陥 #6）。

**エージェント非保持者のフォールバック**として、ステップ1から4それぞれの解答宣言を `examples/session-02/src/domain/appointment/` から切り出して `<details>` に置く。ステップ3は「1と2と同じ形」なので、詰まる場合はステップ1の解答を見て写せる構造にしてある。

**相互レビュー（7分）** は §1.6 の7分版で行う。**この回は必ずエージェント保持者から選ぶ**（形式に慣れるまで最も負担の軽い側から始める）。**このセッションの選定基準は基準1が最も当たりやすい。** `startExamination` の第1引数を `CheckedIn` に絞った差分（型で守った）と、引数を `Appointment` のまま残して `if (appointment.kind !== "CheckedIn") throw` を書き換えただけの差分（実行時の `if` で守った）は、S1 で最も高い頻度で割れる対である。テストはどちらでも緑になるため、**「緑＝守れている」ではないことを最初の回で体験させられる**。基準2（`as` の残存）も当たりやすい。`as Appointment` を消すのが主題であるにもかかわらず、エージェントは戻り値の型エラーを黙らせるために `as` を再導入することがある。

**セッション固有のレビュー観点**（共通4点に足す1点）は「`toStatusLabel` の `default` が本当に消えているか。消したうえで、状態を1つ足したときにコンパイルエラーになるか」である。相互レビューの問い2（この状態を壊すコードを1行書くとしたら）はここで「6つ目の状態を union に足してみてください」という具体形になる。

### 4.2 Session 02 — 値を型にする（30分）

**要求**は、外部の検査ラボから届く JSON をカルテに取り込みたい、フォロー電話のために飼い主の連絡先を扱いたい、というものである。

**演習モジュール**は `examples/session-02/src/boundary/` である。`examResult.ts` は検査結果の取り込みを担い、素朴版で配布して演習対象とする。`ownerContact.ts` は飼い主連絡先の取り込みを担い、同じく素朴版で配布して演習対象とする。`boundary.test-types.ts` は ID 取り違えを固定する型テストであり、空ファイルで配布してステップ4の演習対象とする。

モジュール外に**配布済みで変更しない**ものとして、`src/shared/sensitive.ts`（`[Symbol.for("nodejs.util.inspect.custom")]` 付き）、`src/shared/schemaResult.ts`、`src/domain/ids/*.ts`（branded ID 5種。うち1つは完成例として `AppointmentId` を置く）がある。

// examples/session-02/src/boundary/examResult.ts（配布される素朴版）

// examples/session-02/src/boundary/ownerContact.ts（配布される素朴版）
export const parseOwnerContact = (raw: any): OwnerContact => ({

なぜ事故るかというと、`any` を通しているので外部 JSON の形が変わっても気づかず、ID が `string` なので取り違えを型が止められず、連絡先が素の `string` なので `JSON.stringify` すればどこにでも漏れるからである。

**ステップは4件である。** まずステップ1で「形の違う JSON はドメイン型にならない」ようにする。`parseExamResult` の `raw: any` を `raw: unknown` に変え、`ExamResultSchema` を組み、`schemaResult(...)` を返す（推定18行）。次にステップ2で「電話番号とメールはログに出ない」ようにする。`parseOwnerContact` の `email` と `phone` の schema に `.brand<...>().transform(Sensitive.of)` を足し、`schemaResult` を通す（推定16行）。続くステップ3では「手書きの型と schema がずれない」ようにする。`ExamResult` と `OwnerContact` の手書き型を捨て、`z.infer<typeof Schema>` から導く（推定8行）。最後にステップ4で「ID の取り違えはコンパイルで止まる」ようにする。`boundary.test-types.ts` に `@ts-expect-error` の型テストを2本書く（`ownerId` を `petId` の位置に渡す等。推定10行）。

### 4.4 Session 04 — 副作用を外に出す（35分）

**要求**は、誰がいつ診察を開始したかをあとから追えるようにしたい、というものである。保存は外部ストレージへの非同期呼び出しになる。

**セッション固有のレビュー観点**は「保存の戻り値でパイプラインを上書きしていないか（`event` が生き残っているか）」である。問い2は「保存を必ず失敗させるフェイクを渡したとき、状態と記録のどちらかが残りますか」という具体形になり、ステップ4で書いたテストが答えになる。

**最終回であるため、締めの1分を長めに使う。** TA は「型で守れなかった残り」をシートに書かせたあと、**4回分の記述を見返すよう促して**まとめ枠（§4.6）へ繋ぐ。

**時間内訳**は brief 5分、teach 7分（port・注入・イベント・dual-write・`ResultAsync`）、exercise 15分（言語化2分・委譲10分・個人検証3分）、review 8分（班内相互レビュー）で、5+7+15+8 = **35分** ✓ である。**第4版で teach を8分から7分へ、個人検証を5分から3分へ変え、debrief 5分を相互レビュー8分に置き換えた。委譲10分は変えていない。** teach で落とすのは「`andThrough` を `andThen` にすると event が消える」という罠 (a) の予告であり、GREEN 判定 (c) と相互レビューの観点3で実物として扱う（§3.5）。

### 4.5 Final — 参照実装ツアー（5分・講師デモ）

参加者は環境構築をしない。講師が画面で `examples/final/src/useCase/startExaminationUseCase.ts` を開き、**当日 S4 で書いたものとほぼ同じ形であること**を最初に見せる。次に §2.5 の3差分を示し、サイトの該当節へ誘導する。

**時間内訳**は teach 4分（`startExaminationUseCase.ts` の並置2分と3差分の位置づけ2分）、review 1分（自習導線の案内。`reference` なので相互レビューは持たない）で、4+1 = **5分** ✓ である（第4版で分数の変更はない）。

### 4.6 まとめ枠（10分・固定枠。性格を変更）

初版は「まとめ、行動計画、質疑」であった。第2版では §1.5 の通り、**「エージェントレビュー」の成果物を作る枠**にする。

**第4版で内訳の中身を変えた。分数は10分のままである。** 相互レビューが4回入ることで、レビュー観点シートの「型で守れなかった残り」欄は各回の末尾1分で1行ずつ埋まっている（§1.5 / §1.6）。したがってこの枠は「白紙を埋める枠」ではなく「**4回分を読み返して1つを選ぶ枠**」になる。

内訳は、シートの4行を読み返して**明日の業務に持ち帰る1つに丸をつける**のに4分（第3版では「空欄を埋める」4分であった）、班内で1人1つ「明日の業務で最初に見る箇所」を宣言する（PRD-10）のに3分、全体まとめと質疑に3分で、4+3+3 = **10分** ✓ である。

**この変更の効果**は2つある。第一に、記述が4回に分割されるので、記憶が新しいうちに書ける（S1 の判断を3時間後に思い出して書く必要がなくなる）。第二に、まとめ枠が押しても**シートは既に埋まっている**ので、成果物が失われない。第2版の設計ではまとめ枠が潰れるとシートが空のまま持ち帰られる構造だったが、第4版ではその依存が消えた。

## 5. `examples/` の新ディレクトリ構成

### 5.1 構成

```
examples/
  session-00/   # 引き継ぎ。legacy 一式（演習なし）
  session-01/   # 状態      開始点 = 00 の legacy + 配布 union + 素朴な遷移関数
  session-02/   # 境界      開始点 = 01 の解答を含む
  session-03/   # 失敗      開始点 = 02 の解答を含む
  session-04/   # 副作用    開始点 = 03 の解答を含む
  session-05/   # 到達点    = 04 の解答（exercises なし）
  final/        # 参照実装（変更しない）
```

`session-05` はセッションではなく**到達点スナップショット**である。サイトの catalog には載せない。役割は、(a) Session 04 の答え合わせ、(b) 「今日の到達点」として持ち帰る単一のプロジェクト、(c) 全演習の解答とステップ解答スニペットの所在を一意にすること、の3つである。現行の「最終演習の正解がどこにも存在しない」欠陥（調査 #4）を構造的に解消する。

ディレクトリ名 `session-0N` は据え置く。workspace 名 `@fp-with-ts/clinic-session-0N`、root scripts、`apps/docs` の raw glob、worker のリダイレクトがすべてこの規約に乗っており、改名の利得が小さいためである。

### 5.2 `src` / `test` / `exercises` の枠組み — 維持する

現行の3分割と、`vitest.config.ts`（`test/**` のみ）／ `vitest.exercises.config.ts`（`exercises/**` のみ）の2ファイル構成は**そのまま維持する**。理由は3つある。

- 「通常テストで確認する健全性と、教材で意図的に失敗させる演習を区別する」ことは PRD の品質要件（`prd-001.md:226-227`）かつ `AGENTS.md` の教材不変条件であり、この2ファイル構成がそれを最小のコストで実現している。
- 6セッションすべてで両 config がバイト単位で同一であり、増減しても複製コストがない。
- `apps/docs` の `run-command.ts` が、`exercises/**` と `test/**` でコマンドを出し分ける実装に依存している。

変更するのは中身の規約だけである。

**`src/`** は、現行では演習で参加者が**新規作成**する（つまり存在しない）が、新構成では演習モジュールのファイルは**必ず存在**し、素朴な実装または `// TODO` の穴が入っている。

**`exercises/`** は、現行では未存在ファイルへの dynamic import であり赤の理由がモジュール解決エラーだが、新構成では実在ファイルを static import し、赤の理由が assertion 失敗になる。加えて**ステップ単位で `describe` を分け、どこまで進んだかが赤の数で読める**ようにする。

**`test/`** は、現行ではセットアップ確認のみだが、新構成ではセットアップ確認に加えて**前セッションの演習テストを回帰として持ち越す**。

**`tsconfig.json` の include** は、現行では `src` / `test` / `vitest.config.ts` だが、新構成では `exercises/**/*.ts` と `vitest.exercises.config.ts` を追加する。

**`package.json` の script** は、現行では `build` / `typecheck` / `test` / `exercise` だが、新構成では `build` を削除する（`tsc --noEmit` の別名でしかなく、final の `build` と意味が違うためである）。

**依存**は、現行では演習に必要な依存が入っていない回があるが、新構成では S2 以降に `zod`、**S3 以降に `neverthrow`**、S2 以降に `@types/node`（`util.inspect` 検証のため）を宣言する。

> **第2版での依存の変更**: `ResultAsync` は neverthrow の同一パッケージに含まれるため、S4 で追加依存は発生しない（`examples/final/package.json` で `neverthrow@^8.2.0` を確認済みである）。

### 5.3 セッション間の連鎖の担保（初版から維持）

**規約**は、`session-0N/exercises/**` の期待値が `session-0(N+1)/src/**` に対して緑になることである。

**担保方法**は、`session-0(N+1)/test/regression/` に `session-0N` の演習テストを回帰テストとして**そのまま持ち越す**ことである。これにより次の3つが得られる。

- `pnpm --filter @fp-with-ts/clinic-session-0(N+1) test` が既存の `vitest.config.ts`（`test/**`）で自動的に連鎖を検証する。追加のスクリプトも CI ジョブも要らない。
- 「session-03 → 04 の `safeParse` → `parse` 隠れ改修」（調査 #7）のような差分は、持ち越した回帰テストが落ちるので混入できない。
- 参加者が自分の答えと次スナップショットを突き合わせられる。

累積の結果、`session-05/test/regression/` には S1 から S4 の全演習テストが揃い、「到達点が今日学んだ全部を満たしている」ことを1コマンドで示せる。

**副次的な規約**として、各セッションの `README.md` は「このディレクトリは Session NN の**開始**スナップショットである。解答は `examples/session-0(N+1)/src` にある」の形式で統一する。これが現行の番号ずれ（調査 #5）の恒久対策になる。

### 5.4 差分予算テスト（第2版で新設）

新スコープ制約の条項4を機械的に強制する。実体は `apps/docs/src/test/examples/exercise-budget.test.ts`（純ロジックであり、レンダリングしない）である。

各演習セッション `N` について、次を行う。

1. `examples/session-0N/src/<module.dir>/` と `examples/session-0(N+1)/src/<module.dir>/` を読む。
2. ファイル単位で行を比較し、**追加＋変更行数**（コメント行・空行を除く）を数える。
3. 変更ファイル数が `module.fileBudget`（5以下）以下であり、実効行数が `module.lineBudget`（80以下）以下であることをアサートする。
4. `steps[].targets` の全ファイルが `module.dir` 配下にあることをアサートする。
5. `steps.length` が4以下、`decisions.length` が3以下であることをアサートする。

**この方式には次の限界があり、明記しておく。**

- 行単位の比較であり、TypeScript の構文は解釈しない。整形の違いを差分として数える。**正確な値ではなく予算の上限監視である**ことを前提にする。
- `module.dir` の外に配布される「次セッション用の新規ファイル」は予算に入らない。これは意図した設計（演習スコープはモジュール内に閉じるという条項1そのもの）だが、「モジュール外に本質を逃がす」抜け道でもある。**§5.3 の回帰テスト持ち越しが、この抜け道で連鎖が壊れることを防ぐ**という二重の守りになっている。
- 比較は「素朴版 → 解答版」を測っており、参加者が実際に打つ量とは一致しない（エージェント使用時はさらに乖離する）。**測っているのは「読む差分の量」である。**

### 5.5 演習の RED を「情報のある赤」にする

現行の RED はモジュール解決エラーであり、`expect` が何を要求しているかはテスト本文を読まないと分からない。新構成では演習対象ファイルが必ず存在するので、赤は必ず assertion 失敗になる。加えて演習テストは次を守る。

- **`describe` をステップに1対1で対応させる。** ステップ1が緑になればブロック1が緑になる。TA は「今どのステップか」を赤の数で把握できる。**第4版では、これが相互レビューのピックアップ判断の入力にもなる。** TA は委譲フェーズの巡回中に班の到達段階を赤の数で読み、**班の最小到達点に合わせたステップ**をレビュー対象に選ぶ（§1.6 の「エージェント非保持者の差分をピックアップする場合」）。
- 各 `it` の名前を業務の言葉で書く（例: 「会計済みの来院は診察を開始できない」）。
- 型レベルの禁止は `// @ts-expect-error` で表明し、`pnpm typecheck` で検証する（`exercises/**` を include に入れたことで初めて機能する）。
- 副作用が**起きていないこと**を明示的にテスト名に書く（例: 「失敗時は store へ書かない」）。`examples/final` のテスト命名規約を踏襲する。

## 6. `apps/docs` の再構成

### 6.1 content collection を導入するか — 導入しない（初版から維持）

**判断は、導入しないことである。** ユーザーが挙げた痛み（セッション数を変えるとページを手で足す）は、content collection ではなく **catalog 駆動の動的ルート**で解く。理由は4つある。

第一に、2026-08-06 に「Astro Content Collections、MDX、外部 CMS による本文構造化」を明示的に対象外と決定済みであり、その理由（各セッションを教材として改善する自由度を優先し、本文を先回りして共通スキーマへ閉じ込めない）は今も有効である。

第二に、教材本文は Markdown/MDX の表現力を超えている。吹き出し会話（`.onboarding-story`）、来院タイムライン（`.visit-timeline`）、ガイド付き Monaco、WebContainer playground は、いずれも `.astro` のテンプレートと island で書かれている。

第三に、content collection のスキーマ定義には `zod` が要るが、`apps/docs` の依存は現在 `@astrojs/react` / `@webcontainer/api` / `astro` / `monaco-editor` / `react` / `react-dom` の6つであり zod を含まない。残り18日で依存とビルドの検証を増やす利得がない。

第四に、ページ数の手作業は動的ルートで消える。本文の置き場所を変える必要はない。

**代わりに採る案（フェーズ2）**は次の通りである。`src/pages/sessions/[slug].astro` を1枚だけ置き、`getStaticPaths` を `catalog.ts` から生成する。本文は `src/sessions/content/<slug>.astro` に置き、`import.meta.glob("../../sessions/content/*.astro", { eager: true })` で対応コンポーネントを解決して描画する。これで catalog が唯一の真実になり、`site-contract.test.ts` の「ページ glob と catalog が一致すること」というテスト自体が不要になる。

**リスクと退避**についても書いておく。Astro 4 で `.astro` を `import.meta.glob` の eager import で受け取り動的コンポーネントとして描画する経路は、本設計時点で実機検証していない（推測を含む）。実装フェーズの最初に技術検証を行い、通らなければ**フェーズ1の形（セッションごとに1枚の `.astro`、計6枚）で確定する**。フェーズ1でも catalog スキーマ刷新・章骨格の構造化・テストの作り直しはすべて成立するので、当日までのクリティカルパスには乗せない。

### 6.2 セッションページのテンプレート／セクション骨格

全セッション共通の5章とする。`SessionLayout` が章定義を受け取り、**TOC を自動生成する**（現行の手書き `<ol slot="toc">` を廃止する）。

**第1章 `#incident`「何が起きたか」** には、要求、事故、**守る不変条件（`decisions[].invariant` から生成する）**、今回のミッションを置く。全 kind で必須である。

**第2章 `#legacy`「配布コードを読む」** では、素朴な実装のどこが素朴かを `SessionCodeOverview`（読み取り専用ガイド）で指す。**演習モジュールの範囲を明示する。** 全 kind で必須である。

**第3章 `#red`「失敗を再現する」** には、`CommandBlock phase="red"`、**演習モジュールと4ステップの表（`exerciseModule` と `steps` から生成する）**、先に読むファイルを置く。`exercise` の kind のみに置く。

**第4章 `#refactor`「型で閉じる」** には、**ADV の3フェーズ**、依頼文の骨子（穴あき）、ステップごとの `<details>` 解答（非空の `steps[].solutions` から次スナップショットの実ソースを順に切り出す）、編集可能な `SessionCodePlayground`、`CommandBlock phase="green"` を置く。`exercise` の kind のみに置く。

**第5章 `#review`「レビューと持ち帰り」** には、**共通4点＋固有1点のレビュー観点**、**`decisions[].notByType`（型で守れない残り）**、完了条件、`examples/final` の対応ファイル（`finalReferences` から生成する）、振り返り、代替進行を置く。全 kind で必須である。**第4版で、`kind === "exercise"` の回にはさらに「班内相互レビュー」の小節を置く。** 中身は、この回の所要（`peerReview.minutes`）、ピックアップ人数（`peerReview.pickCount`）、**参加者へ投げる3つの問い（`peerReview.questions` から生成する）**、そして進行上の約束事5点である。**問いを参加者側の画面にも出すのが要点である。** TA の手元だけにあると、指名された参加者が何を答えればよいか分からないまま考えることになる。約束事5点は S1 のページに全文、S2 以降は S1 へのリンクで置く。

現行の Session 00 と Final が他5ページと非対称だった問題（調査所見 #3）は、`kind` で章の有無を宣言することで解消する。`orientation` と `reference` は3章、`exercise` は5章である。並びと id は kind ごとに固定する。

**第2版での要点**は次の通りである。初版は「編集する2関数を本文へ機械的に出す」ことが要点だった。第2版では **ADV の3成果物（不変条件・依頼文・レビュー観点）が全演習ページに必ず現れる**ことをテストで強制する。`decisions` が空のセッションはビルドが通らない。**制約が運用ルールではなくビルドの制約になる**という初版の狙いはそのままに、対象を「関数の個数」から「判断と成果物」へ移した。

### 6.3 `catalog.ts` の新スキーマ

```ts
export type SessionKind = "orientation" | "exercise" | "reference";

/** 演習で参加者が編集してよい範囲。1演習1ディレクトリ。 */
export type ExerciseModule = Readonly<{
  dir: string;          // "examples/session-01/src/domain/appointment"
  fileBudget: number;   // <= 5
  lineBudget: number;   // <= 80（実効行）
}>;

export type SolutionReference = Readonly<{
  path: string;                 // "examples/session-02/src/domain/appointment/transitions.ts"
  symbol: string;               // "startExamination"
  lines: readonly [number, number];
}>;

/** 1つ以上の宣言を完成させる粒度。エージェント非保持者向けの解答提示単位でもある。 */
export type ExerciseStep = Readonly<{
  id: string;                     // "s1-narrow-argument"
  goal: string;                   // 業務の言葉で1文
  targets: readonly string[];     // 触るファイル（すべて module.dir 配下）
  solutions: readonly [SolutionReference, ...SolutionReference[]]; // targetsごとに次snapshotの同一相対pathを1件以上含む
}>;

/** 参加者が下す設計判断。1演習3件まで。PRD-04 / PRD-05 に対応。 */
export type Decision = Readonly<{
  invariant: string;   // 守る不変条件（1文）
  byType: string;      // 型でどう表すか
  notByType: string;   // 型で守れない残り
}>;

export type AdvBreakdown = Readonly<{
  articulate: number;  // 言語化
  delegate: number;    // 委譲
  verify: number;      // 検証
}>;

export type TimeBreakdown = Readonly<{
  brief: number;      // 事故提示と RED
  teach: number;      // 技法の解説
  exercise: number;   // 参加者が手を動かす（= adv の3値の和）
  review: number;     // kind === "exercise" では班内相互レビュー、他は debrief
}>;

/** 班内相互レビュー。kind === "exercise" のみ。第4版で新設。 */
export type PeerReview = Readonly<{
  minutes: number;                 // timeBreakdown.review と一致
  pickCount: 1 | 2;                // TA がピックアップする人数
  questions: readonly string[];    // 参加者へ投げる問い（3件）
}>;

export type SessionSummary = Readonly<{
  slug: string;
  snapshot: ExampleSnapshot;
  sequence: "00" | "01" | "02" | "03" | "04" | "Final";
  kind: SessionKind;
  title: string;
  durationMinutes: number;
  timeBreakdown: TimeBreakdown;
  adv?: AdvBreakdown;                          // kind === "exercise" のみ
  peerReview?: PeerReview;                     // kind === "exercise" のみ（第4版）
  animal: Readonly<{ name: string; type: string; avatar: string }>;
  summary: string;
  incident: string;                            // 事故の1行
  exerciseCommand?: string;                    // "pnpm exercise:01"
  exerciseModule?: ExerciseModule;             // kind === "exercise" のみ
  steps: readonly ExerciseStep[];              // 0 または 1〜4 件
  decisions: readonly Decision[];              // 0 または 1〜3 件
  finalReferences: readonly string[];          // examples/final の対応ファイル
}>;

export type ExampleSnapshot =
  | "session-00" | "session-01" | "session-02"
  | "session-03" | "session-04" | "session-05" | "final";
```

#### 現行および初版案からの差分と理由

- **`label` を削除する。** `animal.name` と重複しており、どのページ・レイアウトからも参照されていない死にフィールドである。`final` だけ値が食い違っている。
- **`kind` を追加する。** Session 00 と Final の非対称を「例外」ではなく「宣言された種別」にするためである。
- **`timeBreakdown` と `adv` を追加する。** 時間配分を facilitator-guide と二重管理せず、catalog を唯一の真実にするためである。§3.2 の検算をテストで固定する。

**全般: 不変条件を1文で書けない**（言語化フェーズ、第2版で新規）。拾い方は、「〜が〜できない」の型を黒板に常掲することである。事故報告の1行をそのまま否定形にすれば足りることを示す。

**全般: 依頼文の穴に何を入れるか分からない**（第2版で新規）。拾い方は、言語化フェーズで書いた1文をそのまま貼るのが正解であることを最初に明言することである。2つを別物だと思わせない。

**S1: `as const satisfies` を書く位置が分からない。`as` を外すとどこがエラーになるか読めない。** 拾い方は、「エラーメッセージの `Property 'x' is missing` は、その状態で必須の項目を教えている」と読み方を先に教えることである。

**S1: `assertNever` を入れると既存の `switch` が全部赤くなる。** 拾い方は、「赤の数＝見直すべき分岐の数」であり、これが網羅性検査の効果そのものだと説明することである。

**S2: Zod の `.brand()` と `.transform()` の順序が分からない。`z.infer` の結果が読めない。** 拾い方は、順序は「brand → transform」で固定と明言することである。配布コードに1つ完成例（`AppointmentId`）を置く。

**S3: `andThen` と `map` の使い分けが分からない。`Result` を返す関数を `map` に渡してネストする。** 拾い方は、「関数が `Result` を返すなら `andThen`、素の値を返すなら `map`」の1行ルールをスライドに常掲することである。

**S4: `Dependencies` の分割代入と、カリー化された `Appointment.startExamination(context)(...)` の呼び出し形で詰まる。** 拾い方は、呼び出し1行を配布コードのコメントに写経用として置くことである。

**S4: `andThrough` を `andThen` にして event が消える**（第2版で新規）。拾い方は、GREEN 判定 (c) がこれを捕まえることである。「保存の戻り値でパイプラインを上書きしていないか」をレビュー観点として明示する。

**S4: `ResultAsync` を返す関数を `await` してしまう**（第2版で新規）。拾い方は、「パイプラインの終端まで `await` しない。終端は `match` か `await` 1回」と明言することである。

**相互レビュー: 問い1に誰も答えない**（第4版で新規）。拾い方は、TA が自分で1回答えて型を示すことである（「この差分は、この15行目の引数型で守っています」）。それでも出ない場合は、**問いを「守っている行を指してください」ではなく「この差分の中で、`if` は何本ありますか」に落とす**。数を数える問いは必ず答えが出る。数えたあとで「その `if` は不変条件を守るための `if` ですか」へ戻す。

**相互レビュー: ピックアップされた本人が長々と説明を始める**（第4版で新規）。拾い方は、進行の約束事4（本人は弁明しない。読むのは依頼文の1文だけ）を最初に読み上げてあることを根拠に、TA が「ありがとうございます、では班の皆さんに聞きます」で引き取ることである。**約束事を先に共有しておくのは、この引き取りを角の立たない形にするためでもある。**

**相互レビュー: 議論が「どちらの書き方が好みか」に流れる**（第4版で新規）。拾い方は、問いを「好み」から「壊れ方」へ戻すことである。「では、その書き方だと**どういうコードを書いたときに壊れますか**」と問い直す。壊れ方が言えれば設計の議論であり、言えなければ好みの議論である。**この線引きを TA の進行カードに1行で書く。**
