# AGENTS.md 整備設計

## 状態

- 日付: 2026-08-06
- 対象: リポジトリルートと `apps/docs/`
- 方針: エージェント製品に依存しない、リポジトリ固有の指示を整備する

## 背景

このリポジトリには、リポジトリ固有の `AGENTS.md` が存在しない。現在の作業では個人環境のルールや会話上の指示に依存しており、教材固有の判断基準、意図的に失敗する演習、公開サイトの保護対象、変更範囲別の検証方法が一か所にまとまっていない。

2026-08-04から2026-08-06までの関連セッション約15件を確認したところ、次の要求と手戻りが繰り返されていた。

- PRDと参加者目線を基準にし、ページ単体でも目的と作業内容を理解できるようにする
- 型や技法の説明より先に、登場人物の要求、業務イベント、事故、状態遷移を示す
- 計画、承認、実装、批判的レビューを分ける
- トップページの見た目とコンテンツを、サイト基盤変更からも保護する
- モバイルを含む実画面で視覚変更を確認する
- ドキュメント、表示ページ、テスト、カタログ、ルーティングを同期する

一方、次の問題が手戻りにつながっていた。

- トップページの要素が移行時に失われ、復旧後も実画面で直っていなかった
- 参加者目線や業務シナリオを後工程で補った
- 成果物の正規配置を作成後に直した
- 教材として不自然な日本語が混入した
- ローカルの成果物だけを案内し、ユーザーが実機から確認できなかった
- worktree外への誤適用や、存在しない個人環境パスへの依存が発生した

これらのうち、複数セッションで反復し、今後の変更にも安定して適用できる事項だけをリポジトリ指示へ昇格する。

## 目的

- 教材の目的と参加者の行動変容を、変更判断の基準にする
- 教材上意図された壊れ方と通常の回帰を区別する
- 公開サイトの内容と視覚品質を、基盤変更や共通変更から保護する
- 変更対象に応じた同期範囲と検証方法を明確にする
- どの対応エージェントでも解釈できる、製品非依存の指示にする

## 対象外

- 特定のエージェント製品、モデル、ツール名に依存する役割分担
- 個人環境のルールファイルや絶対パスへの参照
- 特定のPR番号、コミット、ブランチ、worktreeパス
- 単一セッションにだけ必要だった表示調整や一時的な運用
- 一般的なコーディング規約や秘密情報保護ルールの重複掲載

## 採用する構成

責務分割型を採用する。

1. ルートの `AGENTS.md` は、リポジトリ全体の目的、教材の不変条件、構成、作業フロー、TypeScript方針、共通検証を扱う。
2. `apps/docs/AGENTS.md` は、参加者が見るページの受け入れ条件、トップページ保護、変更時の同期範囲、視覚検証を扱う。
3. 子ファイルはルートの内容を再掲せず、`apps/docs/` 固有の追加条件だけを書く。

ルートだけに全指示を集約する案は、UI固有ルールが教材コードの作業にも混ざるため採用しない。反対にルートを索引だけにする案は、教材コード変更時にPRDや学習設計の原則が適用されにくいため採用しない。

## ルート `AGENTS.md` の設計

### リポジトリの目的と判断基準

- 関数型ドメインモデリングを、型の技巧ではなく業務事故の防止として体験できる教材であることを示す。
- 教材体験の判断基準として `docs/prd/prd-001.md` を指定する。
- 教材や演習の変更前に、対象参加者、前提知識、期待する行動変容を確認する。

### ディレクトリの責務

- `apps/docs/`: Astroで構築した公開サイト
- `packages/clinic-example/src/legacy/`: 事故を再現するための意図的に壊れやすい実装
- `packages/clinic-example/src/clinic/`: 関数型ドメインモデリングのworked example
- `packages/clinic-example/test/`: 常に成功すべき通常テスト
- `packages/clinic-example/exercises/`: 教材上の失敗と改善を体験する演習テスト
- `worker/`: ヘルスチェック、旧URLリダイレクト、静的アセット委譲
- `docs/event/`: 当日のセットアップ、進行、トラブル対応
- `docs/design/`: 参考モックアップであり、公開サイト本体ではない

### 教材の不変条件

- 技法の説明からではなく、業務上の要求または事故から始める。
- 不変条件、採用する技法、技法の限界、検証方法、振り返りを対応させる。
- 参加者が編集する範囲は原則として2関数以内に保つ。
- 型の複雑さではなく、事故を防げることと効果を確認できることを優先する。
- `legacy` の問題を先回りして解消せず、worked exampleと演習の対応を維持する。
- ドキュメント、コード、テスト、演習コマンドの説明を同期する。
- 関係のない再設計や、現在必要のない将来向け抽象化を混ぜない。

### 作業フロー

- 計画依頼では実装を始めず、実装依頼では承認済みの仕様と計画を引き継ぐ。
- 大規模な移行や全面改修では、変えてよいものと維持するものを先に明記する。
- 現在の依頼で指定または承認された仕様書と計画は、変更前に読み、合意済みの判断を再解釈しない。過去の完了済み計画を自動的な拘束条件にはしない。
- 提供済みのworktreeがあればそれを使う。なければ現在地と既存worktreeを確認し、新規作成が必要な場合だけ、依頼で指定された基準ブランチ、または最新の `origin/main` から隔離されたworktreeを作る。
- 作業が完了し必要な検証が成功したら、明示的な別指示がない限り、作業ブランチをpushしてドラフトPull Requestを作成する。同じブランチの未完了Pull Requestがある場合は新規作成せず更新する。pushまたはPull Requestの作成・更新に失敗した場合は、ローカルマージや強制pushで迂回せず、失敗内容を報告して停止する。
- 新しい文書を作る前に、同種成果物の正規配置と命名を確認する。

### TypeScript方針

`packages/clinic-example` では現在の教材設計に合わせ、次を維持する。

- `Readonly` なデータ
- 判別共用体による状態とエラー
- 純粋な状態遷移関数
- Zodによる外部入力境界
- Branded TypeによるIDの区別
- `Result` による予期可能な失敗
- 現在の診察開始ユースケースでは、成功した状態変更だけ `ExaminationStarted` を記録する。失敗自体を業務イベントとして扱う新しい要件がある場合は、仕様、説明、テストをまとめて変更する
- `Sensitive` によるPIIのログ保護
- 相対importの `.js` suffix

### 共通検証

- TypeScriptや教材ロジックの変更では、変更したパッケージのテスト、`pnpm typecheck`、`pnpm test` を実行する。
- 全体変更では、CIと同じ `pnpm typecheck`、`pnpm test`、`pnpm build` を実行する。
- 通常の健全性確認は `pnpm test` とする。
- 現在のworked exampleでは、`pnpm exercise:00` は事故の再現として意図的に失敗し、`pnpm exercise:01` から `pnpm exercise:05` までは成功する。starterや演習途中では期待結果が異なるため、コマンド名だけで判断せず、その時点の説明と期待する失敗理由を照合する。
- 実行できなかった検証は、完了扱いにせず理由を報告する。

## `apps/docs/AGENTS.md` の設計

### モジュールページの受け入れ条件

- `src/pages/modules/*.astro` は、ページ単体で、背景、登場人物の要求、起きる出来事、参加者の作業、確認方法、期待する気づきが分かるようにする。
- 状態モデリングでは、業務イベント、遷移前の状態、遷移後の状態、実装する関数を対応づける。
- 最初のモジュールだけでなく、後続モジュールも同じ学習構造を保つ。
- 時系列や状態遷移を、理解しづらい表だけで説明しない。内容に応じてタイムライン、段階表示、状態図、カードを使う。
- トップ、案内、エラーページにモジュール固有の構造を強制しない。すべての参加者向けページでは、日本の開発現場で自然な日本語を使い、不自然な直訳やプロジェクトで定着していない用語を避ける。

### トップページの保護

- 明示的な依頼がない限り、トップページの見た目、文章、情報量、主要導線を変えない。
- サイト基盤の移行、レイアウト共通化、共通CSSの変更でも保護対象として扱う。
- 影響が及ぶ変更では、変更前の主要テキストと表示を確認し、変更後にモバイルとデスクトップで実画面を比較する。
- 復旧作業では、差分や自動テストだけでなく、ユーザーが見る最終ページを確認する。

### 変更時に同期する対象

モジュールの追加、改名、移動では、少なくとも次をまとめて確認する。

- `apps/docs/src/modules/catalog.ts`
- `apps/docs/src/pages/modules/*.astro`
- 対応するページテスト
- `apps/docs/scripts/verify-static-build.mjs` の必須HTML
- 内部リンクと前後ナビゲーション
- 旧URLを維持する場合の `worker/routes.ts` とテスト

`catalog.ts` は表示順、slug、前後ナビゲーションの基準として扱う。

### 視覚検証

- トップページまたは共通CSSの変更では、`pnpm --filter @fp-with-ts/docs test`、`pnpm --filter @fp-with-ts/docs build`、`pnpm --filter @fp-with-ts/docs test:visual` を実行する。現行の視覚テストはトップページを対象としている。
- モジュールページのUIやCSSを変更した場合は、視覚テストが対象ページを含むか確認する。含まなければ対象URLをモバイル幅とデスクトップ幅で直接確認するか、必要に応じて視覚テストへ追加する。
- 自動テストだけで完了を判断せず、モバイル幅を先に、その後デスクトップを実画面で確認する。
- スクリーンショットが入力として与えられた場合は、近い条件で変更前後を比較する。
- ユーザーの確認が必要な場合は、利用可能な環境で実際に開けるプレビューを案内する。

### 変更範囲別の検証

- ページとナビゲーション: `pnpm --filter @fp-with-ts/docs test`、`pnpm --filter @fp-with-ts/docs build`
- CSSとレスポンシブUI: 上記に加えて、対象範囲を覆う視覚テストと実画面確認
- Workerルーティング: Workerテストを含む `pnpm --filter @fp-with-ts/docs test`、`pnpm typecheck`

## ルールの解決と失敗時の扱い

- ルートの指示を全体へ適用し、子ファイルは配下固有の条件だけを追加する。
- 学習目的はPRD、実行コマンドは `package.json` とCI設定、現在の挙動はテストと実装を優先して確認する。現在の依頼で指定された仕様書・計画以外の古い計画書だけを根拠にしない。
- 参照先が存在しない場合は、別製品や別環境のパスを推測せず、参照切れとして報告する。
- 通常テストの失敗、教材上意図された失敗、視覚差分を区別して報告する。
- ルートと子ファイルで同じ指示を重複させず、矛盾が生じないようにする。

## 検証計画

AGENTS.md実装後に次を確認する。

1. 記載したパスとスクリプトが現在のリポジトリに存在する。
2. ルートには目的、構成、教材の不変条件、作業フロー、TypeScript方針、共通検証があり、子ファイルにはモジュールページ、トップページ保護、同期対象、視覚検証、docs固有の検証だけがある。
3. `Claude`、`Codex`、`Opus`、`Sonnet`、ホームディレクトリ表現、個人環境の絶対パスを含まない。
4. セッション固有のPR番号、ブランチ名、コミットIDを含まない。
5. Markdownの見出し構造とコード表記が崩れていない。
6. `git diff --check` が成功する。
7. `apps/docs/AGENTS.md` がルートのディレクトリ説明、worktree手順、TypeScript方針を重複していないことを目視確認する。
8. ルートの作業フローに、検証成功後のpush、ドラフトPull Requestの作成または更新、失敗時の停止条件があり、`apps/docs/AGENTS.md` に同じ指示を重複させていない。

AGENTS.mdのみの変更は実行コードへ影響しないため、基準状態で `pnpm test` が成功することを確認したうえで、実装後は文書固有の検証を中心に行う。

## 受け入れ条件

- ルートと `apps/docs/` に2つの `AGENTS.md` があり、検証計画2と7の責務分担を満たす。
- リポジトリの目的、教材の不変条件、意図的な失敗、共通検証がルートから分かる。
- モジュールページの参加者目線、トップページ保護、同期範囲、視覚検証が `apps/docs/` から分かる。
- 検証計画3と4の禁止対象を含まず、個人環境や特定製品なしで成立する。
- 背景で挙げた反復課題に対応し、対象外に挙げた一時的な事情を含まない。
- 検証成功後は統合方法を毎回質問せず、明示的な別指示がない限りドラフトPull Requestを作成または更新し、失敗時に別の統合方法へ勝手に切り替えない。
