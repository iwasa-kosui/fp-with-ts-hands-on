# Workers 未実装ページ実装 設計

## 概要

Workers で配信しているハンズオンサイトをデータ駆動の SPA に統一し、未実装の6モジュールを既存 Module 00 と同じ詳細度で公開します。既存のハッシュルーターは通常パスを扱うルーターへ変更し、トップページ、各モジュール、前後ナビゲーションを同じ仕組みで描画します。

本設計では、[FP with TypeScript ハンズオン PRD](../../prd/prd-001.md) を要件の基準にします。設計、実装タスク、テストを PRD の要件 ID と対応付けます。

## 目的

- 未実装の6モジュールについて、参加者がハンズオンを進めるために必要なコンテンツをすべて実装します。
- 関数型ドメインモデリングを、事故対応だけではなく、新しい要求へ安全に対応して変更容易性を保つ方法として学べる構成にします。
- URL の直入力、再読み込み、戻る・進むで同じページを表示できる通常パスのルーティングへ統一します。
- コンテンツを型付きデータへ集約し、ページごとの HTML と CSS の重複をなくします。

## スコープ

### 対象

- トップページを既存の静的 HTML から SPA のホーム画面へ移します。
- 既存 Module 00 のデザインとコンテンツを共通テンプレートと型付きデータへ移します。
- 未実装の6モジュールを Module 00 と同じ詳細度で実装します。
- `main.ts` のハッシュルーターを通常パスのルーターへ変更します。
- 旧 `/module-00/` から正規 URL への互換導線を残します。
- PRD-01 から PRD-10 と PRD-12 をコンテンツ、型、テストへ反映します。
- PRD-02 の「要求・事故」という表現を、PRD の体験設計とリリース判定基準に合わせて「要求または事故」へ明確にします。

### 対象外

- PRD-11 の30日後フォローアップの実施は対象外です。2026年8月5日にユーザーが承認したスコープ例外として扱います。
- Worker のルーティング実装は変更しません。Static Assets の SPA fallback と既存の assets 委譲を利用します。
- 外部 API、データベース、Docker、外部アカウントは追加しません。
- ハンズオンの技法と関係しないリファクタリングは行いません。

## 現状

- `apps/docs/index.html` は独立した静的トップページで、`#app` と `/src/main.ts` の読み込みがありません。
- `apps/docs/src/main.ts` にはハッシュを使うルーターとモジュールレンダラーがありますが、現在のトップページから接続されていません。
- 詳細な静的ページは `apps/docs/public/module-00/index.html` だけです。
- `apps/docs/src/content/modules.ts` には未実装6モジュールの概要がありますが、Module 00 と同じ画面を描画するための構造が不足しています。
- `wrangler.jsonc` は存在しないアセットへのアクセスを SPA の `index.html` へ戻す設定です。
- `worker/index.ts` は `/healthz` 以外を Static Assets へ委譲しています。

## URL 設計

正規 URL は次のとおりです。

- `/`
- `/modules/00-break-the-app/`
- `/modules/00-read-the-incident/`
- `/modules/01-state-modeling/`
- `/modules/02-boundary-and-ids/`
- `/modules/03-result-errors/`
- `/modules/04-agent-review/`
- `/modules/05-mini-integration/`

`/modules/00-break-the-app/` は既存 Module 00 のコンテンツに対応します。旧 `/module-00/` は互換ルートとしてこの正規 URL に置き換えます。

末尾スラッシュの有無はルーターで正規化します。存在しないパスと未知のモジュール ID には、トップとモジュール一覧へ戻れるアプリ内 404 を表示します。

## アーキテクチャ

### アプリの入口

`apps/docs/index.html` は `#app` と `/src/main.ts` の読み込みを持つ最小のアプリシェルにします。現在のトップページの内容は削除せず、ホーム画面のレンダラーとデータへ移します。

### ルーター

ルーターは `location.pathname` を解析し、ホーム、モジュール、互換ルート、404 のいずれかへ変換します。表示内容の生成は担当せず、ルートの解析と URL の生成だけを担当します。

同一オリジンのアプリ内リンクでは History API を使い、ページ全体を再読み込みせずに遷移します。`popstate` で戻る・進むを処理します。直接アクセスと再読み込みは Workers Static Assets の SPA fallback でアプリシェルへ戻します。

### レンダラー

ホーム画面とモジュール画面を別のレンダラーへ分けます。モジュール画面は共通レイアウトを組み立て、コマンド、ファイル表、チェックリスト、本文などの小さなセクションレンダラーへ処理を委譲します。

前後ナビゲーションはモジュール配列の順序から生成します。ページごとに URL や隣接モジュールを重複定義しません。

### スタイル

既存 Module 00 の配色、ヘッダー、ヒーロー、カード、表、コマンド表示、チェックリスト、レスポンシブ挙動を共通 CSS へ移します。Module 00 固有の文章や題材は CSS や HTML に残さず、コンテンツデータへ移します。

## コンテンツモデル

### 学習の起点

各モジュールは事故を必須にせず、主たる起点を判別共用体で表します。

```ts
type ModuleTrigger =
  | Readonly<{
      kind: "incident";
      situation: string;
      incident: string;
    }>
  | Readonly<{
      kind: "new-requirement";
      situation: string;
      requirement: string;
    }>
  | Readonly<{
      kind: "review";
      situation: string;
      reviewProblem: string;
    }>;
```

`review` はレビューの仕組みを改善する要求を表し、PRD の「要求」に含めます。画面は `kind` に応じて見出しと本文を切り替えます。どの起点からも、不変条件、ミッション、演習、効果確認へ同じ流れで接続します。

### モジュールに必要な情報

各モジュールは次の情報を持ちます。

- 主たる起点と状況
- 守るべき不変条件
- 今回使う技法と適用理由
- その技法では解決しない範囲
- 編集するファイルと最大2関数の対象
- Red と Green のコマンド、期待結果
- 読むファイルと注目箇所
- 実装手順と観察事項
- 変更容易性がどのように改善されたかの説明
- レビュー観点と完了条件
- 業務へ転用するための振り返り設問
- 時間不足時の代替進行と解答済みコードへの復帰方法
- 補足本文、コード例、参考リンク

本文は prose、code、command、file-table、checklist などの判別共用体で表します。レンダラーはブロックの種類ごとに必要なマークアップを生成します。自由形式の HTML 文字列はコンテンツデータへ保存しません。

### 最終演習

最終演習では、既習の技法だけを使い、問題の発見、技法の選択、最大2関数の局所変更、テストまたは型検査による効果確認を一巡します。

末尾には、参加者が自分の業務コードについて次の2点を記述するワークを置きます。

- 最初に見直す実装箇所
- その箇所で最初に試す行動

記述内容の外部送信や永続化は行いません。

## データフロー

1. 初回表示時に `location.pathname` を正規化します。
2. ルーターがパスをホーム、モジュール、互換ルート、404 のいずれかへ変換します。
3. モジュールルートでは slug に対応する型付きデータを取得します。
4. 対応するレンダラーが HTML を生成して `#app` へ反映します。
5. アプリ内リンクの選択時は URL を History API へ追加し、同じ処理で再描画します。
6. 戻る・進むでは `popstate` を受けて再描画します。
7. 描画後はページ先頭へ移動し、ページ見出しへフォーカスを移します。

## エラー処理

- 未知のパスと存在しない slug にはアプリ内 404 を表示します。
- モジュール ID の重複、空の必須項目、3関数以上の編集対象、PRD 必須項目の欠落はテストで失敗させます。
- コンテンツブロックの未対応種別は TypeScript の網羅性検査で検出します。
- 外部リンク、ダウンロード、別オリジンのリンクは History API で処理しません。
- 旧静的 Module 00 はデータ移行の確認後に削除します。静的ファイルが互換ルートを遮らない状態にしてからルーターで置き換えます。

## アクセシビリティとレスポンシブ対応

- `header`、`nav`、`main`、見出し、表、リストなどの意味に合う要素を使います。
- アプリ内遷移後にページ見出しへフォーカスを移し、表示内容が変わったことを伝えます。
- キーボードだけで全リンクとチェック項目へ到達できるようにします。
- コードとコマンドは横スクロールできるようにし、ページ全体の横スクロールを発生させません。
- 1440px と 390px で、本文、表、コード、ナビゲーションを確認します。

## テスト戦略

### 自動テスト

- パスの正規化、URL 生成、ホーム、各モジュール、404、互換ルートをテストします。
- 全モジュールについて PRD 必須項目、編集対象の上限、slug の一意性をテストします。
- ホーム、全モジュール、404 の主要な見出しとセクションをレンダリングテストで確認します。
- History API のリンク判定と `popstate` 後の再描画をテストします。
- `pnpm typecheck`、`pnpm test`、`pnpm build` を通します。

### 手動確認

- 各正規 URL を直接開き、再読み込みして同じ内容が表示されることを確認します。
- トップ、モジュール一覧、前後ナビゲーション、戻る・進むを確認します。
- `/module-00/` から正規 URL へ置き換わることを確認します。
- 未知の URL でアプリ内 404 が表示されることを確認します。
- 1440px と 390px で全ページの主要セクションを確認します。

## 完了条件

- トップと全モジュールがデータ駆動の共通レンダラーで表示されます。
- 未実装6モジュールが Module 00 と同じ詳細度で公開されます。
- 事故を必要としないモジュールは、新しい要求またはレビュー要求から自然に開始します。
- URL にハッシュを使わず、直リンク、再読み込み、戻る・進むが機能します。
- 旧 `/module-00/` の互換導線が機能します。
- PRD-01 から PRD-10 と PRD-12 の対応テストが成功します。
- PRD-11 が承認済みのスコープ例外として設計書と計画書に残ります。
- 型検査、テスト、ビルドが成功します。

## 主なリスクと対策

### トップページの内容が失われる

静的 HTML を空のアプリシェルへ置き換えるだけでは、PRD-01 に必要な導入説明が失われます。既存の文章と導線をホーム画面のレンダラーへ移してから、静的 HTML を縮小します。

### Module 00 の移行で詳細が欠落する

見た目だけを共通化すると、期待する失敗や読むファイルなどの学習情報が失われる可能性があります。既存ページのセクションを移行チェックリストにし、移行前後のレンダリングを比較します。

### PRD の必須項目がページごとに抜ける

目視レビューだけでは6ページの抜けを検出しづらいため、PRD の必須項目を型とコンテンツ契約テストで検査します。

### 旧静的ページがルーターを遮る

`public/module-00/index.html` が残ると Static Assets がルーターより先に応答します。コンテンツ移行を確認した後に静的ページを削除し、SPA fallback と互換ルートへ切り替えます。
