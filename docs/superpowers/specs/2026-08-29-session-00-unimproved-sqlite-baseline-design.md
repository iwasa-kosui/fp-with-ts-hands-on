# Session 00 未改善SQLiteベースライン設計

- 日付: 2026-08-29
- 状態: 承認済み

## 背景

現在の `examples/session-00/src/legacy` は、状態を `string` で扱い、予約全体をログへ出す最小限の実装だけを持ちます。この名前と配置では、未使用の旧コードに見えます。また、Session 02からSession 06で改善する対象の一部しか含まれないため、Session 00を読んでも後続セッションが必要な理由を十分に確認できません。

Session 00は、廃止予定のコードを保存する場所ではありません。参加者が引き継いだ現行システムとして動作し、後続セッションで改善する問題を観察するための開始スナップショットです。コードの配置は後続セッションと揃え、振る舞いと型の差を同じパスで比較できるようにします。

現行システムの問題はメモリ内の例だけでは再現しません。Finalと同じSQLite系の永続化を使い、プロセスを再起動しても不正な状態、個人情報を含む監査記録、状態と監査記録の不整合が残るようにします。

## 目的

- `src/legacy` と `Legacy` 接頭辞を廃止し、Session 02以降と対応するソース配置にします。
- Session 02からSession 06で扱う改善を一切行っていない現行システムを、動作するWebアプリケーションとして再現します。
- ブラウザ操作だけで各問題を発生させ、SQLiteへ保存された結果を同じ画面で確認できるようにします。
- Finalと同じ `better-sqlite3`、Drizzle ORM、SQL migrationを使い、Session 00のデータをファイルへ永続化します。
- Session 00の公開ページとCode Explorerから、事故と後続セッションの学習事項を対応付けられるようにします。

## 対象外

- Session 02からSession 07のin-memory storeをSQLiteへ変更しません。
- Finalの認証、管理画面、飼い主・ペット管理、フォローアップ一覧は複製しません。
- Session 00の問題を修正しません。安全なエラー型、入力検証、用途別ID、純粋な状態遷移、原子的なイベント保存は後続セッションの責務として残します。
- 意図的な問題と関係しない脆弱性は追加しません。SQL文字列連結やHTMLへの未加工出力は使いません。

## 未改善の予約モデル

`Appointment` は状態ごとの判別共用体にしません。一つの型へすべてのデータを置き、状態固有の値をoptional fieldとして持たせます。

- `status` は任意の `string` とします。
- 予約、ペット、飼い主、獣医師、検査、監査イベントのIDはすべて `string` とします。
- 氏名、メールアドレス、電話番号も通常の `string` として予約へ含めます。
- 診察、会計、キャンセルの情報は、現在状態と関係なく追加または上書きできるようにします。
- 状態更新関数は遷移元を限定せず、新しい状態と追加フィールドを受け取って予約全体を上書きします。
- 状態表示は網羅性検査のない `Record<string, string>` とfallbackで処理します。

このモデルにより、会計済みから診察中への戻り、不明な状態文字列、理由のないキャンセル、診察結果のない会計を型も実行時処理も拒否しません。

## 未検証の入力境界

`boundary/examResult.ts` は名前だけの境界です。`raw: any` を受け取り、スキーマ検査をせず検査結果として返します。

- 必須フィールドの欠落を許します。
- `items` が配列でなくても許します。
- リクエストの `petId` を予約の `petId` と照合しません。
- 読み取り専用の値に変換せず、受け取ったオブジェクトを後から変更できます。

Webの事故再現操作から、欠落値と型違いを含む検査結果を送信し、そのまま予約のJSON状態へ保存します。

## 失敗と副作用

`useCase/startExamination.ts` は、後続セッションで解消する問題を一つの処理に集めます。

- 予約が存在しない場合と状態が不正な場合に `Error` をthrowします。
- Web routeはエラーメッセージを調べ、予約なしを状態不正として誤って表示できる実装にします。
- `new Date().toISOString()` と `randomUUID()` を処理内で直接呼びます。
- 予約状態の更新と監査記録の追加を別々のSQLとして実行します。
- 状態更新後に監査記録が失敗しても、状態更新をrollbackしません。
- DB接続、時刻、ID generatorをResultのpipelineへ注入しません。
- DBの破損したJSONは検証せず、型アサーションで `Appointment` として返します。

通常操作では、同じ操作を繰り返すたびに異なる時刻とイベントIDが監査ログへ残ります。監査保存失敗の事故再現では、予約更新後に既存のイベントIDを再利用して一意制約違反を起こし、予約だけが更新された状態を確実に作ります。

## SQLite永続化

Finalと同じライブラリとmigration方式を使います。

- `better-sqlite3` でSQLiteファイルを開きます。
- Drizzle ORMでテーブルを定義し、`drizzle-orm/better-sqlite3/migrator` でSQL migrationを適用します。
- 開発時のDBは `examples/session-00/clinic.sqlite` とし、Git管理から除外します。
- `server.ts` は起動時にmigrationを適用します。
- 起動時は予約が存在しない場合だけデモデータを投入します。既存データを毎回resetしません。
- `POST /demo/reset` だけが予約と監査記録を削除し、既知の初期データを入れ直します。

DBには次の2テーブルを置きます。

`appointments` は `appointment_id`、`owner_id`、`pet_id`、`status`、`state` を持ちます。`state` は予約全体のJSONです。状態、IDの用途、JSON内部と列の一致を制約または読み出し時検査で保証しません。

`audit_logs` は `event_id`、`appointment_id`、`event_name`、`payload`、`occurred_at` を持ちます。`payload` には予約全体を保存し、飼い主の氏名、メールアドレス、電話番号も残します。

外部キー、状態のCHECK制約、予約更新と監査追加をまとめるトランザクションは使いません。これはSession 00で観察する問題の一部です。migration自体とデモresetは、教材を繰り返し実行できるように正常な方法で実装します。

## ブラウザで再現する事故

共通の `ClinicDashboard` にoptionalな事故再現領域を追加します。他セッションがこのpropsを渡さない場合、現在の表示と振る舞いは変わりません。

事故再現領域は、説明、実行ボタン、実行後に確認する結果を一組として表示します。

1. 通常フローを進めた後、会計済みの予約を診察中へ戻します。
2. 定義されていない状態 `waiting-for-magic` を保存します。
3. `ownerId` を `petId` の列とJSONへ保存します。
4. `petId` と `items` の形が不正な検査結果を保存します。
5. 存在しない予約で診察開始を試し、状態不正として表示されることを確認します。
6. 診察開始を繰り返し、毎回異なる時刻とイベントIDが生成されることを確認します。
7. 予約更新後に監査追加を失敗させ、予約の状態と監査件数が一致しない状態を作ります。
8. 監査payloadへ飼い主の連絡先が保存されていることを確認します。

画面下部には、現在の `appointments` 行、直近の `audit_logs`、検出した不整合を表示します。JSONはコード表示として描画し、HTMLとして解釈しません。

不整合の表示は、Session 00の壊れた業務処理とは分離した読み取り専用のデモ機能です。少なくとも次を表示します。

- 未知の状態文字列
- `ownerId` と `petId` が同じ値になっている状態
- 予約更新に対応する監査記録がない状態
- 監査payloadに含まれる連絡先フィールド

## Webとエラー境界

通常の予約操作は全状態で表示し、業務状態による非表示制御を行いません。これにより、画面から不正遷移を実行できます。

事故再現routeは固定された入力だけを使います。利用者が任意のSQLや保存先を指定する機能は作りません。DB例外や内部情報はHTTP response本文へ出さず、固定noticeへ変換します。ただし、予約なしと状態不正を誤分類する振る舞いは教材上の問題として残します。

監査追加失敗のrouteは例外を捕捉して固定noticeへredirectします。画面を再読込すると、先にcommitされた予約状態と不足した監査記録を確認できます。

## 公開教材

`examples/session-00/README.md` から `legacy` という表現を削除し、SQLiteへ保存される現行システムの観察方法を説明します。

`apps/docs/src/pages/sessions/00-system-handover.astro` のCode Explorerガイドは、次の改善軸を扱います。

- 任意の状態文字列とoptional field
- 用途を区別しないID
- `any` と検証のない外部入力
- PIIを含む監査payload
- throw、メッセージ判定、失敗理由の誤分類

各ガイドは、実装後の正確なファイルパスと行番号を参照します。Session 00では修正案を実装せず、事故、保存結果、後続セッションで確認する場所を結び付けます。

## テスト方針

新しい振る舞いはTDDで追加します。意図的に悪い振る舞いも回帰対象として明示します。

- `packages/clinic-web` では、事故再現propsを渡した場合だけ操作とDB表示が描画され、既存propsでは表示されないことを確認します。
- 予約モデルでは、不明な状態、ID取り違え、不正な検査結果を受け入れてしまうことを確認します。
- SQLite adaptorでは、予約と監査ログが別接続から読めること、監査payloadにPIIが残ることを確認します。
- 監査追加失敗では、処理が失敗しても予約更新だけが残ることを確認します。
- Webテストでは、各事故再現routeを実行し、画面のDB表示とnoticeから結果を確認します。
- 一時ファイルDBを使うintegration testで、アプリを作り直しても状態が残ることを確認します。
- `test`、`typecheck`、`build` をSession 00と共通UIで実行し、公開ドキュメントの契約テストも実行します。

テスト名には、正しい設計と誤認しないように「未改善の現行システムが許してしまう」「監査だけ欠落する」のような事故を表す文言を使います。
