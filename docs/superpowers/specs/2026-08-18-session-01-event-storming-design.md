# Session 01 をイベントストーミングによる業務モデリングへ再設計する

作成日: 2026-08-18

## 背景

現行の S1 は「ワークフロー・カード」の6欄を班で埋める15分の班ワークです。欄は trigger / input / current state / expected failures / output event / side effects で、S2〜S5 の各回がそれぞれの欄に対応します。

この構成には3つの問題があります。

第一に、6欄は `startExamination` の型シグネチャを日本語へ分解したものであり、業務のモデリングではなく実装の下書きになっています。Domain Modeling Made Functional が S1 相当の位置で扱うのは、データ構造ではなくビジネスイベントとワークフローです。現行の S1 はこの順序を逆にしています。

第二に、班が埋めた内容が成果物として残りません。`WorkflowCard.astro` の入力欄には保存機構がなく、ページを離れると消えます。S2〜S5 のページから S1 を開き直す導線もありません。「S1 で描いたものを S2〜S5 で埋めていく」という PRD の記述は、サイト上では成立していません。

第三に、「カード」という語が4つの別物を指しています。S1 の6欄ワークシート、S2〜S5 のリスク一覧の各項目、要求から次の問いまでの因果5段、設計判断と差分の対応が、いずれも `decision-card` として実装されています。運営文書にはさらに相互レビュー進行カードと解答カードがあります。[Issue #44](https://github.com/iwasa-kosui/fp-with-ts-hands-on/issues/44) が「診察開始カードが未定義語のまま S2〜S5 に出てくる」と指摘したのはこの状態の表層です。

## 変更後の S1

ゴールを次のように変えます。

> 散文で語られた業務からドメインイベントを拾い、コマンドとアクターを添え、同じ集約を変えるイベントをまとめて集約に名前を付けられるようになる。

対象範囲は来院から会計までの一連です。その中から予約・カルテ・会計の3つの集約を班で見つけます。S2〜S5 が予約集約のなかの診察開始コマンドだけを扱う理由が、参加者自身が見つけた集約として残ります。

持ち時間15分と内訳は現行のまま使います。

- ブリーフィング3分: 動物病院の一日を描いた散文を読みます
- 説明4分: ドメインイベント・コマンド・ワークフロー・集約の4語彙と手順4段を示し、講師が散文からドメインイベントを1件だけ拾って Excalidraw に置いて見せます
- 班ワーク6分: 残りのドメインイベントを散文から拾って時系列に並べ、各イベントに誰の何の依頼で起きたかを添え、同じ集約を変えるイベントをまとめて集約に名前を付けます
- レビュー2分: 講師回答例と比べ、粒度の違いを一つ挙げます

講師が実演するのは1件だけです。残りは班が拾います。散文から出来事を拾う動作が、参加者が自分の業務へ持ち帰れる唯一の部分だからです。並べ替えや集約のグルーピングは、拾った後の作業にあたります。

### 手順4段

ページに常設し、班ワーク中も参照できるようにします。参加者が自社の業務で同じことを再現するための手順です。

1. 起きた出来事を過去形で書き出す
2. 時間の順に並べる
3. それぞれの出来事が、誰の何の依頼で起きたかを添える
4. 同じ集約を変えるドメインイベントをまとめ、集約に名前を付ける

### 語彙

扱う語彙は4つです。

- ドメインイベント: 業務上起きた出来事。過去形で書きます
- コマンド: 誰かが出した依頼。ドメインイベントを引き起こします
- ワークフロー: 一つの依頼を受けてドメインイベントを出すまでのひとかたまり
- 集約: コマンドを受けて状態を変え、ドメインイベントを出す単位。一貫性を保って一緒に変わるまとまりです

集約を加えた理由は、手順4段の最後で囲む対象を確保するためです。診察開始のワークフロー境界だけを囲む場合、境界に含まれるイベントは「診察が開始された」1件しかなく、囲む対象が付箋1枚になります。班ワーク6分の実質が「並べる」だけになり、囲む作業が成立しません。集約を軸にすると、散文から予約・カルテ・会計の3つの集約が立ち上がり、それぞれに複数のイベントが対応するため、囲む作業に実質が生まれます。集約を見つけたことは S2 以降にも直接つながります。S2 が扱う予約の状態遷移は、S1 で見つけた予約集約の内部です。

ポリシー、読み取りモデル、外部システムは引き続き扱いません。15分で導入できる語彙数を超えるためです。

集約は「集約＝テーブル」「集約＝クラス」と誤解されやすい概念です。実装やデータベースを連想させる語では説明せず、コマンドを受けて一緒に変わる業務上のまとまりとして説明します。

S2〜S5 で使う型名（`ExaminationStarted`、`StartExaminationCommand` など）は S1 では出しません。業務の言葉のままモデルを描き切ることが S1 の主旨であり、型への対応づけは S2 の冒頭で行います。

## 素材となる散文

新規に書き下ろします。S0 は業務・操作・保存先を表で提示していますが、表からはドメインイベントを拾えません。S1 の散文は現場の一日を時間の流れで語る文章にします。

要件は次のとおりです。

- 分量は3分で読み切れる長さ、目安は600〜800文字
- 拾えるドメインイベントは5件前後。6分の班ワークで扱える上限です
- 来院から会計までを含みます。診察開始の前後だけに絞りません
- 誰が何をしたかが文中に現れます。アクターを推測させません
- 事故（二重請求・連絡先流出）は書きません。S0 で扱い済みであり、S1 は正常系の業務を描く回です
- 実装、画面、データベース、型に関する語を含みません

## 講師回答例のデータ

`WorkflowCard.astro` に配列としてハードコードされている現行の回答例を、S1 ページ（`apps/docs/src/pages/sessions/01-business-events-and-workflows.astro`）の frontmatter へ直接書きます。独立モジュールへの切り出しは行いません。

切り出しの目的だった「S2〜S5 からの引用」は、S2〜S5 の再構成と同じく本設計の範囲外です。現時点で S1 の回答例を参照する消費者は S1 ページ1つだけであり、消費者が2つになった時点で切り出せば足ります。

```ts
type DomainEvent = Readonly<{
  id: string;
  name: string;           // 過去形。「来院が受け付けられた」
  actor: string;          // 「受付スタッフ」
  command: string;        // 「来院を受け付ける」
  aggregate: string;      // 「予約」。このイベントが属する集約名
}>;
```

時系列の順序は配列の並び順で表します。イベントに時刻を持たせません。散文が語る一日は特定の日付を指しておらず、順序だけが意味を持つためです。

同じ `aggregate` を持つイベント列が、班がまとめるべき集約の答えにあたります。予約・カルテ・会計の3集約に分かれます。

## Excalidraw テンプレートと当日運用

班ワークはページ上ではなく Excalidraw で行います。テンプレートを `docs/event/session-01-event-storming.excalidraw` としてリポジトリで管理します。

テンプレートに含めるものは次のとおりです。

- 講師実演の1件が置かれた状態のドメインイベント
- 時系列の軸
- ドメインイベント・コマンド・アクター・集約の記入例を1組
- 手順4段

当日の運用は、TA が excalidraw.com でテンプレートを開き、Live collaboration を開始して班へリンクを配る形です。この手順をファシリテーターガイドへ追記します。班数分のリンクを事前に用意する案は採りません。リンクが外部に残り続けるためです。

## ページ構成

S1 ページには手順・散文・講師回答例だけを置きます。参加者が埋める場所はページに作りません。

- `#incident`: ブリーフィングと散文
- `#workflow`: 語彙4つ、手順4段、Excalidraw テンプレートへの導線
- `#review`: 講師回答例と、粒度の違いを比べる観点

`WorkflowCard.astro` は削除します。`WorkflowRiskMap` は S1 から外します。

## 未検証事項

- 6分で5件のドメインイベントを拾い、コマンドとアクターを添え、集約にまとめられるか。リハーサルで計測が必要です
- 語彙が3つから4つに増えたことで、6分の班ワークに収まるかの不確実性が上がっています。集約は「集約＝テーブル」「集約＝クラス」と誤解されやすく、説明4分での定義づけに時間がかかる可能性があります。リハーサルで計測が必要です
- Excalidraw の Live collaboration を班ごとに立ち上げる手順が、S1 の3分のブリーフィング中に完了するか
- 会場のネットワークで Excalidraw の共同編集が実用速度で動くか。動かない場合の代替として紙の付箋を用意するかどうか
