状態図もにぎやかに

動物は単なる飾りではなく、予約・受付・診察・会計の状態を見分けるサインとして使う。

🐾 Discriminated Union
状態ごとに持てる値と遷移関数を分ける。
🎫 Branded Type
診察券番号をただの string から分離する。
🧪 Result
失敗を例外ではなく戻り値で表す。
🔒 Sensitive
ログに出ると困る値を runtime でも赤く隠す。
📜 Domain Event
あとから事故を追える変更記録を残す。
🤖 Agent Review
AI が業務ルールを外していないか見る。

3時間の流れ

事故から始め、型で状態遷移と入力境界を閉じ、最後に AI エージェントへ同じ変更を頼む前提でレビューする。

0:10-0:25 🐢 事故を起こす Paid -> InExamination を再現し、なぜ通るのかを見る。
0:25-0:40 🐕 事故を読む テスト、型、業務ルールのどこに穴があるかを読む。
0:40-1:10 🐾 Discriminated Union 状態ごとに持てる値と遷移関数を分ける。
1:20-1:45 🎫 Zod / Brand / PII 外部入力を検査し、飼い主連絡先は Sensitive でログ漏えいから守る。
1:45-2:15 🧪 Result と Event 失敗を戻り値にし、成功した診察開始だけを変更記録に残す。
2:15-2:35 🤖 Agent Review 同じ変更を AI に頼むなら、どこを疑うかを明文化する。
2:35-2:50 🐈 ミニ総合演習 事故、境界、Result、レビューを小さく一周する。

参考記事を教材に混ぜる

既存記事は別枠の読み物にせず、境界・ログ・変更記録の module に差し込む。記事の主張を小さなテストに落とし、当日の納得度につなげる。

🔒 PII ログ防御 構造的部分型や Branded Type だけではログ漏えいを防げない。Zod 境界で Sensitive に包む。 📜 ドメインイベント 状態変更をあとから調査できる出来事として記録する。失敗時には余計な event を残さない。

コードも読みやすく

見た目はポップにしつつ、本文とコードの読みやすさは残す。可愛い画面から、型で守るルールへ自然に入る。

守りたい不変条件

Paid は終端状態。診察室に戻る遷移は業務上存在しない。

type VisitStatus =
  | "Scheduled"
  | "CheckedIn"
  | "InExamination"
  | "Paid"
  | "Canceled";

const moveToExamination = (visit: Visit): Visit => ({
  ...visit,
  status: "InExamination",
});

// Incident: Paid -> InExamination が通ってしまう
moveToExamination(paidVisit);
